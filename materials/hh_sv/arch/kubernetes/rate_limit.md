# Rate Limiting

Этот механизм называется Rate Limiting (ограничение частоты запросов). В
контексте безопасности и антифрода он решает две задачи: защищает сервер от
перегрузки (DoS-атаки) и останавливает мошенников, которые пытаются перебрать
пароли или массово выкачать данные.

Основные компоненты механизма

Механизм состоит из трех ключевых частей:

1. KeyResolver: Определяет, по какому признаку ограничивать запросы. Например,
   это может быть IP-адрес пользователя, API-ключ или ID авторизованного
   пользователя.
2. RateLimiter (Алгоритм): В Spring Cloud Gateway по умолчанию используется
   алгоритм Token Bucket (корзина токенов).
3. Хранилище (Redis): Используется для хранения счетчиков токенов в
   централизованном виде. Без Redis лимиты будут применяться к каждой копии
   Gateway отдельно, что позволит пользователям обходить ограничения, обращаясь
   к разным подам.

Как работает алгоритм Token Bucket

Алгоритм имитирует "корзину" с токенами, которая пополняется с фиксированной
скоростью:

1. Replenish Rate (Скорость пополнения): Определяет, сколько токенов добавляется
   в корзину каждую секунду.
2. Burst Capacity (Пиковая емкость): Максимальный размер корзины. Это количество
   запросов, которое пользователь может выполнить мгновенно за одну секунду
   (всплеск трафика).
3. Запрос: Каждый входящий запрос пытается забрать один токен (параметр
   requestedTokens, по умолчанию равен 1).
4. Результат: Если токен есть, запрос проходит дальше. Если корзина пуста,
   Gateway возвращает ошибку HTTP 429 Too Many Requests

В мире Spring Boot и микросервисов это реализуется тремя основными способами:

1. На уровне API Gateway (Рекомендуемый подход)
   Если вы используете Spring Cloud Gateway, в него уже встроен
   RequestRateLimiter. Он работает на базе алгоритма Token Bucket (корзина
   токенов) и использует Redis.

* Как это работает: У пользователя есть «корзина», куда каждую секунду капает,
  например, 5 токенов. Один запрос = один токен. Если токены кончились, сервер
  возвращает ошибку 429 Too Many Requests.
* Плюс: Запрос отсекается еще «на входе» в вашу сеть, не нагружая
  бизнес-микросервисы.

2. На уровне приложения (Bucket4j)
   Если шлюза нет или нужна специфичная логика внутри микросервиса, используют
   библиотеку Bucket4j.

// Пример создания лимита: 10 запросов в минуту
Refill refill = Refill.intervally (10, Duration.ofMinutes (1));
Bandwidth limit = Bandwidth.classic (10, refill);
Bucket bucket = Bucket.builder ().addLimit (limit).build ();
if (bucket.tryConsume (1)) {
// исполняем запрос
} else {
// выкидываем 429 ошибку
}

3. На уровне инфраструктуры (Nginx / Service Mesh)
   Ограничение можно настроить в конфиге Nginx (limit_req_zone) или средствами
   Service Mesh (например, Istio). Это самый быстрый и «дешевый» для ресурсов
   способ, но он плохо знает о бизнес-логике (например, о ID пользователя внутри
   JWT).

Алгоритмы, которые стоят за этим:

* Fixed Window (Фиксированное окно): Сбрасывает счетчик ровно в 00:00, 00:01 и
  т.д. (Минус: в стыке минут можно пропустить двойную нагрузку).
* Sliding Window (Скользящее окно): Более точный, считает запросы за последние
  60 секунд относительно текущего момента.
* Leaky Bucket (Протекающее ведро): Обрабатывает запросы с постоянной скоростью,
  «выравнивая» всплески трафика.

Интересно посмотреть пример конфига для Spring Cloud Gateway, чтобы ограничение
работало автоматически для всех маршрутов?

Настройка через API GATEWAY:

Представьте, что API Gateway — это «вышибала» на входе в клуб (вашу систему
микросервисов). Вместо того чтобы каждый микросервис (бармен, диджей, охрана
внутри) сам проверял паспорт и считал, сколько раз зашел гость, это делает один
человек на входе.
В Spring Cloud Gateway это работает так: запрос от пользователя попадает сначала
на шлюз. Шлюз смотрит в Redis (общую память) и спрашивает: «Этот пользователь
(или IP) за последние 60 секунд заходил больше 10 раз?». Если да — шлюз сразу
разворачивает его с ошибкой 429 Too Many Requests, даже не беспокоя ваши
микросервисы.
Как это настраивается (Пример)
В файле конфигурации application.yml вашего Gateway-сервиса вы просто
прописываете правила:

``` yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://ORDER-SERVICE
          predicates:
            - Path=/orders/**
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 5    # Сколько запросов в секунду разрешено (скорость пополнения)
                redis-rate-limiter.burstCapacity: 10   # Максимальный "всплеск" (размер корзины)
                key-resolver: "#{@userKeyResolver}"    # По какому признаку считать (например, по ID пользователя)
```

Главные фишки этого подхода:

1. Экономия ресурсов: Ваши тяжелые микросервисы на Java (Spring Boot) даже не
   узнают, что была попытка флуда. Они не тратят память и процессор на обработку
   лишних запросов.
2. Единая точка входа: Вам не нужно писать код защиты в каждом микросервисе.
   Настроили в одном месте — защитили всё.
3. Централизованный лимит: Если у вас 5 инстансов микросервиса заказов, лимит
   будет общим для всех, так как данные хранятся в одном Redis.

Что такое KeyResolver?
Это небольшой Java-бин, который говорит шлюзу, кого именно мы ограничиваем.
Обычно ограничивают по userId из токена или по IP-адресу:

@Bean
public KeyResolver userKeyResolver () {
// Ограничиваем по ID пользователя из заголовка или JWT
return exchange -> Mono.just (exchange.getRequest ().getHeaders ().getFirst (
"X-User-Id"));
}

Хотите увидеть, как выглядит полная цепочка запроса от браузера через Gateway до
микросервиса при срабатывании такой защиты?

да:

Вот как выглядит прохождение запроса через Spring Cloud Gateway с включенным
Rate Limiter (на базе Redis).
Схема цепочки запроса

1. Клиент (Браузер/App): Отправляет HTTP-запрос (например, POST /orders).
2. Gateway (Вход): Принимает запрос и определяет маршрут (Route).
3. KeyResolver (Определение цели): Извлекает идентификатор (например, userId из
   JWT или IP-адрес).
4. Redis (Проверка лимита): Gateway выполняет атомарный Lua-скрипт в Redis:
    * Есть токены? Уменьшает счетчик на 1 и пропускает запрос дальше.
    * Нет токенов? Возвращает статус 429 сразу клиенту.
5. Микросервис (Order Service): Получает запрос только если лимит не превышен.
6. Ответ: Проходит обратно через Gateway к клиенту.

Как это выглядит в цифрах (Логика "Корзины")
Представьте настройки: replenishRate: 5 (5 зап/сек) и burstCapacity: 10 (макс.
запас).

| Время (сек) | Запросы от юзера | Состояние корзины в Redis | Результат                          |
|-------------|------------------|---------------------------|------------------------------------|
| 0.0         | 8 запросов разом | Было 10, стало 2          | 200 OK (все 8 прошли)              |
| 0.5         | 4 запроса разом  | Было 2, не хватает!       | 429 Too Many Requests (для всех 4) |
| 1.0         | 1 запрос         | Корзина пополнилась на 5  | 200 OK                             |

Визуализация заголовков (Response Headers)
Когда Gateway возвращает ответ, он добавляет специальные заголовки, чтобы клиент
(фронтенд) понимал, что происходит:

* X-RateLimit-Remaining: Сколько запросов осталось в текущем окне.
* X-RateLimit-Burst-Capacity: Максимальный размер всплеска.
* X-RateLimit-Replenish-Rate: Скорость пополнения.

Почему это круто для антифрода?
Если мошенник запустит скрипт, который делает 1000 запросов в секунду, ваш
Spring Boot микросервис даже не шелохнется. Gateway отсечет 995 запросов на
уровне Redis-проверки. Это защищает базу данных и процессор от бесполезной
работы.
