## Проектирование для Spring Framework и JDBC:

## JdbcTemplate

Однозначно лучше использовать JdbcTemplate. Это «золотой стандарт» для проектов
на Spring без Hibernate.
Если «чистый» JDBC заставляет вас вручную открывать/закрывать Connection,
обрабатывать SQLException и возиться с ResultSet, то JdbcTemplate берет всю
рутину на себя.
Почему для вашего проекта (2-3 недели) это лучше:

1. Меньше кода (Boilerplate): Вместо 20 строк кода для простого запроса
   останется 3–5. Вы успеете сделать больше фич за спринт.
2. Безопасность из коробки: Он автоматически использует PreparedStatement, что
   защищает от SQL-инъекций.
3. Удобный маппинг: Вам не нужно перебирать rs.next (). Метод queryForObject или
   query сделает это за вас.
4. Интеграция с транзакциями: Он идеально работает с аннотацией @Transactional.
   Если что-то пойдет не так, Spring сам откатит изменения.

Пример, как меняется проектирование кода:

```java
public void demo() {

// Было (Чистый JDBC):
    Connection conn = dataSource.getConnection();
    PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE id = ?");
    ps.setLong(1, id);

    ResultSet rs = ps.executeQuery();
    if (rs.next()) {
        User user = new User(rs.getLong("id"), rs.getString("name"));
// И не забыть закрыть всё в finally...
    }
}

// Стало (JdbcTemplate):
public User findById(Long id) {
    return jdbcTemplate.queryForObject(
            "SELECT * FROM users WHERE id = ?",
            (rs, rowNum) -> new User(rs.getLong("id"), rs.getString("name")),
            id
    );
}
```

## Общие положения

Проектирование БД — тема глубокая, и кажется, что нужно рассказать сразу всё. На
самом деле интервьюер хочет увидеть твой алгоритм мышления.
Давай подготовим «золотой ответ» на случай, если этот вопрос возникнет снова (а
он возникнет). Раздели ответ на 4 четких этапа:

1. Как ты выделял таблицы (Логический уровень)
   «Да, у каждого сервиса была своя БД (PostgreSQL). Проектирование я начинал с
   анализа бизнес-сущностей.

    * Например, в сервисе чеков главной таблицей была receipts.
    * Я приводил структуру к 3-й нормальной форме, чтобы избежать дублирования.
    * Выделял справочники (например, типы статусов чека или категории магазинов)
      в отдельные таблицы, связывая их через Foreign Keys».

2. Как ты выбирал типы данных (Технический уровень)
   «Для надежности в распределенной системе я использовал UUID в качестве
   первичных ключей (Primary Keys) вместо обычных Long. Это позволяло
   генерировать ID на стороне сервиса и не бояться коллизий при миграциях. Для
   дат всегда использовал TIMESTAMPTZ, чтобы не было проблем с часовыми поясами
   в федеральном проекте».
3. Как ты заботился о скорости (Производительность)
   «Я проектировал индексы под конкретные запросы:

    * Обязательно B-tree индексы на поля, по которым идет поиск (например,
      user_id).
    * Unique Constraints на связку полей (номер чека + ИНН магазина), чтобы база
      сама отсекала дубликаты чеков (базовый антифрод)».

4. Как ты управлял изменениями (Процессы)
   «Все изменения структуры я описывал через Liquibase. Это позволяло
   версионировать базу вместе с кодом и безопасно накатывать изменения на
   тестовые и продакшн-стенды через CI/CD».

Если спросят про БД, начни так:

«Я проектировал базы исходя из принципа Database-per-service. В каждом сервисе я
строил схему в 3-й нормальной форме, закладывал индексы под бизнес-запросы и
управлял схемой через Liquibase...» — и дальше по пунктам выше.

# === Highload ===

Тема Highload (высоких нагрузок) — это всегда про поиск «бутылочного горлышка» и
умение распределять работу. Если тебя спросят: «Как подготовить систему к
наплыву 3000 пользователей в минуту?», отвечай системно, разделяя приложение и
базу.
Вот твой чек-лист для уверенного ответа:

1. Как подготовить Приложение (Прикладной уровень)

    * Горизонтальное масштабируемость: «Я проектирую сервисы как Stateless (без
      состояния). Это позволяет поднять в Kubernetes 10 копий сервиса вместо
      одной, а Load Balancer равномерно распределит трафик между ними».
    * Асинхронность (Kafka): «Самые тяжелые задачи (OCR, отправка уведомлений) я
      выношу из синхронного потока. Пользователь получает ответ "Принято", а
      данные улетают в очередь. Это защищает сервис от нехватки потоков (Thread
      Exhaustion)».
    * Java 21 (Virtual Threads): «Для I/O-интенсивных задач (запросы к БД или
      внешним API) я использую виртуальные потоки. Они позволяют обрабатывать
      тысячи одновременных соединений, не раздувая пул системных потоков».
    * Кэширование: «Часто запрашиваемые данные (например, список активных акций)
      я храню в Redis. Это снимает нагрузку с основной базы данных».

2. Как подготовить Базу Данных (Уровень данных)

    * Индексация: «Первым делом я проверяю, чтобы все запросы в WHERE и JOIN шли
      по индексам. Использую EXPLAIN ANALYZE, чтобы найти медленные запросы».
    * Пул соединений (Connection Pool): «Я настраиваю HikariCP, чтобы приложение
      не тратило время на создание нового коннекта к БД на каждый чих».
    * Разделение Чтения и Записи (Read Replicas): «Если запросов на чтение
      (просмотр призов) слишком много, я настраиваю репликацию: запись идет в
      Master-базу, а чтение — с нескольких Slave-реплик».
    * Партиционирование: «Для таблицы чеков я использую Partitioning по дате.
      Postgres будет искать не во всей базе за год, а только в маленькой секции
      за текущий месяц».

3. Что делать, чтобы всё НЕ упало (Надежность)

    * Circuit Breaker (Предохранитель): «Я использую библиотеки типа
      Resilience4j. Если внешний API (например, ФНС) начинает тормозить или
      падать, мой сервис перестает его спамить запросами, отдавая заглушку. Это
      спасает всю цепочку от каскадного падения».
    * Rate Limiting: «На уровне API Gateway я ограничиваю количество запросов с
      одного IP, чтобы защититься от ботов или случайных DDOS-атак».
    * Graceful Shutdown: «Настраиваю корректное завершение работы сервиса, чтобы
      при обновлении в K8s он успел дописать текущие транзакции в БД и только
      потом выключился».

4. Оптимизация (Как найти проблему)

    * Мониторинг (Grafana): «Я смотрю на 4 "Золотых сигнала": Latency
      (задержка), Traffic (нагрузка), Errors (ошибки) и Saturation (насыщенность
      ресурсами — CPU/RAM)».
    * Логирование (Loki): «По Trace ID я отслеживаю, на каком именно
      микросервисе запрос начал "тормозить"».

Твой "козырь" на интервью:
Если тебя спросят: "С чего начнешь оптимизацию?", скажи:

      «Я не буду гадать. Я сначала настрою метрики и профилирование, найду 
      самое узкое место (через EXPLAIN в БД или замеры времени в коде) и буду 
      лечить именно его. Преждевременная оптимизация — корень всех зол».

## Оптимизация БД

### Оптимизация БД с JDBC

Оптимизация в Spring JDBC (JdbcTemplate) отличается от JPA/Hibernate тем, что вы
контролируете каждый символ в SQL. Это дает огромную гибкость, но требует
дисциплины.
Вот 5 способов выжать максимум из ваших запросов за 2-3 недели спринта:

1. Используйте Batch Updates (Пакетная вставка)
   Если вам нужно сохранить 100+ записей, не делайте 100 вызовов update (). Это
   «убьет» сеть и БД.

    * Как: Используйте jdbcTemplate.batchUpdate (). Он отправит один массив
      данных одним пакетом.
    * Эффект: Ускорение записи в 10–50 раз.

2. Ограничение выборки (Fetch Size)
   По умолчанию JDBC может пытаться вытянуть все 100 000 строк в память Java,
   что приведет к OutOfMemory.

    * Как: Настройте jdbcTemplate.setFetchSize (100). Это скажет драйверу тянуть
      данные порциями.
    * Эффект: Стабильное потребление памяти приложением под нагрузкой.

3. NamedParameterJdbcTemplate вместо обычного
   В обычном JdbcTemplate параметры ставятся через ?. Если их 20, легко
   ошибиться порядком.

    * Как: Используйте именованные параметры: WHERE id = :userId.
    * Эффект: Код становится читаемым, его легче отлаживать во время ваших
      демо-встреч с заказчиком.

4. Правильный маппинг (RowMapper vs ResultSetExtractor)

    * RowMapper: Идеален для списков объектов (одна строка БД = один объект).
    * ResultSetExtractor: Нужен, если одна строка БД превращается в сложную
      структуру или если вы делаете JOIN (один заказ + 5 товаров).
    * Зачем: Это позволяет избежать повторных запросов к БД в цикле (проблема
      N+1), которые часто возникают при проектировании «в лоб».

5. Индексы и EXPLAIN (Уровень БД)
   Spring JDBC не спасет, если в базе нет индексов.

    * Как: Возьмите тяжелый запрос из кода и выполните его в консоли БД с
      префиксом EXPLAIN ANALYZE.
    * На что смотреть: Если видите Seq Scan на большой таблице — нужен индекс. В
      Spring-приложении убедитесь, что вы ищете по тем колонкам, которые
      индексированы (Foreign Keys, артикулы, даты).

6. Внешний пул соединений (HikariCP)
   В старых проектах часто забывают про пул. Если каждое обращение к БД
   открывает новое физическое соединение — это провал.

    * Как: Подключите HikariCP. Он держит «горячие» соединения готовыми к
      работе.
    * Эффект: Мгновенный отклик приложения.

Маленький лайфхак для вашего спринта:
Чтобы быстро понять, какие запросы тормозят, включите логирование SQL в
logback.xml или через настройки DataSource. Вы сразу увидите в консоли Tomcat,
какой запрос «висит» больше секунды.

### Общее

Нагрузка на базу данных (БД) — это часто самое узкое место в Highload. Если
приложение можно легко масштабировать, просто добавив новые поды в Kubernetes,
то с БД всё сложнее.
Вот как Middle-разработчик должен отвечать на вопрос об отслеживании и
оптимизации нагрузки на PostgreSQL:

1. Как отследить нагрузку? (Monitoring)
   Мы мониторим БД через Grafana, куда данные попадают из специального агента —
   postgres_exporter.

    * CPU и Load Average: Если процессор загружен на 90%+, значит, база
      захлебывается в тяжелых расчетах или неэффективных индексах.
    * Connections: Сколько сейчас активных соединений из HikariCP. Если мы
      упираемся в max_connections, новые запросы от приложения будут падать с
      ошибкой.
    * Transaction Throughput (TPS): Сколько транзакций в секунду проходит через
      базу.
    * Slow Queries: Самое важное. Мы смотрим топ самых медленных запросов через
      расширение pg_stat_statements. Оно показывает, какие запросы выполняются
      дольше всего и сколько ресурсов потребляют.

2. Как оптимизировать? (Performance Tuning)
   Если мы видим, что база «тормозит» на 1000 RPS, наш план действий:

    * Индексация (Index Scan vs Seq Scan): Мы запускаем запрос с приставкой
      EXPLAIN ANALYZE. Если видим Sequential Scan (полный перебор таблицы),
      значит, нужно добавить индекс на поля в WHERE или JOIN.
    * Устранение N+1 в Hibernate: Проверяем логи, чтобы Hibernate не делал 100
      отдельных запросов к базе там, где можно сделать один JOIN (используем
      @EntityGraph или JOIN FETCH).
    * Пул соединений (HikariCP): Оптимизируем настройки пула на стороне Spring
      Boot. Слишком маленький пул заставляет потоки ждать, слишком большой —
      перегружает память БД.
    * Connection Bouncer (PgBouncer): Если микросервисов много, мы ставим перед
      Postgres прокси-сервер PgBouncer, который эффективно переиспользует
      соединения и не дает базе упасть от тысяч коннектов.

3. Архитектурные решения для Highload
   Если индексы уже не помогают:

    * Read Replicas: Настраиваем репликацию. Приложение пишет в Master, а все
      SELECT-запросы (просмотр истории чеков, личный кабинет) идут на
      Slave-реплики. Это кратно увеличивает пропускную способность на чтение.
    * Кэширование в Redis: Выносим «горячие» данные (настройки акций,
      справочники) в Redis, чтобы вообще не дергать Postgres.
    * Партиционирование: Делим огромную таблицу чеков на части (например, по
      месяцам). Postgres будет искать данные только в нужной секции, что ускорит
      поиск в разы.

Как ответить на интервью (Твой сценарий):

      «Нагрузку на БД я отслеживал в Grafana через метрики postgres_exporter. 
      Основной фокус был на Slow Queries и загрузке CPU. Для оптимизации я 
      использовал EXPLAIN ANALYZE, чтобы выявлять неэффективные запросы и 
      настраивать индексы. В критических узлах мы переходили с Hibernate на 
      Spring JDBC, чтобы полностью контролировать SQL. Также для снижения 
      нагрузки на мастер-базу мы использовали Read Replicas для тяжелых 
      аналитических выборок».

Каверзный вопрос: «Что делать, если база начала "тормозить" прямо сейчас на
продакшене?»
Твой ответ:

1. Посмотрю в Grafana на количество активных транзакций и заблокированных строк
   (Locks).
2. Найду самый «тяжелый» запрос через pg_stat_activity.
3. Если он «вешает» базу — приму решение об убийстве этого процесса
   (pg_terminate_backend) и пойду разбираться, почему он не попал в индексы.

### pg_stat_statements

pg_stat_statements — это стандартный модуль расширения для PostgreSQL, который
собирает подробную статистику выполнения всех SQL-запросов на сервере.

Это основной инструмент для поиска «тяжелых» и медленных запросов, позволяющий
понять, какие из них больше всего нагружают систему.

Основные возможности

1. Группировка запросов: Модуль нормализует запросы (заменяет конкретные
   значения констант на параметры), объединяя похожие операции в одну запись для
   удобного анализа.
2. Метрики выполнения: Для каждой группы запросов отслеживаются:
3. Количество вызовов (calls).
    - Общее, среднее, минимальное и максимальное время выполнения.
    - Количество затронутых строк (rows).
    - Статистика по работе с кэшем (чтение и запись блоков данных).
4. Планирование: Начиная с версии PostgreSQL 13, расширение также может
   отслеживать время, затраченное на планирование запросов.

Как включить расширение
Поскольку модулю требуется дополнительная разделяемая память, его настройка
проходит в два этапа:

1. На уровне сервера: Добавьте название модуля в файл конфигурации
   postgresql.conf и перезапустите базу данных:

  ```text 
    shared_preload_libraries = 'pg_stat_statements'
  ```

2. На уровне базы данных: Выполните SQL-команду для создания объектов
   расширения:

   CREATE EXTENSION pg_stat_statements;

Использование
После установки данные доступны через представление pg_stat_statements. Типичный
запрос для поиска 5 самых длительных по общему времени выполнения запросов
выглядит так:

```sql
   SELECT query, calls, total_exec_time, mean_exec_time
   FROM pg_stat_statements
   ORDER BY total_exec_time DESC
   LIMIT 5;
```

**Параметры:**

Для эффективной настройки pg_stat_statements в postgresql.conf стоит обратить
внимание на три ключевых параметра:

1. pg_stat_statements.max: Определяет максимальное количество уникальных
   запросов, которые модуль будет хранить (по умолчанию 5000). Если база
   высоконагруженная и запросов очень много, старые записи будут вытесняться.
   Если памяти достаточно, это значение можно смело увеличивать до 10000 и выше.
2. pg_stat_statements.track: Указывает, какие запросы отслеживать.
    * top — только те, что прислал клиент напрямую (по умолчанию).
    * all — включая вложенные запросы (например, внутри функций и триггеров).
      Это полезно для глубокого анализа, но создает чуть больше нагрузки.
3. pg_stat_statements.track_planning: Появился в новых версиях. Если включить
   (on), модуль будет считать время, которое PostgreSQL тратит на построение
   плана запроса, а не только на его выполнение. Это помогает найти запросы,
   которые «планируются» дольше, чем работают.

### HicariCP

HikariCP — это современный и очень быстрый «пул соединений» (Connection Pool)
для Java-приложений. В Spring Boot он идет по умолчанию.
Зачем он нужен?
Создание физического соединения с базой данных (PostgreSQL) — это «дорогая» и
долгая операция (нужно установить TCP-сессию, пройти авторизацию и т.д.).
Если на каждый запрос от пользователя открывать новое соединение, база «умрет»
от нагрузки, а пользователь будет ждать лишние 100–200 мс.
HikariCP при старте приложения открывает, например, 10 соединений и держит их
«горячими». Когда приходит запрос, Spring просто берет готовое соединение из
пула, использует его и возвращает обратно.

Как его настраивать (в application.properties)
Для Middle-разработчика важно знать 3–4 ключевых параметра:

```properties
# Максимальное количество соединений в пуле (по умолчанию 10)
spring.datasource.hikari.maximum-pool-size=20
# Минимальное количество «спящих» соединений
spring.datasource.hikari.minimum-idle=5
# Сколько времени поток готов ждать свободное соединение из пула (мс)
spring.datasource.hikari.connection-timeout=30000
# Максимальное время жизни одного соединения (чтобы база не копила ошибки)
spring.datasource.hikari.max-lifetime=1800000
```

Как отвечать на интервью (Твой сценарий):

      «В проекте мы использовали HikariCP как стандартный пул соединений. 
      Основная настройка, которую мы оптимизировали под нагрузку в 1000 RPS — 
      это maximum-pool-size.
      Мы подбирали его опытным путем: слишком маленькое значение заставляло 
      потоки (особенно Virtual Threads) ждать в очереди (ConnectionTimeout), 
      а слишком большое — перегружало память PostgreSQL. Также мы настраивали 
      max-lifetime, чтобы вовремя обновлять "уставшие" соединения и не 
      ловить ошибки связи с БД».

Твой «козырь» (Связь с Java 21):
«Важно понимать, что при использовании Virtual Threads (где тысячи потоков)
нельзя ставить пул в 1000 соединений — база просто упадет. Виртуальные потоки
очень эффективны, но они все равно должны стоять в очереди за ограниченным
количеством соединений в HikariCP (например, 30–50 штук на инстанс)».

Резюме: HikariCP — это про эффективное переиспользование ресурсов.

### Необходимое количество инстансов для highload приложений

Вопрос про количество экземпляров (реплик) — это проверка на твой опыт
эксплуатации системы в реальном бою. Здесь нет одной цифры на все случаи жизни,
но есть стандарты индустрии.

1. Сколько реплик приложения (Микросервиса)?
   В Kubernetes количество экземпляров (подов) определяется нагрузкой (те самые
   RPS) и требованием к отказоустойчивости.

    * Минимум — 2 инстанса: Никогда не держи один. Если один под упадет или
      будет перезагружаться при обновлении, второй подхватит трафик. Это
      называется High Availability (HA).
    * Стандарт для Middle-проекта — 3-5 инстансов: Этого достаточно, чтобы
      выдержать 1000 RPS на Java 21. Если один сервер (нода) в кластере выйдет
      из строя, у тебя останется еще несколько рабочих копий на других серверах.
    * Как определить точно? Через HPA (Horizontal Pod Autoscaler). Ты
      настраиваешь правило в K8s: «Если загрузка CPU на подах > 70%, добавь еще
      2 копии». Система сама будет раздуваться до 10-20 инстансов в пики акций и
      сдуваться ночью.

2. Сколько экземпляров Базы Данных?
   С базой всё сложнее, так как данные должны быть синхронизированы.

* Классика (Master + Replica):
    * 1 Master (основной узел для записи чтения).
    * 1-2 Replica (Slave) (копии только для чтения).
    * Если Master упадет, одна из реплик станет новым мастером (Failover).
* Зачем больше? Если у тебя очень много тяжелых SELECT-запросов (аналитика,
  списки чеков), ты добавляешь 3-5 реплик и распределяешь чтение между ними.

3. Как определить, сколько нужно именно тебе? (Алгоритм)
   На интервью отвечай так: «Количество ресурсов я определяю через Load Testing
   (Нагрузочное тестирование)».
   Твой план действий:

    1. Замер ресурсов (Baseline): Запускаем один экземпляр сервиса и даем на
       него нагрузку (например, через JMeter).
    2. Поиск лимита: Смотрим, при каком RPS сервис начинает «тупить» (растет
       Latency) или потреблять слишком много CPU/RAM. Допустим, один сервис
       тянет 300 RPS.
    3. Расчет: Если нам нужно держать 1000 RPS, нам нужно минимум 4 инстанса + 1
       запасной на случай сбоя = 5 инстансов.
    4. Мониторинг: В продакшене смотрим в Grafana. Если загрузка CPU на подах
       постоянно низкая (10-20%), мы уменьшаем количество копий, чтобы не
       тратить деньги компании.

Как ответить на интервью (Твой сценарий):

      «В моем проекте для обеспечения отказоустойчивости мы использовали 
      минимум 3 реплики каждого микросервиса в Kubernetes. Это позволяло 
      проводить бесшовные обновления (Rolling Update) и выдерживать падение 
      одной ноды кластера.
      Для базы данных PostgreSQL мы использовали связку Master + 2 Read 
      Replicas, чтобы распределить нагрузку на чтение.
      Точное количество инстансов мы определяли на основе нагрузочного 
      тестирования, подбирая оптимальный баланс между пропускной способностью 
      (RPS) и потреблением ресурсов (CPU/RAM)».

Твой козырь (Связь с Java 21):
«Благодаря переходу на Java 21 и Virtual Threads, нам удалось снизить количество
необходимых реплик приложения, так как каждый инстанс стал эффективнее
обрабатывать блокирующие вызовы к БД, не упираясь в лимиты системных потоков».

# === PostgreSQL ===

В контексте системы с розыгрышем призов по чекам, вопросы по PostgreSQL будут
касаться двух вещей: как вы справлялись с нагрузкой (когда тысячи людей
одновременно грузят чеки) и как обеспечивали целостность (чтобы один чек не
разыграли дважды).
Вот основные темы и лучшие ответы для Middle-уровня:

1. Индексы: как ускорить поиск?
   Вопрос: Какие индексы вы создавали в таблице чеков?
    * Ответ: «Помимо Primary Key, я обязательно создавал Unique Index на связку
      серия_номера + номер_чека + дата + ИНН_магазина (или на фискальный признак
      чека — ФП/ФД). Это решало сразу две задачи:
      быстрый поиск чека при загрузке и автоматическую защиту от дубликатов на
      уровне БД».
    * Продвинутый уровень: Упомяните, что для аналитики по датам использовали
      B-tree индекс, а если был поиск по метаданным чека (JSONB), то
      использовали GIN-индекс.

2. Уровни изоляции транзакций и гонки (Race Conditions)
   Вопрос: Как вы гарантировали, что один и тот же приз не выдадут двум разным
   пользователям в один момент?
    * Ответ: «Для критических операций (выдача приза) я использовал стандартный
      уровень Read Committed, но с механизмом пессимистической блокировки
      (SELECT ... FOR UPDATE). Когда сервис розыгрыша выбирает доступный приз из
      таблицы, он блокирует строку. Другой поток в это время будет ждать, пока
      первая транзакция не завершится».
    * Альтернатива: Можно сказать про Optimistic Locking через аннотацию
      @Version в Hibernate. Это лучше работает, если конфликты случаются редко —
      это экономит ресурсы БД.

3. Производительность: JPA vs JDBC
   Вопрос: Почему в стеке указаны и Data JPA, и JDBC? Где что применяли?
    * Ответ: «Spring Data JPA я использовал для большинства стандартных
      CRUD-операций — это ускоряет разработку.
      Но для тяжелых задач, например, массовой загрузки чеков (Batch Insert) или
      сложных аналитических отчетов по розыгрышам, я переходил на Spring JDBC.
      Это позволяло избежать оверхеда Hibernate и использовать нативные
      фишки Postgres (например, ON CONFLICT DO NOTHING)».

4. Проблема "Select Count (*)" и пагинация
   Вопрос: Как вы отображали список чеков в личном кабинете, если их миллионы?
    * Ответ: «Я использовал пагинацию. Чтобы БД не "умирала" на больших
      смещениях (OFFSET), мы старались использовать Keyset Pagination
      (фильтрация по ID последнего элемента). Также я избегал лишних count (*),
      так как на больших таблицах в Postgres это медленная операция».

Главный совет на интервью по БД:
Если вас спросят: «Как бы вы оптимизировали запрос, который стал тормозить?»,
ваш план ответа:

1. Выполню EXPLAIN ANALYZE, чтобы найти узкое место (Sequential Scan вместо
   Index Scan).
2. Проверю наличие нужных индексов.
3. Посмотрю, не "протухла" ли статистика в БД (нужен ли ANALYZE).
4. Если не помогает — попробую переписать запрос или вынести часть логики в кэш
   (Redis).

# === Антифрод ===

отличный выбор. Давайте реализуем проверку на превышение лимита транзакций
(например, не более 5 операций в минуту от одного пользователя). Это
классический сценарий для предотвращения «брутфорса» платежей или спама.
Для этого лучше всего подходит связка Spring Boot + Redis + Lua-скрипт. Redis
идеален, так как он работает в памяти и доступен всем экземплярам вашего
микросервиса.

1. Зависимости в pom.xml
   Вам понадобится стартер для работы с Redis:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>

2. Логика проверки (FraudService)
   Использование Lua-скрипта внутри Redis гарантирует атомарность: проверка и
   инкремент счетчика пройдут как одна операция, что исключает ошибки при
   одновременных запросах.

```java

@Service
public class FraudCheckService {

    private final StringRedisTemplate redisTemplate;

    // Конфигурация: 5 запросов за 60 секунд
    private static final int LIMIT = 5;
    private static final int WINDOW_SECONDS = 60;

    public FraudCheckService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public boolean isAllowed(String userId) {
        String key = "fraud:limit:" + userId;

        // Lua-скрипт: увеличивает счетчик и ставит TTL, если ключа нет
        String script =
                "local current = redis.call('INCR', KEYS[1]) " +
                        "if current == 1 then " +
                        "  redis.call('EXPIRE', KEYS[1], ARGV[1]) " +
                        "end " +
                        "return current";

        Long currentCount = redisTemplate.execute(
                new DefaultRedisScript<>(script, Long.class),
                Collections.singletonList(key),
                String.valueOf(WINDOW_SECONDS)
        );

        return currentCount != null && currentCount <= LIMIT;
    }
}
```

3. Обработка события в Kafka
   Предположим, ваш сервис заказов бросает событие в Kafka. Антифрод-сервис его
   слушает и принимает решение.

```java

@Component
public class TransactionListener {

    private final FraudCheckService fraudService;
    private final KafkaTemplate<String, String> kafkaTemplate;

    public TransactionListener(FraudCheckService fraudService, KafkaTemplate<String, String> kafkaTemplate) {
        this.fraudService = fraudService;
        this.kafkaTemplate = kafkaTemplate;
    }

    @KafkaListener(topics = "transactions-topic", groupId = "fraud-group")
    public void validateTransaction(TransactionEvent event) {
        if (!fraudService.isAllowed(event.getUserId())) {
            // Если лимит превышен — отправляем команду на блокировку
            kafkaTemplate.send("fraud-alerts-topic", new FraudAlert(event.getTxId(), "Limit exceeded"));
            System.out.println("ALERT: Подозрительная активность пользователя " + event.getUserId());
        } else {
            // Если всё ок — продолжаем процесс
            kafkaTemplate.send("validated-transactions-topic", event);
        }
    }
}
```

Почему это эффективно:

1. Скорость: Проверка в Redis занимает доли миллисекунд.
2. Скейлинг: Если у вас 10 инстансов сервиса заказов, они все будут смотреть в
   один Redis и видеть общий счетчик пользователя.
3. Надежность: Если Redis «упадет», можно настроить try-catch, чтобы по
   умолчанию пропускать транзакцию (fail-safe), но логировать инцидент.

### Антифрод и ФНС

Это отличный вопрос для интервью, на котором можно показать глубокое понимание
бизнес-процессов.
Связь здесь прямая: ФНС — это единственный первоисточник, который может
подтвердить, что чек реальный, а не нарисованный в фотошопе.
Как это работает технически:

1. Проверка существования: Мошенники часто генерируют фейковые QR-коды или
   подправляют суммы в графических редакторах. Обращение к API ФНС (или через
   посредника-фискала) позволяет проверить, зарегистрирован ли такой чек в базе
   налоговой. Если ФНС говорит «чек не найден» — это 100% фрод.
2. Защита от повторов (Double Spending): Интеграция позволяет получить
   уникальный идентификатор чека (ФП/ФД). Вы сохраняете его в базе и, если
   кто-то другой попытается зарегистрировать тот же чек, система его
   заблокирует.
3. Валидация данных: В чеке из супермаркета может быть написано «Акционный
   товар», а мошенник может это подделать. По API ФНС вы получаете сырые данные
   из чека (состав корзины, ИНН магазина, время). Вы сравниваете данные из
   распознанного изображения с данными из ФНС. Если они расходятся — это фрод.
4. Сверка магазинов: Если ваша акция проходит только в «Магните», а чек по базе
   ФНС пробит в «Пятерочке» (хотя на фото подделан логотип), API ФНС сразу
   покажет реальный ИНН владельца кассы.

запрашивали данные по его фискальным признакам через API. Это позволяло нам в
реальном времени отсекать поддельные чеки, проверять корректность магазина и
времени покупки, а также гарантировать, что один и тот же фискальный документ не
будет использован для получения приза дважды».

Всё логично? Эта связка показывает, что вы понимаете не только как написать

## Паттерны микросервисной архитектуры, используемые в проекте

# Circuit Breaker (например, библиотека Resilience4j)

Circuit Breaker (Предохранитель) — это паттерн проектирования, который
предотвращает «эффект домино» в микросервисной архитектуре. Если один сервис
начинает тормозить или падать, предохранитель обрывает связь с ним, чтобы не
«уложить» всю систему.
Работает он ровно так же, как электрический автомат у вас в щитке: если в одной
розетке короткое замыкание, вылетает пробка, чтобы не сгорела вся квартира.
Как это работает (3 состояния)

1. Closed (Закрыт): Всё хорошо. Запросы проходят через предохранитель к сервису.
   Он считает количество успешных и неудачных ответов.
2. Open (Открыт): Если процент ошибок превысил порог (например, 50% запросов
   упали), предохранитель «размыкается». Все последующие запросы к этому сервису
   даже не отправляются. Вместо ожидания тайм-аута они мгновенно получают ошибку
   или «запасной ответ» (Fallback). Это дает упавшему сервису время «прийти в
   себя».
3. Half-Open (Полуоткрыт): Через некоторое время предохранитель пропускает
   пробную партию запросов. Если они прошли успешно — он закрывается (всё
   починилось). Если нет — снова открывается.

Зачем это вам (на примере Spring Boot и 1000 RPS)
Представьте: сервис «Оплаты» стал отвечать за 10 секунд вместо 0.5с. При
нагрузке 1000 RPS все потоки вашего сервера (Tomcat) быстро забьются ожиданиями
ответов от «Оплаты». В итоге всё приложение перестанет отвечать вообще на любые
запросы.
Circuit Breaker просто отсечет запросы к «Оплате», и ваш сервис заказов
продолжит работать (пусть и без возможности оплатить).
Resilience4j — это стандарт для Spring Boot.
Раньше использовали Netflix Hystrix, но сейчас он в архиве. Resilience4j — это
современная библиотека, которая легко настраивается через аннотации.

Что она умеет кроме предохранителя:

- TimeLimiter: жестко обрубает запрос, если он длится дольше лимита.
- Retry: если запрос упал, библиотека сама повторит его (например, 3 раза с
  паузой).
- RateLimiter: ограничивает количество запросов к сервису, чтобы не «заддосить»
  его самого.

Как ответить на интервью:

      «Я использовал Resilience4j для реализации паттерна Circuit Breaker. Это
      позволило избежать каскадных сбоев: если один из 6+ микросервисов начинал 
      тормозить, предохранитель размыкал цепь, и мы отдавали пользователю 
      Fallback (запасные данные из кэша), сохраняя общую работоспособность 
      системы и свободные потоки в Tomcat».

# Отказоустойчивые микросервисные системы

Отказоустойчивая система (Fault Tolerant) — это такая система, которая
продолжает работать (пусть и частично), если один или несколько её сервисов
«упали», база данных тормозит или сеть между серверами мигает.

Отказоустойчивость строится на:

1. Изоляция сбоев (Bulkheading). Сбой одного сервиса не влияет на работу
   другого. Использование паттерна
   `Circuit Breaker (например, библиотека Resilience4j)`

2. Асинхронное взаимодействие (EDA). Сервисы общаются через брокеры. Сервис
   пишет в кафку действия пользователя, если другой сервис недоступен и не может
   забрать информацию, заберет, когда станет доступен. Система в целом осталась
   работоспособной.

3. Самовосстановление в Kubernetes (Self-healing). Liveness Probe: K8s
   определяет и поднмает упавшие приложения. Replicas: Всегда запущено минимум
   2–3 копии (пода) каждого сервиса для надежности.

4. Работа с БД и данными. `Пул соединений (HikariCP)`: при нагрузках на БД
   вместо большого количества соединений поднимает лишь несколько. Retry: Если
   запрос к БД не прошел из-за кратковременного сбоя сети, Spring JDBC может
   автоматически повторить попытку через секунду.

# Проектирование отказоустойчивости

Проектирование отказоустойчивости (Resilience) в системе с нагрузкой 1000 RPS и
6+ микросервисами — это умение создавать систему, которая «умеет болеть, но не
умирать».
На интервью отвечай по уровням, двигаясь от кода к инфраструктуре:

1. Уровень приложения (Код на Spring Boot)
   Здесь твоя задача — изолировать сбои, чтобы один упавший сервис (например,
   ФНС) не потянул за собой остальные.

* Circuit Breaker (Resilience4j): Если внешнее API тормозит, «предохранитель»
  размыкается. Вместо ожидания таймаута в 30 секунд (что забьет потоки Tomcat),
  сервис мгновенно отдает Fallback (запасной ответ, например: «Чек принят,
  проверим позже»).
* Retry Policy: Для кратковременных сбоев сети настрой Exponential Backoff.
  Первая попытка через 1с, вторая через 2с, третья через 5с. Это лечит 90%
  «мигающих» ошибок.
* Rate Limiting: Ограничь количество запросов на один user_id. Это защитит
  сервис чеков от DDOS-атак или багов на фронтенде.

2. Уровень взаимодействия (Kafka)
   Переход от синхронных вызовов (REST) к асинхронным (Events) — главный залог
   надежности.

* Буферизация: Если сервис призов упал, Kafka сохранит все проверенные чеки в
  топике. Когда сервис поднимется, он просто дочитает сообщения. Данные не
  теряются.
* Dead Letter Queue (DLQ): Если чек невозможно обработать (битый JSON), не
  блокируй очередь. Отправь его в специальный «топик для ошибок» для ручного
  разбора.

3. Уровень данных (БД и JDBC)
   База — самое узкое место. Если она «ляжет», упадет всё.

* Connection Pool (HikariCP): Настрой лимиты. Лучше заставить пользователя
  подождать 1-2 секунды в очереди пула, чем открыть 1000 соединений и уронить
  PostgreSQL.
* Transactional Outbox: Чтобы не было ситуации «в базу записали, а в Кафку не
  отправили», сначала пиши событие в таблицу outbox в той же транзакции, что и
  чек.

4. Уровень инфраструктуры (Kubernetes)
   K8s — это твой «реаниматолог».

* Health Checks: Настрой Liveness Probe (чтобы K8s перезапустил зависший под) и
  Readiness Probe (чтобы трафик не шел на сервис, который еще загружается).
* Horizontal Pod Autoscaler (HPA): При росте нагрузки до 1000 RPS K8s должен
  автоматически поднять количество подов с 2 до 10.
* Anti-Affinity: Настрой правила, чтобы копии одного сервиса жили на разных
  физических серверах. Если сгорит одна «железка», вторая копия выживет.

5. Уровень контроля (Observability)
   Ты не можешь починить то, чего не видишь.

* Alerting: Настрой алерты в Prometheus не на «загрузку CPU», а на «Error Rate >
  5%» или «Длина очереди в Kafka растет».

Золотая фраза для интервью:

      «Отказоустойчивость для меня — это Graceful Degradation (плавная 
      деградация). Если сервис ФНС недоступен, пользователь всё равно может 
      загрузить чек. Мы принимаем его, сохраняем в S3 и ставим в очередь в 
      Kafka. Система продолжает работать, а проверку мы выполним позже, когда 
      внешнее API восстановится».

## Обеспечение отказоустойчивости (Resilience)

Чтобы уверенно защитить этот пункт перед архитектором, забудь про фразу «я
просто добавил библиотеку». Архитектор спросит: «А что именно произойдет,
если...».
Твой ответ должен строиться на трех сценариях «катастроф» и твоих решениях:

1. Сценарий: «Внешнее API Налоговой (ФНС) безбожно тормозит»

    * Проблема: Потоки (threads) в твоем Spring Boot приложении закончатся, так
      как все они будут ждать ответа по 30 секунд. При 1000 RPS сервис упадет за
      секунды.
    * Твое решение (Circuit Breaker): «Я настроил Resilience4j. Если 50%
      запросов к ФНС за последние 30 секунд превышают таймаут, предохранитель
      размыкается (Open state). Новые запросы даже не пытаются идти в ФНС, а
      сразу получают Fallback — статус "В обработке". Это спасает ресурсы нашего
      CPU и памяти».

2. Сценарий: «Взрывной рост трафика (1000+ RPS)»

* Проблема: Пользователи начали грузить чеки слишком часто, база данных
  (PostgreSQL) начала «задыхаться» от количества транзакций.
* Твое решение (Rate Limiting + Buffering):
    * «Во-первых, я внедрил Rate Limiter на уровне пользователя (не более 1 чека
      в минуту).
    * Во-вторых, я использовал Kafka как буфер. Даже если сервис промо-логики не
      успевает обрабатывать 1000 чеков в секунду, они просто копятся в топике.
      Мы не теряем данные и не "кладем" базу синхронными запросами».

3. Сценарий: «Один из 6 микросервисов полностью упал»

* Проблема: Сервис призов недоступен. Пользователь загрузил чек, он проверен, но
  приз не начислить.
* Твое решение (Self-Healing + Eventual Consistency):
    * «В Kubernetes настроены Liveness/Readiness probes. Если сервис упал, K8s
      сам его перезапустит.
    * Благодаря Kafka, данные о проверенном чеке никуда не денутся. Как только
      сервис призов поднимется, он дочитает очередь и начислит всё, что
      пропустил. Это обеспечивает согласованность в конечном счете (Eventual
      Consistency)».

Коварный вопрос от архитектора: «А как вы тестировали эту отказоустойчивость?»
Твой ответ:

      «Мы проводили нагрузочное тестирование (например, через JMeter или 
      Gatling), имитируя 1000 RPS. Также мы искусственно отключали один из 
      сервисов в Dev-окружении, чтобы проверить, что остальные 5 продолжают 
      работать, а очереди в Kafka растут корректно, не переполняя диск».

Резюме для защиты:
Отказоустойчивость в моем проекте — это не одна фича, а комплекс:

1. Isolation (Circuit Breaker) — чтобы не упасть вместе с соседом.
2. Asynchrony (Kafka) — чтобы пережить пики нагрузки.
3. Redundancy (K8s) — чтобы иметь копии сервисов на случай сбоя.

## Отказоустойчивость Kafka

Вопрос про падение Kafka — это проверка на «высший пилотаж». Архитектор хочет
увидеть, понимаете ли вы предел надежности своей системы.
Вот как грамотно выстроить ответ:

1. Инфраструктурная надежность (Replication)
   Сначала скажите, что Kafka сама по себе очень живучая:

* Кластерный режим: «В продакшене мы не используем один сервер Kafka. У нас
  кластер (минимум 3 ноды)».
* Replication Factor: «Для критических топиков (чеки) мы выставляем
  replication-factor: 3. Это значит, что данные одновременно записываются на 3
  разных сервера. Даже если 2 из них сгорят, данные не потеряются».
* min.insync.replicas: «Мы настраиваем продюсер так, чтобы он получал
  подтверждение (acks=all) только когда сообщение записано минимум на две
  реплики».

2. Поведение приложения (Local Buffering)
   Что делает ваш Spring Boot, если Kafka всё-таки недоступна (например,
   проблемы с сетью в K8s)?

* Retry в коде: «Spring Kafka имеет встроенные механизмы ретраев. Приложение
  будет пытаться переотправить сообщение несколько раз».
* Fallback на БД (Transactional Outbox): Это ваш главный козырь. «Поскольку мы
  используем паттерн Outbox, мы сначала сохраняем событие в таблицу outbox в
  PostgreSQL. Если Kafka лежит, специальный сервис-релей (Relay) просто не
  сможет отправить запись и попробует снова через минуту. Чек из базы никуда не
  денется, и как только Kafka поднимется, все накопленные события улетят в
  топики».

3. Graceful Degradation (Что видит юзер)
    * «Если Kafka недоступна, наш API-сервис продолжает принимать чеки и
      сохранять их в БД и S3 (так как транзакция в базу прошла успешно). Мы
      просто не можем запустить цепочку OCR и ФНС мгновенно. Пользователь видит
      статус "Принято, обрабатывается", и для него система выглядит работающей,
      хотя внутри возникла задержка».

4. Мониторинг (Alerting)
    * «У нас настроены алерты в Prometheus на ошибки подключения к брокеру. Мы
      узнаем о проблеме с Kafka через секунды после её возникновения».

Резюме для ответа:

      «Падение всей Kafka целиком — событие крайне маловероятное при 
      кластерной настройке с репликацией. Но даже в этом случае наша система 
      сохранит целостность данных благодаря Transactional Outbox в базе данных. 
      Мы продолжим принимать чеки от пользователей, а асинхронная обработка 
      (распознавание и ФНС) "догонит" очередь сразу после восстановления 
      брокера».

Совет для интервью: Если вас спросят: «А если и база данных, и Kafka упадут
одновременно?», честно отвечайте: «В таком сценарии (Disaster) система
перестанет принимать новые чеки, но благодаря регулярным бэкапам в S3 и архивам
БД, мы сможем восстановить состояние на момент аварии».

# Масштабируемая архитектура

Масштабируемость (Scalability) — это способность системы справляться с ростом
нагрузки (те самые 1000 RPS) путем добавления ресурсов, а не переписывания кода.
В твоем проекте с чеками на Java Spring Boot и K8s стоит выделить три
направления масштабирования:

1. Горизонтальное масштабирование (Horizontal Scaling)
   Это база для Kubernetes. Вместо одного мощного сервера ты запускаешь много
   маленьких подов.

    * Stateless дизайн: Чтобы это работало, твои 6 сервисов не должны хранить
      данные о пользователе внутри себя (в оперативной памяти). Все сессии — в
      JWT, все данные — в БД/S3.
    * HPA (Horizontal Pod Autoscaler): В K8s настраивается правило: «Если
      нагрузка на CPU сервиса чеков > 70%, запусти еще 5 копий». Как только
      акция закончилась и RPS упал — K8s сам удалит лишние копии, экономя
      деньги.

2. Масштабируемость через Kafka (Consumer Groups)
   Это самый сильный аргумент для твоей системы с чеками.

    * Параллелизм: В Kafka топик делится на партиции (partitions). Если у тебя
      10 партиций, ты можешь запустить 10 экземпляров сервиса распознавания
      чеков (OCR). Каждый будет забирать свою часть данных.
    * Разрыв связности: Если пользователи загружают 2000 чеков в секунду, а
      сервис ФНС успевает обработать только 500, система не падает. Kafka просто
      накапливает очередь. Мы «масштабируем» время обработки, не теряя данные.

3. Масштабируемость базы данных
   БД — это часто «узкое место». При проектировании с нуля ты закладываешь:

    * Connection Pooling (HikariCP): Позволяет эффективно переиспользовать
      ограниченное число соединений с БД.
    * Read Replicas: Если у тебя много запросов на чтение (пользователи
      постоянно смотрят статусы своих чеков), ты направляешь SELECT запросы на
      реплику базы, а INSERT/UPDATE — на мастер-ноду.
    * Database Sharding (на перспективу): Если чеков станут миллиарды, данные
      можно делить по user_id между разными серверами БД.

4. Разделение на чтение и запись (CQRS Lite)
   В твоем проекте:

    * Запись: Быстрый прием чека и ответ «Ок».
    * Чтение: Тяжелое распознавание и бизнес-логика в фоне.
      Это позволяет масштабировать эти процессы независимо. Если завтра чеки
      станут весить в 10 раз больше, ты просто добавишь ресурсов сервису
      хранилища, не трогая сервис призов.

Как это «продать» на интервью:

      «Я спроектировал архитектуру как Stateless микросервисы, что позволило 
      нам использовать HPA в Kubernetes для автоматического масштабирования под
      пиковые 1000 RPS. Использование Kafka дало нам возможность горизонтально
      масштабировать потребителей (Consumers) через Consumer Groups, а 
      разделение на сервисы позволило точечно выделять ресурсы самым "тяжелым"
      узлам, таким как OCR-распознавание».

Критический вопрос от архитектора: «А что вы будете делать, если сама Kafka
станет узким местом?»
Ответ: «Мы просто добавим больше Brokers в кластер и увеличим количество
Partitions в топиках. Kafka линейно масштабируется почти до бесконечности».

## HPA в K8s

Настройка HPA (Horizontal Pod Autoscaler) в Kubernetes — это то, что превращает
твой Spring Boot в настоящий Highload. На интервью это подтверждает, что твои
«1000 RPS» — не просто цифра, а технически обеспеченный результат.
Вот как это работает «под капотом» и как об этом рассказать:

1. Как работает магия (Алгоритм)
   HPA — это контроллер, который раз в 15 секунд опрашивает метрики твоих подов.

    * Логика: «Если средняя загрузка CPU по всем подам сервиса чеков > 70%,
      значит пора рожать новые копии».
    * Формула: Количество копий = CurrentReplicas * (CurrentMetric /
      TargetMetric).

2. Что нужно настроить (Манифест)
   В K8s ты создаешь объект HorizontalPodAutoscaler. На интервью можно описать
   его структуру:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: checks-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checks-service     # Кого масштабируем
  minReplicas: 2             # Минимум (для отказоустойчивости)
  maxReplicas: 20            # Максимум (чтобы не разорить компанию на серверах)
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70  # Порог срабатывания
```

3. Критически важный нюанс: Resources & Limits
   HPA не будет работать, если в твоем Deployment не прописаны Requests (сколько
   ресурсов гарантированно нужно приложению).

    * Твой ответ на интервью: «Я обязательно настраивал resources.requests,
      чтобы Kubernetes понимал процент загрузки от базового потребления Spring
      Boot».

4. Продвинутый уровень: Custom Metrics (Prometheus)
   Иногда CPU — плохой показатель для Java (из-за работы Garbage Collector).

    * Твой «козырь»: «Для сервиса распознавания чеков мы можем масштабироваться
      не по CPU, а по длине очереди в Kafka. Если в топике скопилось более 5000
      необработанных чеков, HPA добавляет новые поды, чтобы быстрее разгрести
      очередь». Это настраивается через Prometheus Adapter.

5. Подготовка самого Spring Boot
   Чтобы приложение быстро масштабировалось:

    * Startup time: Оптимизируй запуск (например, не делай тяжелых проверок БД
      при старте).
    * Graceful Shutdown: Настрой в application.properties, чтобы старые поды не
      «убивались» мгновенно, а дорабатывали текущие чеки.

Как это «продать» на интервью:

      «Для обработки 1000 RPS я настроил HPA в Kubernetes. Мы определили 
      границы от 2 до 20 реплик. Основным триггером была загрузка CPU, но мы 
      также мониторили Consumer Lag в Kafka. Это позволило нам бесшовно 
      проходить пики федеральных акций: система сама "раздувалась" под нагрузкой
      и "схлопывалась" ночью, оптимизируя затраты на инфраструктуру».

Вопрос на «засыпку» от архитектора: «А что будет с вашей БД (PostgreSQL), если
HPA резко поднимет 20 подов, и каждый откроет по 50 соединений?»
Твой ответ: «Для этого мы используем PgBouncer (прокси для БД) или жестко
ограничиваем пул в HikariCP, чтобы суммарное число коннектов не превысило лимит
базы».

# Оптимизация производительности БД и профилирование высоконагруженных узлов

На интервью по теме Highload (1000 RPS) и Spring JDBC от тебя ждут не
теоретических определений, а конкретного алгоритма: «как я нахожу проблему и как
её лечу».
Вот структурированный ответ, который объединит твой опыт с чеками и техническую
экспертизу:

1. Профилирование: Поиск «узких мест» (Bottlenecks)
   Расскажи, как ты понимаешь, что БД начала «тормозить»:

    * Мониторинг (Prometheus/Grafana): «Я смотрю на метрики HikariCP (Active
      Connections, Wait Time). Если время ожидания соединения из пула растет —
      база не успевает отдавать данные».
    * Логирование медленных запросов: «В Spring Boot я настраиваю
      logging.level.org.springframework.jdbc.core=DEBUG (на тестовом стенде) или
      включаю Slow Query Log на стороне БД (например, PostgreSQL), чтобы поймать
      запросы дольше 200–500 мс».
    * Инструменты: Упомяни, что используешь EXPLAIN ANALYZE. Это «золотой
      стандарт» профилирования SQL.

2. Оптимизация на уровне БД (SQL & Схема)
   Когда запрос найден, что с ним делать?

    * Индексация (B-Tree & Составные): «Для сервиса чеков я проектировал
      составные индексы, например (user_id, status). Это позволяет БД мгновенно
      находить все 'новые' чеки конкретного пользователя, не сканируя всю
      таблицу (избегаем Seq Scan)».
    * Индексы на Foreign Keys: «В JDBC мы пишем JOIN-ы вручную. Я всегда
      проверяю наличие индексов на колонках связи, чтобы вложенные циклы (Nested
      Loops) не убивали производительность».
    * Избавление от SELECT *: «В высоконагруженных узлах я выбираю только нужные
      ID и статусы. Это экономит память в JVM и пропускную способность сети
      между Tomcat и БД».

3. Оптимизация на уровне приложения (Spring JDBC)
   Как код помогает базе выжить:

    * Пакетная обработка (Batching): «При загрузке 1000 чеков в секунду нельзя
      делать 1000 вставок. Я использую `jdbcTemplate.batchUpdate()`. Это
      группирует запросы и снижает количество сетевых задержек (Round-trips)».
    * Fetch Size: «Для тяжелых выборок (например, реестр чеков для промо-логики)
      я выставляю setFetchSize (100), чтобы не выкачивать миллион строк в память
      за раз».
    * Разделение Чтения и Записи: «Если проект растет, я предлагаю использовать
      Read Replicas. Пишем в Master, а тяжелые VIEW-проекции для пользователей
      читаем с реплики».

4. Архитектурные приемы (Highload-фишки)

    * Кэширование (Redis): «Самые часто запрашиваемые данные (например, правила
      промо-акции или профиль юзера) я выношу в Redis. Это снимает 30-40%
      нагрузки с основной БД».
    * Асинхронность (Kafka): «Мы не пишем всё сразу в основную таблицу. Сначала
      чек попадает в Kafka, и сервис-обработчик пишет его в базу порциями,
      сглаживая пики нагрузки (Load Leveling)».

Итоговый "Senior-ответ" на интервью:

      «Оптимизация для меня — это цикл: мониторинг лагов в Grafana -> поиск 
      тяжелого SQL через Slow Query Log -> анализ плана через EXPLAIN -> и 
      правка индекса или перенос логики в Kafka/Redis. Например, в проекте с 
      чеками мы оптимизировали узел проверки промо-товаров, заменив вложенные 
      подзапросы на JOIN и добавив составной индекс, что позволило снизить 
      Response Time в 5 раз при нагрузке в 1000 RPS».

## EXPLAIN ANALYZE

На интервью по Highload умение «читать» план запроса (EXPLAIN) отделяет
разработчика, просто пишущего код, от инженера, который понимает, как
работает база данных.
Вот краткий гид, как уверенно ответить на этот вопрос:

1. Что такое EXPLAIN ANALYZE?
   Скажи: «Я использую не просто EXPLAIN (который дает только прогноз), а
   EXPLAIN ANALYZE. Он реально выполняет запрос и показывает фактическое время и
   количество строк на каждом этапе».
2. На что смотреть в первую очередь (Красные флаги)
   Когда перед тобой дерево выполнения запроса, ищи эти «плохие» слова:

    * Seq Scan (Sequential Scan):
        * Что это: База читает всю таблицу целиком с диска.
        * Вердикт: Для 1000 RPS и таблицы в миллионы чеков — это смерть.
        * Лечение: Добавить индекс на колонку в WHERE или JOIN.
    * Nested Loop (Вложенный цикл):
        * Что это: Для каждой строки из первой таблицы база ищет совпадение во
          второй.
        * Вердикт: Ок для маленьких таблиц, но если обе таблицы большие — это
          тормоза.
        * Лечение: Проверить индексы на внешних ключах (Foreign Keys), чтобы
          база переключилась на Hash Join.
    * Rows Removed by Filter:
        * Что это: База прочитала много строк, но отбросила их, так как они не
          подошли под WHERE.
        * Лечение: Индекс неэффективен. Нужно создать составной индекс, который
          включает это поле.

3. На что смотреть во вторую очередь (Хорошие знаки)

    * Index Scan: База использует индекс, чтобы найти нужные строки. Это хорошо.
    * Index Only Scan: «Святой Грааль» оптимизации. Базе даже не нужно лезть в
      саму таблицу, все данные она нашла прямо в индексе.
    * Bitmap Index Scan: Средний вариант — база нашла много совпадений в индексе
      и теперь идет за ними в таблицу пачкой.

4. Ключевые метрики в плане

    * Cost: Условная единица «тяжести» запроса (зависит от CPU и I/O). Сравнивай
      Cost «до» добавления индекса и «после».
    * Actual Time: Реальное время в миллисекундах.
    * Loops: Сколько раз выполнялся этот узел дерева.

5. Твой ответ на интервью (Пример кейса)

   «Я анализировал запрос выбора чеков по статусу NEW. EXPLAIN ANALYZE
   показал Seq Scan, так как индекса на поле status не было. После
   добавления индекса план сменился на Bitmap Index Scan, а время выполнения
   упало с 800 мс до 2 мс. Однако при 1000 RPS этого было мало, и я заметил
   External Merge Disk (сортировка на диске). Я увеличил параметр work_mem
   в настройках БД, чтобы сортировка проходила в оперативной памяти, что
   убрало задержки».

Шпаргалка для "Senior-ответа":
Если архитектор спросит: «А почему индекс может не использоваться, хотя он
есть?», отвечай:

1. Низкая селективность: Если в таблице 90% чеков имеют статус PROCESSED, база
   решит, что проще прочитать всё подряд (Seq Scan), чем прыгать по индексу.
2. Функции в WHERE: Если написать WHERE UPPER (status) = 'NEW', обычный индекс
   на status не сработает. Нужен функциональный индекс.

## Метрики БД в Grafana

Для высоконагруженного проекта на Spring Boot и PostgreSQL путь метрик из базы в
Grafana обычно выглядит как конвейер из трех звеньев. Сама база данных не умеет
«стучаться» в Графану, поэтому нужен посредник.

Вот классическая схема: PostgreSQL → Postgres Exporter → Prometheus → Grafana.

1. Источник: PostgreSQL
   База данных хранит системную статистику в специальных таблицах
   (представлениях), например pg_stat_activity (активные подключения) или
   pg_stat_database (количество транзакций, промахи мимо кэша).
2. Сборщик: Postgres Exporter (Sidecar или отдельный сервис)
   Поскольку Prometheus не умеет напрямую делать SQL-запросы к базе, рядом с БД
   (часто в том же Kubernetes-кластере) запускается маленькая утилита — Postgres
   Exporter.

    * Что он делает: Он раз в несколько секунд подключается к БД, выполняет
      SQL-запросы к системным таблицам и переводит их в формат, понятный
      Prometheus.
    * Эндпоинт: Он открывает порт (обычно 9187), где по адресу /metrics виден
      длинный список текстовых данных.

3. Хранилище: Prometheus
   Prometheus заходит на этот эндпоинт экспортера, забирает («скрейпит») цифры и
   сохраняет их у себя как временной ряд (Time Series).

    * Пример метрики: pg_stat_database_xact_commit{datname="orders_db"} —
      количество успешных транзакций.

4. Визуализация: Grafana
   В Grafana ты добавляешь Prometheus как Data Source (источник данных).

    * Ты создаешь дашборд и пишешь запрос на языке PromQL (например, чтобы
      посчитать процент загрузки пула соединений).
    * Grafana рисует график на основе этих данных.

Альтернативный путь: Через Spring Boot (Micrometer)

Если ты используешь HikariCP (пул соединений внутри Java), то метрики самого
пула попадают в Grafana иначе:

1. Spring Boot Actuator + Micrometer собирают данные о том, сколько соединений
   сейчас занято приложением.
2. Эти данные доступны по адресу /actuator/prometheus твоего приложения.
3. Prometheus забирает их напрямую из Java-приложения, а Grafana рисует график
   «Загрузка пула соединений со стороны бэкенда».

Что ответить на интервью:

      «Метрики БД попадают в Grafana через Postgres Exporter, который 
      опрашивает системные таблицы базы и отдает данные в формате Prometheus. 
      Сам Prometheus агрегирует эти метрики, а в Grafana мы строим дашборды. 
      Также мы мониторим состояние пула соединений напрямую через Spring 
      Actuator, что позволяет видеть картину и со стороны базы (нагрузка на 
      диск, транзакции), и со стороны приложения (свободные коннекты в HikariCP)».

## Micrometer

Micrometer — это «SLF4J, но для метрик». Если SLF4J — это стандартный фасад для
логов в Java, то Micrometer — это единый интерфейс для сбора числовых
показателей (метрик) вашего приложения.
В контексте вашего стека (Spring Boot, Highload 1000 RPS, Prometheus) он играет
роль «переводчика».

Как это работает в Spring Boot

1. Инструментация: Вы добавляете зависимость micrometer-registry-prometheus.
2. Сбор данных: Micrometer внутри кода Spring Boot автоматически начинает
   «замерять» важные вещи:
    * Сколько времени выполняется каждый HTTP-запрос.
    * Сколько потоков в Tomcat сейчас занято.
    * Состояние пула соединений HikariCP (сколько коннектов свободно).
    * Параметры JVM (размер Heap, частота сборки мусора).
3. Экспорт: Micrometer переводит эти данные в формат, который понимает
   Prometheus, и отдает их через эндпоинт /actuator/prometheus.

Основные типы метрик, которые вы используете:

* Counter (Счетчик): Только растет. Например, «общее количество загруженных
  чеков».
* Gauge (Измеритель): Показывает текущее значение (может расти и падать).
  Например, «количество активных соединений с БД прямо сейчас».
* Timer (Таймер): Считает количество событий и их длительность. Например, «время
  ответа API Налоговой».

Почему это важно для вашего интервью:

Вы можете сказать:

      «Для мониторинга высоконагруженных узлов мы использовали Micrometer, 
      встроенный в Spring Boot. Он автоматически собирал метрики 
      производительности HikariCP и интерфейсов Kafka, а также позволял нам 
      создавать кастомные метрики (например, количество успешно распознанных 
      QR-кодов). Все эти данные через Prometheus попадали в Grafana, где мы 
      видели реальную нагрузку в 1000 RPS».

# Оптимизация SQL-запросов

Оптимизация SQL — это процесс перехода от «тяжелого» полного сканирования таблиц
к точечной выборке данных. В контексте Spring JDBC и Highload (1000 RPS),
оптимизация обычно идет по этим 5 уровням:

1. Анализ плана запроса (EXPLAIN)
   Это первое, что нужно сделать. Вы берете SQL из кода и запускаете его в
   консоли БД с командой EXPLAIN ANALYZE.
    * Что искать: Seq Scan (полный обход таблицы). Это враг номер один.
    * Цель: Добиться Index Scan или Index Only Scan (когда данные берутся прямо
      из индекса без захода в таблицу).
2. Индексация (Правильные ключи)
   Индексы ускоряют чтение, но замедляют запись (что важно при 1000 RPS чеков).
    * B-Tree индексы: Стандарт для колонок, по которым идет поиск (user_id,
      check_id).
    * Составные индексы: Если вы ищете по двум полям сразу (WHERE user_id = ?
      AND status = ?), один индекс на оба поля будет работать быстрее, чем два
      отдельных.
    * Индексы на Foreign Keys: В Spring JDBC мы часто делаем JOIN. Убедитесь,
      что все колонки связей индексированы.
3. Оптимизация структуры запроса

    * Избегайте SELECT *: В JDBC это заставляет базу тратить ресурсы на вычитку
      всех колонок и передачу их по сети. Выбирайте только то, что мапите в
      POJO.
    * Замена подзапросов на JOIN: Современные базы (PostgreSQL) хорошо
      оптимизируют JOIN, в то время как WHERE id IN (SELECT...) может работать
      крайне медленно на больших данных.
    * Пагинация (LIMIT/OFFSET): Никогда не выкачивайте все 1000 чеков
      пользователя за раз. Используйте LIMIT и OFFSET (хотя на миллионах строк
      лучше использовать keyset pagination — поиск по последнему ID).

4. Оптимизация VIEW (Проекций)
   Поскольку вы упоминали VIEW:

    * Predicate Pushdown: Проверьте, пробрасывает ли БД ваш WHERE внутрь вью.
      Если нет — база сначала вычисляет всё вью, а потом фильтрует результат.
      Это убивает производительность.
    * Materialized Views: Если данные во вью нужны для отчетов и не должны быть
      актуальны до секунды, используйте материализованные представления (они
      хранят результат на диске как таблицу).

5. Оптимизация на уровне Spring JDBC

    * Batch Updates: Для массовой вставки чеков или обновления статусов
      используйте jdbcTemplate.batchUpdate (). Вместо 100 запросов в базу уйдет
      один пакет данных.
    * Fetch Size: Для больших выборок установите jdbcTemplate.setFetchSize
      (100), чтобы драйвер тянул данные порциями, не перегружая память Tomcat.

Как это преподнести на интервью (Кейс):

      «Когда мы заметили, что сервис промо-акций начал тормозить, я 
      проанализировал логи медленных запросов и выполнил EXPLAIN ANALYZE. 
      Выяснилось, что при 1000 RPS база делала Sequential Scan по таблице чеков.
      Я добавил составной индекс на user_id и status, а также переписал тяжелый
      подзапрос на JOIN. Это снизило нагрузку на CPU базы на 40%, а время ответа
      сократилось с 2 секунд до 50 мс».

## Оптимизация SQL-запросов через Spring JDBC

1. Используйте Batch Updates (Пакетная вставка). Если вам нужно сохранить 100+
   записей, не делайте 100 вызовов update (). Это «убьет» сеть и БД.

- Как: Используйте jdbcTemplate.batchUpdate (). Он отправит один массив данных
  одним пакетом.
- Эффект: Ускорение записи в 10–50 раз.

2. Ограничение выборки (Fetch Size). По умолчанию JDBC может пытаться вытянуть
   все 100 000 строк в память Java, что приведет к OutOfMemory.

- Как: Настройте jdbcTemplate.setFetchSize (100). Это скажет драйверу тянуть
  данные порциями.
- Эффект: Стабильное потребление памяти приложением под нагрузкой.

3. NamedParameterJdbcTemplate вместо обычного. В обычном JdbcTemplate параметры
   ставятся через ?. Если их 20, легко ошибиться порядком.

- Как: Используйте именованные параметры: WHERE id = :userId.
- Эффект: Код становится читаемым, его легче отлаживать во время ваших
  демо-встреч с заказчиком.

4. Правильный маппинг (RowMapper vs ResultSetExtractor).

- RowMapper: Идеален для списков объектов (одна строка БД = один объект).
- ResultSetExtractor: Нужен, если одна строка БД превращается в сложную
  структуру или если вы делаете JOIN (один заказ + 5 товаров). Зачем: Это
  позволяет избежать повторных запросов к БД в цикле (проблема N+1), которые
  часто возникают при проектировании «в лоб».

5. Индексы и EXPLAIN (Уровень БД).
   Spring JDBC не спасет, если в базе нет индексов. Как: Возьмите тяжелый запрос
   из кода и выполните его в консоли БД с префиксом EXPLAIN ANALYZE. На что
   смотреть: Если видите Seq Scan на большой таблице — нужен индекс. В
   Spring-приложении убедитесь, что вы ищете по тем колонкам, которые
   индексированы (Foreign Keys, артикулы, даты).
6. Внешний пул соединений (HikariCP). В старых проектах часто забывают про пул.
   Если каждое обращение к БД открывает новое физическое соединение — это
   провал.

- Как: Подключите HikariCP. Он держит «горячие» соединения готовыми к работе.
- Эффект: Мгновенный отклик приложения.

Маленький лайфхак для вашего спринта:
Для мониторинга запросов включается логиирование SQL в logback.xml или через
настройки DataSource.

# === Spring JDBC против Hibernate ===

В высоконагруженных системах (1000 RPS) и коротких спринтах (2-3 недели) выбор
Spring JDBC (JdbcTemplate) часто перевешивает магию Hibernate. Вот 5 главных
причин, почему это выигрышная стратегия:

1. Полный контроль над SQL (No Magic)
   Hibernate генерирует SQL сам. Иногда он делает это неоптимально (например,
   вытягивает все колонки SELECT * или делает лишние JOIN).

    * Выигрыш JDBC: Ты пишешь SQL руками. Если тебе нужно обновить только одно
      поле status у 1000 чеков, ты пишешь ровно один UPDATE. В Hibernate тебе
      пришлось бы сначала загрузить 1000 объектов в память (Managed State),
      изменить их и ждать, пока сессия сделает 1000 апдейтов.

2. Производительность и Память
   Hibernate — это тяжелый фреймворк с кэшированием (1-й и 2-й уровни), грязной
   проверкой объектов (Dirty Checking) и Reflection.

    * Выигрыш JDBC: Он максимально близок к «железу» (JDBC драйверу). У него нет
      накладных расходов на создание тысяч Proxy-объектов. Для микросервиса в
      Kubernetes это означает меньшее потребление RAM (Heap) и более быстрый
      запуск.

3. Решение проблемы N+1 «из коробки»
   В Hibernate легко забыть FetchType.LAZY или запутаться в связях, получив
   сотни лишних запросов к БД в цикле.

    * Выигрыш JDBC: Ты сам проектируешь JOIN. Если тебе нужны чеки вместе с
      товарами, ты пишешь один запрос, используешь ResultSetExtractor и
      собираешь объект за один поход в базу. Это предсказуемо.

4. Пакетная вставка (Batch Updates)
   Для системы с чеками (1000 RPS) это критично.

    * Выигрыш JDBC: jdbcTemplate.batchUpdate () — это прямой и максимально
      быстрый способ отправить пачку данных в БД одним сетевым пакетом. В
      Hibernate настройка батчинга требует магии с конфигами и часто работает
      неочевидно.

5. Предсказуемость в Agile (2-3 недели)
   Когда срок разработки — всего пара недель, отладка «странного поведения
   Hibernate» (почему не сохранилось? откуда этот запрос?) съедает время.

    * Выигрыш JDBC: Ошибка в SQL видна сразу. Маппинг через RowMapper прозрачен.
      Твой коллега на Code Review мгновенно поймет, что делает код, не гадая,
      какие аннотации накручены на Entity.

Как это «продать» на интервью:

      «Для высоконагруженного узла загрузки чеков (1000 RPS) мы выбрали Spring 
      JDBC, так как он дает нам предсказуемую производительность и полный 
      контроль над планом запроса (EXPLAIN). Это позволило избежать проблем с 
      кэшированием Hibernate и минимизировать нагрузку на память в Kubernetes. 
      Мы использовали JdbcTemplate для сложных выборок и Batch Updates для 
      быстрой записи, что критично при таких объемах данных».

Этот пункт — отличная возможность показать, что вы не просто «кодили», а думали

Вот как раскрыть этот тезис по четырем направлениям:

1. Как именно проектировали «с нуля»? (Архитектура)
   Расскажите, как вы делили монолитную идею на сервисы.

    * Декомпозиция: «Я разделил систему на независимые домены: Auth
      (безопасность), Receipt Loader (прием данных), OCR (тяжелая математика),
      Promo Logic (бизнес-правила). Это позволило нам масштабировать каждый
      сервис отдельно. Например, в пики акций мы поднимали 10 копий сервиса
      чеков, но оставляли всего 2 копии сервиса аналитики».
    * Связи: «Чтобы 1000 RPS не "положили" базу, я внедрил асинхронное
      взаимодействие через Kafka. Пользователь получал ответ "Чек принят"
      мгновенно, а вся тяжелая работа шла в фоне».

2. Что такое 1000 RPS в вашем контексте? (Нагрузка)
   Цифра 1000 запросов в секунду звучит солидно. Объясните, что за ней стоит.

    * Пиковые нагрузки: «В обычное время нагрузка была небольшой, но в моменты
      старта розыгрышей или выхода ТВ-рекламы трафик взлетал лавинообразно. 1000
      RPS — это 60 000 запросов в минуту. Каждый запрос — это запись в лог,
      проверка токена в Redis и отправка события в Kafka».
    * Борьба с узкими местами: «При такой нагрузке стандартный Tomcat с пулом в
      200 потоков мог начать тормозить. Здесь нам помогла Java 21 и Virtual
      Threads, которые позволили обрабатывать тысячи соединений одновременно без
      раздувания потребления памяти».

3. Как обеспечили масштабируемость? (Инструменты)

    * Kubernetes (HPA): «Мы использовали Horizontal Pod Autoscaler. Система сама
      докидывала новые инстансы сервисов, когда видела рост нагрузки на CPU».
    * База данных: «Чтобы Postgres не стал бутылочным горлышком, я оптимизировал
      индексы и внедрил Connection Pooling (HikariCP). Также мы использовали
      Redis для кэширования горячих данных (например, условий текущей акции),
      чтобы не дергать основную БД на каждый запрос».

4. Как вы поняли, что система «выдержала»? (Результат)

    * Мониторинг: «Я настроил дашборды в Grafana, где мы следили за Latency
      (временем ответа). Даже при 1000 RPS среднее время ответа (p95) не
      превышало 200 мс».

Пример «золотого ответа» на интервью:

          «Когда я проектировал эту систему, главной задачей было не дать ей упасть во время федеральных акций. Я выбрал микросервисный подход, чтобы изолировать критические узлы. Самое нагруженное место — прием чеков — я сделал максимально легким, вынеся всю логику в Kafka.
          Благодаря Java 21 и Stateless-архитектуре, мы могли горизонтально масштабироваться в Kubernetes до нужного количества RPS. В итоге при нагрузке в 1000 RPS база данных и API Gateway работали стабильно, а пользователи получали отклик без задержек».

Совет: Если спросят: «А почему именно 6 сервисов?», отвечай: «Это позволило нам
соблюсти баланс — сервисы достаточно мелкие, чтобы быть автономными, но их не
так много, чтобы запутаться в их поддержке и сетевых вызовах».

## выбор между мискросервисами и монолитом

Выбор между монолитом и микросервисами — это всегда поиск баланса. Для проекта с
федеральным охватом (3000 юзеров в сутки, 1000 RPS в пике) микросервисы — это
стратегическое решение.
Вот как грамотно обосновать этот выбор на интервью:

1. Изоляция нагрузки (Главный аргумент)
   «В нашем проекте были очень разные по ресурсам задачи. OCR (распознавание
   чеков) — это тяжелая математика, которая съедает CPU. Promo Logic — это
   легкая бизнес-логика.

    * В монолите: Если OCR начнет потреблять весь процессор, «ляжет» всё
      приложение, включая авторизацию и выдачу призов.
    * В микросервисах: Я выделил OCR в отдельный сервис. В пики акций мы
      масштабировали его до 10-15 подов в Kubernetes, не раздувая при этом
      легкие сервисы. Это позволило эффективно использовать ресурсы сервера».

2. Независимое масштабирование и Deployment
   «Нам важна была скорость внесения изменений (Time-to-Market).

    * Если маркетологи просили изменить логику розыгрыша, я обновлял только один
      сервис Promo Logic.
    * При монолите нам пришлось бы пересобирать и тестировать всё огромное
      приложение, что увеличило бы риск багов и время деплоя. В микросервисах
      риск затронуть чужой код минимален».

3. Отказоустойчивость (Fault Tolerance)
   «В федеральных акциях недопустим полный простой системы.

    * Если в монолите упадет модуль интеграции с ФНС (например, из-за таймаута),
      может зависнуть всё приложение.
    * В нашей архитектуре, даже если сервис ФНС или OCR временно недоступен,
      пользователь все равно может зайти в личный кабинет, посмотреть старые
      призы или загрузить новый чек (который просто подождет в Kafka). Система
      остается частично работоспособной».

4. Разнородный стек технологий
   «Микросервисы дали нам гибкость. Например, сервис Aggregator для аналитики
   требовал много оперативной памяти и специфических библиотек, в то время как
   Auth должен был быть максимально легким. Мы смогли настроить разные параметры
   JVM и ресурсы в K8s под каждый конкретный тип задач».

Как ответить кратко (Твой сценарий):

          «Я выбрал микросервисную архитектуру вместо монолита из-за неравномерной нагрузки на разные части системы. Нам нужно было изолировать тяжелый процесс распознавания чеков от легкой бизнес-логики, чтобы иметь возможность горизонтально масштабировать только нагруженные узлы. Кроме того, это обеспечило высокую доступность: выход из строя одного модуля (например, интеграции с внешним API) не приводил к падению всей платформы, и пользователи сохраняли доступ к своим данным».

Каверзный вопрос: «А в чем были минусы?»
Твой ответ:
«Конечно, это усложнило инфраструктуру. Пришлось внедрять Service Discovery, API
Gateway и настраивать сквозное логирование по Trace ID, чтобы понимать, что
происходит в системе. Но при нагрузке в 1000 RPS эти затраты полностью себя
оправдали».

## `Gateway и Discovery`

Отличный выбор! Это классический, надежный стек для Spring Boot микросервисов.
На интервью по этой связке тебя будут проверять на понимание того, как запросы
«бегают» внутри кластера.
Вот как грамотно разложить по полочкам роль этих инструментов в твоем проекте:

1. Eureka Discovery (Зачем она была нужна?)
   В Kubernetes поды постоянно пересоздаются, и их IP-адреса меняются. Чтобы
   сервисы не искали друг друга по жестким ссылкам, нужна «телефонная книга».

    * Твой ответ: «Я использовал Eureka как Service Discovery. Каждый
      микросервис при старте регистрировался в ней. Когда, например, Aggregator
      хотел получить данные от Promo Logic, он не стучался по IP, а запрашивал у
      Eureka актуальный список доступных инстансов по имени сервиса. Это
      обеспечило нам динамическую масштабируемость и отказоустойчивость: если
      один под падал, Eureka вычеркивала его из списка, и трафик на него больше
      не шел».

2. Spring Cloud Gateway (Твоя «входная дверь»)
   Это единая точка входа для фронтенда (React).

    * Твой ответ: «Я настроил Spring Cloud Gateway как единый шлюз. Он решал три
      критические задачи:
        1. Маршрутизация (Routing): Он понимал, что запросы /api/auth/** нужно
           слать в один сервис, а /api/receipts/** — в другой.
        2. Централизованная безопасность: Именно на уровне Gateway мы проверяли
           JWT-токены пользователей. Если токен невалиден, запрос даже не
           доходил до внутренних микросервисов, что экономило ресурсы.
        3. Cross-Origin (CORS): Я настроил правила CORS в одном месте (на
           шлюзе), чтобы фронтенд мог безопасно общаться с нашими API».

3. Как они работали вместе (Workflow запроса)
   Когда пользователь загружал чек (1000 RPS):

    1. Запрос прилетал на Gateway.
    2. Gateway спрашивал у Eureka: «Где сейчас живые инстансы Receipt-Loader?».
    3. Eureka отдавала список IP.
    4. Gateway (используя встроенный балансировщик LoadBalancer) выбирал один из
       IP и перенаправлял запрос.

Твой «козырь» на интервью:
Если спросят: «А зачем Gateway, если в Kubernetes есть свой Service и Ingress?»,
отвечай:

        «Я использовал Spring Cloud Gateway, потому что он позволяет реализовывать сложную логику на языке Java (через Gateway Filters). Например, мы могли на лету модифицировать заголовки, логировать время ответа каждого сервиса или внедрять кастомный Rate Limiting (ограничение частоты запросов) для защиты от ботов. Это гораздо гибче, чем стандартные настройки Ingress».

Каверзный вопрос: «А что будет, если Eureka упадет?»
Твой ответ: «У Spring Cloud есть механизм кэширования на стороне клиента. Каждый
сервис хранит у себя локальную копию таблицы маршрутов из Eureka. Если она
временно недоступна, сервисы всё равно смогут найти друг друга по последним
известным адресам».

`а в k8s есть DNS, можно ли его использовать вместо eureka?`

Да, это отличный и очень глубокий вопрос для Middle+. Короткий ответ: да, в
Kubernetes можно и нужно использовать встроенный DNS, и современные стандарты
разработки часто отдают предпочтение именно ему, а не Eureka.
Вот как это работает и как грамотно обосновать твой выбор на интервью:

1. Как работает DNS в Kubernetes (Native Service Discovery)
   В K8s каждому Service назначается постоянное DNS-имя (например,
   receipt-service).

    * Когда один под хочет вызвать другой, он просто стучится по
      адресу http://receipt-service.
    * Встроенный CoreDNS сам сопоставляет это имя с IP-адресами живых подов.
    * Плюс: Вам не нужно тянуть в проект лишнюю библиотеку (Eureka) и тратить
      память на отдельный сервис-регистратор.

2. Почему же тогда в твоем проекте была Eureka? (Твоё оправдание)
   Если тебя спросят: «Зачем вы тянули Эврику в Кубернетис?», у тебя есть 3
   веских аргумента:

    * Гибкость настроек (Client-Side Load Balancing): «Используя Eureka в связке
      с Spring Cloud LoadBalancer, мы получили полный контроль над балансировкой
      на стороне Java-кода. Мы могли реализовывать сложные алгоритмы (например,
      Weighted Response Time), которые стандартный K8s DNS (работающий на уровне
      IP/L4) делает менее гибко».
    * Локальная разработка: «Нам было важно, чтобы разработчики могли запускать
      всю систему из микросервисов локально на своих машинах (без Minikube/K8s).
      С Eureka это делается одной аннотацией, и система работает одинаково и в
      Docker, и на Windows/Mac».
    * Legacy и миграция: «Проект начинался как распределенная система в обычном
      облаке (или на VM), и при миграции в Kubernetes мы решили оставить
      проверенный стек Spring Cloud, чтобы не переписывать логику взаимодействия
      сервисов и конфигурации Gateway».

3. Сравнение для интервью: DNS vs Eureka

| Критерий           | K8s DNS (Service)            | Spring Cloud Eureka           |
|--------------------|------------------------------|-------------------------------|
| Сложность          | Низкая (из коробки)          | Выше (нужен отдельный сервис) |
| Балансировка       | Server-side (Round Robin)    | Client-side (Любые алгоритмы) |
| Привязка к вендору | Только Kubernetes            | Любая среда (VM, Bare Metal)  |
| Health Checks      | На уровне Liveness/Readiness | Свой механизм регистрации     |

Как ответить на интервью (Твой сценарий):

          «Я знаю, что в Kubernetes есть встроенный механизм Service Discovery через DNS, и в новых проектах "Cloud Native" часто выбирают его.
          Однако в нашем проекте мы использовали Eureka, так как это давало нам независимость от инфраструктуры (возможность запуска вне K8s для тестов) и позволяло использовать Client-side Load Balancing из экосистемы Spring Cloud. Это давало более полный контроль над трафиком внутри Gateway и возможность быстро менять стратегии балансировки без перенастройки манифестов Kubernetes».

Каверзный вопрос: «А если бы вы сейчас начинали проект с нуля под K8s, что бы
выбрали?»
Твой честный ответ: «Я бы рассмотрел отказ от Eureka в пользу нативного K8s
Service + Ingress/Istio. Это упрощает архитектуру и уменьшает потребление
ресурсов (не нужно держать лишний микросервис-регистратор)».

`ingress или istio`:

Для стандартного проекта уровня Middle (как твой с чеками и 1000 RPS) обычного
Ingress более чем достаточно. Istio — это «тяжелая артиллерия», которую
внедряют, когда количество микросервисов переваливает за 20–50 штук.
Вот как объяснить разницу и обосновать свой выбор на интервью:

1. Ingress (Твой вариант)
   Это стандартный способ пустить трафик в кластер.

    * Как работает: Ты описываешь правила в YAML-файле (какой домен на какой
      Service отправить). Контроллер (например, Nginx Ingress) слушает эти
      правила и перенаправляет HTTP-запросы.
    * Плюсы: Легкий, быстрый, есть в любом Kubernetes из коробки.
    * Твой кейс: «Для нашего проекта (6+ сервисов) ресурсов Ingress хватало
      полностью. Он отлично справлялся с терминацией SSL, балансировкой и
      маршрутизацией по путям (/api/auth, /api/receipts)».

2. Istio (Service Mesh)
   Это целая надстройка над Kubernetes, которая управляет трафиком внутри
   кластера (между сервисами).

    * Что дает: Шифрование трафика между подами (mTLS), очень умный алертинг,
      визуализацию связей (Kiali) и продвинутые стратегии деплоя (Canary,
      Blue-Green).
    * Минусы: Огромное потребление ресурсов. Istio подселяет в каждый твой под
      «шпиона» (Sidecar-контейнер Envoy), который ест память и CPU. Настройка и
      поддержка Istio — это работа для отдельного DevOps-инженера.

Как ответить на интервью (Твой сценарий):

          «Для маршрутизации внешнего трафика мы использовали стандартный Ingress-контроллер. На нашем масштабе (6+ микросервисов) его возможностей было достаточно для балансировки и SSL-терминации.
          Мы рассматривали Istio, но решили не усложнять инфраструктуру. Istio дает мощные инструменты (Service Mesh, mTLS, Canary-деплой), но потребляет много ресурсов и требует сложной настройки. Для проекта с 1000 RPS и нашей архитектурой на Spring Cloud Gateway, обычный Ingress оказался более эффективным и экономным решением».

Каверзный вопрос: «А зачем вам Spring Cloud Gateway, если есть Ingress?»
Твой сильный ответ:
«Я разделил зоны ответственности:

1. Ingress отвечал за вход в кластер из интернета (L7 балансировка).
2. Spring Cloud Gateway выполнял роль Backend for Frontend (BFF): он занимался
   проверкой JWT-токенов, модификацией заголовков и логикой, специфичной для
   Java-приложения. Это позволило нам не раздувать конфиги Nginx сложной
   бизнес-логикой и оставить её на стороне разработки».

Резюме:

    * Ingress — это просто «дверь» в дом.
    * Istio — это система умного дома с датчиками в каждой комнате.

### `Api Gateway + Nginx`:

Давай распутаем этот узел. В Kubernetes эти два инструмента обычно работают
вместе, как внешняя дверь в подъезд и дверь в твою квартиру.
Как устроена цепочка запроса:

1. Интернет →
2. Nginx Ingress Controller (внешний шлюз кластера) →
3. Spring Cloud Gateway (твой микросервис-приложение) →
4. Внутренние микросервисы (Auth, Чеки и т.д.).

Зачем нужны оба?

1. Nginx Ingress (Внешний штурвал):
   Это стандартный компонент самого Kubernetes. Его задача — принять трафик из
   интернета, проверить SSL-сертификат (https) и понять, в какой «дом»
   (микросервис) отправить запрос.

    * Проблема: Настраивается он через YAML-файлы. Если ты захочешь сделать там
      сложную проверку (например, сходить в Redis, проверить хитрый заголовок
      или трансформировать JSON), тебе придется писать либо очень длинные и
      страшные конфиги Nginx, либо скрипты на Lua. Это неудобно разработчику.

2. Spring Cloud Gateway (Твой умный фильтр):
   Это обычное Java-приложение.

    * Почему это круто: Ты пишешь логику на Java.
    * Пример: Тебе нужно провалидировать JWT-токен пользователя. В Spring Cloud
      Gateway ты просто пишешь GatewayFilter, подключаешь библиотеку для работы
      с JWT и всё. Если бы ты делал это в Nginx, тебе пришлось бы настраивать
      сложные модули авторизации на уровне всей инфраструктуры.

Что значит «не раздувать конфиги Nginx»?
Это значит, что ты оставил Nginx только для простой работы: «прими запрос и
перекинь его на мой Java-шлюз». А всю умную бизнес-логику (авторизация,
логирование запросов, модификация заголовков, Rate Limiting по пользователям) ты
реализовал в Spring Cloud Gateway.
Как ответить на интервью:

          «В нашем проекте Nginx Ingress выполнял роль внешнего балансировщика трафика на уровне кластера (SSL-терминация и базовая маршрутизация).
          Однако всю логику уровня приложения мы вынесли в Spring Cloud Gateway. Поскольку это Java-сервис, нам было гораздо проще реализовывать в нем проверку JWT-токенов, интеграцию с Eureka и кастомные фильтры. Это позволило разделить инфраструктурные настройки (Nginx) и логику разработки (Spring Cloud Gateway), сделав систему более гибкой для изменений».

Итог: Тебе не нужен именно Nginx для работы Spring Cloud Gateway, но в 99%
случаев в Kubernetes перед твоим Java-шлюзом будет стоять Ingress (чаще всего на
базе Nginx).
Теперь понятно, почему они работают в паре, а не заменяют друг друга?
Напиши, если хочешь разобрать,
`как именно Spring Cloud Gateway понимает, куда слать запрос, если он знает только названия сервисов из Eureka!`

Не совсем так. Если ты используешь Spring Cloud Gateway + Eureka, то Gateway
узнает адреса сервисов не из CoreDNS, а напрямую из библиотеки в своем коде
(Client-side Load Balancing).
Давай разберем, как это работает «под капотом», чтобы ты блеснул на интервью:

1. Почему не CoreDNS?
   CoreDNS — это инструмент самого Kubernetes. Он работает на уровне IP-адресов
   сервисов. Если ты стучишься по имени сервиса, DNS просто отдает тебе IP-адрес
   балансировщика (Service IP).
2. Как работает связка Gateway + Eureka?
   Когда запрос приходит в Spring Cloud Gateway, происходит магия Client-side
   Load Balancing:

    1. Регистрация: Каждый микросервис при старте сообщает Eureka: «Я — сервис
       RECEIPT-SERVICE, мой IP такой-то».
    2. Кэширование: Твой Gateway раз в 30 секунд скачивает из Eureka всю
       «телефонную книгу» и хранит её у себя в памяти.
    3. Маршрутизация: В конфиге Gateway ты пишешь: lb://RECEIPT-SERVICE.
    4. Выбор цели: Когда прилетает запрос, библиотека Spring Cloud LoadBalancer
       (внутри Gateway) сама заглядывает в свой кэш, видит там 3 живых IP-адреса
       этого сервиса и сама выбирает один из них (например, по Round Robin).

3. Зачем так сложно, если есть DNS в K8s?
   Главный аргумент для интервьюера:

«Использование Eureka внутри Spring Cloud Gateway дает нам умную балансировку на
стороне клиента. Мы не зависим от задержек обновления DNS в Kubernetes и можем
реализовывать свои стратегии выбора инстанса. Плюс, это позволяет Gateway
"видеть" состояние каждого конкретного пода через Eureka Heartbeats, что
работает быстрее и точнее, чем стандартные проверки L4-балансировщика в K8s».

Как это объединить в ответ:

          «Хотя в Kubernetes есть CoreDNS, в нашем стеке Spring Cloud Gateway взаимодействовал напрямую с Eureka. Библиотека LoadBalancer на стороне шлюза кэшировала список адресов и сама распределяла запросы между микросервисами. Это позволило нам сохранить единый подход к разработке и конфигурации (через lb://service-name), который работал идентично как в облаке, так и при локальном запуске без Kubernetes».

Резюме:

    * CoreDNS — это инфраструктурный справочник (снаружи приложения).
    * Eureka — это прикладной справочник (внутри Java-кода).

В твоем проекте они могли существовать параллельно, но Gateway доверял именно
Эврике.

`цепочка: Loadbalancer - Ingress - Keycloack+Api Gateway - Eureka - user-service(например)`:

Ты всё верно разложил! Это эталонная цепочка прохождения запроса в современном
энтерпрайз-проекте. Давай проясним роль каждого звена, чтобы на собеседовании ты
мог нарисовать эту схему на доске.
Твоя цепочка «Путь запроса»:

1. Cloud Load Balancer (L4): Это «внешняя железка» от облачного провайдера (AWS,
   Google, Яндекс.Облако). У неё есть публичный Static IP. Её единственная
   задача — принять пакеты из интернета и перебросить их внутрь кластера на ноды
   с Ingress.
2. Ingress Controller (Nginx) (L7): Это «умный распределитель» внутри K8s. Он
   расшифровывает HTTPS (SSL-терминация), смотрит на домен (например,
   api.my-promo.ru) и направляет запрос в конкретный сервис.
3. Spring Cloud Gateway + Keycloak: Твой микросервис-шлюз. Он не просто
   перебрасывает байты, он проверяет авторизацию. Сначала запрос идет в фильтр,
   который стучится в Keycloak (или проверяет его подпись), чтобы понять: «А
   пускать ли этого юзера дальше?».
4. Eureka: Твой шлюз спрашивает у Eureka: «По какому IP сейчас живет
   user-service?».
5. User-service: Конечная цель. Шлюз сам делает запрос на конкретный IP пода,
   который он узнал из Eureka.

Тонкий момент: Keycloak vs Gateway
Обычно они работают в связке:

    * Keycloak — это «паспортный стол». Он выдает JWT-токены и хранит базу пользователей.
    * Gateway — это «пограничник». Он смотрит на токен и говорит: «Ок, проходи».

Как это «продать» на интервью:
Если тебя спросят: «Зачем столько звеньев?», твой ответ:

    «Такая многослойная архитектура позволяет четко разделить зоны ответственности:

    * Инфраструктура (LoadBalancer/Ingress): отвечает за доступность кластера извне и шифрование (SSL).
    * Безопасность (Keycloak/Gateway): централизованно управляет доступом, чтобы бизнес-микросервисы вообще не тратили ресурсы на проверку "левых" запросов.
    * Service Discovery (Eureka): дает нам гибкую балансировку на стороне клиента (Client-side LB), что позволяет системе быть независимой от настроек сети Kubernetes и легко масштабироваться».

Твой козырь (Профессиональный нюанс):
Скажи: «Иногда мы использовали BFF (Backend for Frontend) паттерн, где Gateway
не просто пробрасывал запрос, а мог агрегировать данные из двух сервисов в один
ответ, чтобы фронтенд (React/Angular) делал меньше сетевых вызовов».

`архитектура с общими сервисами и одним кастомным`:

То, что вы описываете, — это классическая Multi-tenant архитектура
(мультиарендность), но реализованная на уровне инфраструктуры. Это абсолютно
нормальная практика для B2B-платформ, и в ней нет никакой «каши», если вы
правильно объясните логику разделения.
Для Middle+ разработчика на интервью это отличный шанс показать, как вы
разделяли Core (стабильную платформу) и Tenant-specific (уникальную логику
акции).
Вот как это разложить по полочкам:

1. Архитектурный подход: "Platform + Instances"
   Вы создали PaaS (Platform as a Service) внутри компании.

    * Core Services (Стабильное ядро): Auth, OCR, Kafka, БД — это общие сервисы,
      которые работают всегда. Они не знают про детали конкретных акций.
    * Promo-Instances (Динамическая часть): Под каждую новую акцию (новый домен)
      вы деплоили отдельный экземпляр user-service.

2. Как организовать разработку (по пунктам):
   На вопрос «как вы этим управляли», отвечайте так:

    * Infrastructure as Code (IaC): «Поскольку акций было много и они шли
      параллельно, мы использовали Helm-чарты в Kubernetes. Для запуска новой
      акции на новом домене нам достаточно было создать новый конфиг-файл, и K8s
      поднимал изолированный инстанс user-service с нужными параметрами».
    * Shared Libraries (SDK): «Чтобы не писать код с нуля, мы вынесли всю рутину
      (работу с БД, клиенты к Kafka, логику валидации) в общие библиотеки
      (Starters). Разработка новой акции сводилась к написанию только уникальной
      бизнес-логики».
    * Routing на Ingress: «Новые домены мы разруливали на уровне Ingress
      Controller. Он смотрел на Host в заголовке запроса и направлял трафик в
      нужный инстанс сервиса».

3. Как это «продать» на интервью:

          «Мы организовали разработку по принципу White Label платформы. У нас было стабильное ядро микросервисов, а под каждую уникальную акцию мы разворачивали отдельный инстанс бизнес-логики.
          Это дало нам полную изоляцию: если в коде одной акции была ошибка или она ложилась под нагрузкой, это никак не влияло на другие параллельные промо-кампании. Мы использовали общие Spring Boot Starter-ы, что позволило сократить разработку уникальной части до минимума и быстро выводить новые домены в продакшн».

Почему это НЕ каша:

1. Изоляция: Акции не мешают друг другу (ни в базе, ни в памяти).
2. Масштабируемость: Вы можете выделить больше ресурсов (подов) на «жирную»
   акцию от Pepsi и меньше — на маленькую локальную акцию.
3. Версионность: Одна акция может работать на старой логике, а новая — уже на
   обновленной, и вам не нужно делать болезненный миграционный апдейт для всех
   сразу.

Дополнение:

Это самый надежный и «чистый» архитектурный подход, который только можно
представить для такой системы. В мире больших данных это называется Physical
Isolation (Физическая изоляция арендаторов).
Для интервьюера это звучит как музыка, потому что вы решили сразу три огромные
проблемы: безопасность, производительность и простоту миграций.
Как это преподнести (Ваш «Senior» ответ):

«Мы выбрали стратегию Database-per-Tenant. Под каждую новую промо-акцию (новый
домен) мы разворачивали не только отдельный инстанс бизнес-логики, но и
полностью изолированную базу данных в PostgreSQL.
Почему это было лучшим решением:

1. Безопасность (Data Privacy): Данные пользователей разных брендов (например,
   Pepsi и Магнита) были физически разделены. Это исключало риск утечки данных
   из одной акции в другую на уровне SQL-запроса.
2. Производительность: Нагрузка от одной супер-популярной акции не аффектила
   работу других. Мы могли гибко настраивать ресурсы (CPU/RAM) для конкретной БД
   в облаке.
3. Миграции (Liquibase): Мы могли обновлять схему БД для новой акции, не трогая
   старые, которые уже запущены и работают. Это дало нам колоссальную гибкость в
   разработке уникальных фич».

Как это было организовано технически:
Если спросят «Как вы этим управляли?», отвечайте так:

* Автоматизация: «Мы использовали CI/CD пайплайны и `Helm-чарты`. При запуске
  новой акции скрипт автоматически создавал новую схему/базу в кластере Postgres
  и накатывал туда актуальную структуру через Liquibase».
* Конфигурация: «Каждый инстанс user-service получал свои параметры подключения
  к БД (URL, Credentials) через Environment Variables в Kubernetes».

Почему это НЕ «каша» из сервисов:
Это Standard Enterprise Pattern. Вы создали масштабируемый «завод» по
производству акций.

    * Стабильное ядро (Auth, OCR, Kafka) — работает со своей БД.
    * Промо-сервисы — каждый со своей БД.

Дополнительно:

Это отличный вопрос, который выявляет разницу между глобальными данными и
данными конкретной акции. В архитектуре это называется разделением на Shared
Data (общие данные) и Tenant Data (данные клиента).
Вот как это обычно устроено в таких платформах, и как вам стоит отвечать на
интервью:

1. Сервисы стабильного ядра (Shared Services)
   У таких сервисов, как Auth, OCR или Aggregator, действительно одна общая база
   данных (или кластер БД) на всю платформу.

    * Auth Service: В нем хранятся учетные данные пользователей, которые могут
      участвовать в разных акциях одного или нескольких брендов. Ему нужна
      единая таблица users, чтобы пользователь не регистрируйся заново в каждой
      акции (Single Sign-On подход).
    * Разделение: Чтобы понять, к какой акции относится запись, в таблицах ядра
      просто добавляется колонка promo_id или client_id. Это называется Logical
      Isolation (логическая изоляция).

2. Почему это не создает проблем?
   На интервью вы можете обосновать это так:

    * Единый профиль: «Мы хотели, чтобы у пользователя был один аккаунт в рамках
      нашей экосистемы. Это позволяло нам видеть общую аналитику лояльности».
    * Стабильность нагрузки: «Нагрузка на Auth-сервис предсказуема и растет
      линейно, в отличие от бизнес-логики акций, где трафик может взлететь в 100
      раз за час. Поэтому ядро живет в одной базе, а "взрывные" данные акций — в
      изолированных».

3. Как это связано в цепочке запроса?
   Когда пользователь грузит чек в конкретной акции:

    1. Gateway проверяет токен в общай базе Auth.
    2. Запрос летит в изолированный user-service конкретной акции.
    3. Там данные пишутся в персональную базу этой акции.
    4. Событие летит в Kafka, где в заголовке указан promo_id.

Как ответить на интервью (Твой сценарий):

          «Архитектура была гибридной. Сервисы ядра (Auth, OCR) использовали единую общую базу данных, так как они оперируют глобальными сущностями платформы. Изоляция данных в них была реализована на логическом уровне через promo_id.
          Однако для бизнес-логики акций (сервис user-service) мы использовали стратегию Database-per-Tenant. Под каждую акцию разворачивалась физически отдельная БД.
          Это позволило нам совместить удобство единого входа (SSO) для пользователей с жесткой изоляцией и масштабируемостью данных конкретных промо-кампаний. Если база одной акции переполнялась или тормозила, это никак не влияло на работу авторизации или производительность других параллельных акций».

`Подключение к ядру сервисов:`

Чтобы эта «каша» из сервисов работала как единый механизм, используется Service
Discovery (в твоем случае Eureka) и Shared Configuration.
Вот как новый user-service узнавал, куда ему стучаться, чтобы попасть в «ядро»:

1. Регистрация в Eureka (Discovery)
   Это самый важный момент. Когда ты деплоишь новый инстанс user-service для
   новой акции:

    * В его конфигах (application.yml) прописан адрес Eureka Server (который
      один на всё ядро).
    * При старте сервис говорит: «Привет, я user-service-promo-lays, мой IP
      такой-то».
    * Теперь Gateway и Aggregator видят его в общем списке и знают, как
      перенаправить на него трафик по домену.

2. Подключение к общей Kafka
   Брокер Kafka у тебя один на всю платформу (кластер).

    * Новый сервис подключается к тем же самым адресам (bootstrap-servers).
    * Чтобы сообщения не перемешались, в коде сервиса или в заголовках сообщений
      передается promo_id (идентификатор акции). Таким образом, сервис «Призы»
      понимает, из какой именно акции прилетел чек.

3. Интеграция через API Gateway (Routing)
   Это то, как пользователь с фронтенда попадает в нужный сервис.

* В Spring Cloud Gateway настраиваются правила маршрутизации по Host (домену).
* Пример: Если запрос пришел на promo-pepsi.ru/api/** — отправить его в сервис
  user-service-pepsi. Если на promo-lays.ru/api/** — в user-service-lays.

4. Общие библиотеки (Starters)
   Чтобы разработчику не нужно было каждый раз вручную прописывать адреса
   Auth-сервиса или БД ядра:

    * Ты создавал custom spring-boot-starter.
    * В нем уже «зашиты» дефолтные адреса стабильного ядра.
    * Разработчик просто подключает либу, и сервис «из коробки» знает, где
      искать Keycloak для проверки токенов и куда слать логи в Loki.

Как это кратко описать на интервью:

          «Новые инстансы бизнес-логики интегрировались в общую архитектуру через Service Discovery (Eureka). При деплое каждый сервис регистрировался в едином реестре, что позволяло API Gateway динамически маршрутизировать трафик по доменным именам. Обмен данными с ядром шел через общую Kafka, где сообщения разделялись по promo_id. Для упрощения настройки мы использовали собственные Spring Boot Starter-ы, которые содержали преднастроенные конфигурации для связи со стабильными компонентами платформы».

`Helm-чарты`:

Если Kubernetes — это операционная система для облака, то Helm — это её «магазин
приложений» или менеджер пакетов (аналог apt в Ubuntu, npm в JS или Maven в
Java).
Helm-чарт — это структурированный набор YAML-файлов (шаблонов), который
описывает всё необходимое для запуска вашего Spring Boot приложения в K8s.
Зачем они нужны, если есть обычные манифесты?
Представьте, что у вас 6 микросервисов. Для каждого нужно описать Deployment,
Service, Ingress, ConfigMap.

1. Проблема дублирования: 90% кода в этих YAML-файлах одинаковые. Различаются
   только названия сервисов, порты и Docker-образы.
2. Проблема сред (Environment): Для Dev-стенда вам нужна 1 копия (реплика)
   приложения и слабая БД, а для Prod — 10 копий и мощные ресурсы. В обычных
   YAML вам пришлось бы копировать файлы и править их вручную.

Как работает Helm-чарт:

1. Шаблонизация (Templates): Вместо жестко прописанного имени образа вы пишете
   заглушку: image: {{ .Values.image.repository }}.
2. Файл значений (values.yaml): Это «пульт управления» чартом. Здесь вы один раз
   прописываете:
    * replicaCount: 3
    * image: my-spring-app:v1.2
    * db_url: jdbc:postgresql://prod-db:5432/
3. Упаковка: Вы один раз создаете универсальный шаблон (чарт) для своих Spring
   Boot сервисов и переиспользуете его для всех 6+ приложений, просто подставляя
   разные values.yaml.

Главные фишки для вашего проекта (2-3 недели):

    * Rollback (Откат): Если после деплоя в K8s всё сломалось, одна команда helm rollback мгновенно вернет предыдущую рабочую версию.
    * Управление зависимостями: В чарт вашего приложения можно добавить «зависимость» (например, PostgreSQL или Redis). При установке чарта Helm сам скачает и развернет базу данных рядом с вашим сервисом.
    * Версионность: Каждый деплой — это новая версия (Release). Вы всегда видите в истории: «Версия 5 была задеплоена в среду, версия 6 — сегодня».

Аналогия для Java-разработчика:
Dockerfile — это как .class файл (инструкция для одного контейнера).
Helm-чарт — это как Maven-архетип или проект целиком, который знает, как
собрать, настроить и запустить все части системы вместе.

`структуры папок типичного Helm-чарта для Spring Boot`

Типичный Helm-чарт для Spring Boot проекта выглядит как обычная папка в корне
вашего Git-репозитория (обычно называется /charts или по имени сервиса).
Вот как устроена его структура:

```text
my-spring-app/            # Название чарта
├── Chart.yaml            # Метаданные (версия чарта, описание, версия приложения)

    ├── configmap.yaml    # Шаблон для application.properties
    ├── secret.yaml       # Шаблон для паролей к БД (зашифрованные данные)
    └── _helpers.tpl      # Вспомогательные функции (например, генерация уникальных имен)
```

Как это работает на практике:
В файле templates/deployment.yaml вместо жестко прописанного количества реплик
вы пишете:

replicas: {{ .Values.replicaCount }}

А в файле values.yaml (который вы правите перед деплоем) указываете:

replicaCount: 3
image:
repository: my-registry/spring-boot-app
tag: v1.0.5

Главная фишка для ваших 2-3 недельных спринтов:
Вы можете сделать два разных файла со значениями:

1. values-dev.yaml (1 реплика, маленькая БД, логи в DEBUG).
2. values-prod.yaml (10 реплик, мощная БД, логи в ERROR, включен кэш).

При деплое вы просто говорите: helm install my-app ./my-spring-app -f
values-prod.yaml.

# === Выбор между Kafka и RabbitMQ ===

Выбор между этими брокерами для системы с 1000 RPS и 6+ сервисами — это
классический вопрос на системный дизайн. В твоем проекте с чеками Kafka
выигрывает у RabbitMQ по трем фундаментальным причинам:

1. Пропускная способность (High Throughput)

    * RabbitMQ: Хранит сообщения в оперативной памяти (в основном) и удаляет их
      сразу после подтверждения (Ack). Это быстро, но при 1000 RPS и больших
      очередях он начинает «умножать на ноль» свою производительность, тратя
      ресурсы на управление очередями.
    * Kafka: Пишет данные сразу на диск (используя последовательную запись). Она
      спроектирована для гигантских потоков данных. 1000 RPS для нее — это
      «легкая разминка», в то время как RabbitMQ на таких объемах может начать
      нестабильно работать (особенно при заполнении памяти).

2. Хранение и «Перемотка» (Persistence & Replay)

    * RabbitMQ: Как только сервис подтвердил получение чека, сообщение исчезает.
      Если в сервисе «Призов» был баг и он неправильно начислил баллы за
      последние 2 часа — данные утеряны.
    * Kafka: Это лог событий. Сообщения хранятся столько, сколько ты укажешь
      (например, 7 дней).
    * Выигрыш: Ты можешь «перемотать» время назад (Reset Offset) и заново
      прогнать все чеки через исправленный сервис. Для финансовых или
      промо-акций это критическая фича.

3. Горизонтальное масштабирование (Consumer Groups)

    * RabbitMQ: Масштабируется сложно. Если один сервис не справляется,
      добавление новых копий сервиса может привести к накладным расходам на
      синхронизацию очереди.
    * Kafka: Использует партиции (partitions). Если у тебя 10 партиций в топике
      checks, ты можешь запустить 10 экземпляров сервиса распознавания (OCR).
      Каждый будет параллельно и независимо обрабатывать свою часть чеков. Это
      идеальный способ утилизировать ресурсы Kubernetes.

4. Отказоустойчивость (Availability)

    * Kafka: Изначально распределенная система. Данные реплицируются между
      брокерами (Replication Factor). Падение одной ноды кластера вообще не
      прерывает работу.
    * RabbitMQ: Поддерживает кластеризацию, но она сложнее в настройке и часто
      становится «бутылочным горлышком» при высокой нагрузке.

Как ответить на интервью:

          «Для нашей системы с 1000 RPS мы выбрали Kafka, так как нам требовалась высокая пропускная способность и возможность повторной обработки событий (Replayability). В отличие от RabbitMQ, Kafka позволяет горизонтально масштабировать потребителей через Consumer Groups, что критично для тяжелых задач вроде OCR. Кроме того, хранение лога событий в Kafka дает нам уверенность, что при сбое любого из 6 сервисов мы сможем восстановить состояние системы без потери данных пользователей».

# Выбор Postgres для высоких нагрузок

Выбор PostgreSQL для системы с 1000 RPS и микросервисной архитектурой — это
стандарт индустрии. В отличие от NoSQL (MongoDB) или более простого MySQL,
Postgres дает идеальный баланс между строгостью данных и инструментами
оптимизации.
Вот 5 причин, почему он выигрывает в Highload-проектах:

1. Продвинутые индексы
   Postgres — король индексации. Для 1000 RPS это критично:

    * Частичные индексы (Partial Indexes): Можно создать индекс только по
      «активным» чекам (WHERE status = 'NEW'). Это делает индекс крошечным и
      невероятно быстрым.
    * Индексы на выражения (Functional Indexes): Позволяют искать без потери
      скорости, даже если в запросе есть функции (например, LOWER (email)).
    * Составные индексы: Идеально работают для сложных фильтров в промо-акциях.

2. Поддержка JSONB (Гибрид SQL и NoSQL)
   В чеках часто прилетает много специфических данных от ФНС, которые сложно
   разложить по колонкам.

    * Выигрыш: Вы храните основную структуру в таблицах, а детали — в поле типа
      JSONB. Оно индексируется (GIN-индексы), что позволяет искать по внутренним
      полям JSON так же быстро, как по обычным колонкам.

3. MVCC (Многоверсионность)
   Postgres отлично справляется с ситуацией, когда одни процессы пишут 1000
   чеков в секунду, а другие — читают отчеты.

    * Механика: Читающие транзакции не блокируют пишущие (и наоборот). Это
      позволяет поддерживать высокую пропускную способность (Throughput) без
      «зависаний» базы.

4. Расширяемость и инструменты

    * Postgres Exporter: Как мы обсуждали, он идеально отдает метрики в
      Prometheus.
    * PgBouncer: Позволяет держать тысячи соединений от 6+ микросервисов, даже
      если сама база настроена на лимит в 100 коннектов.
    * Логическая репликация: Позволяет легко создать Read Replicas, чтобы
      разгрузить основной сервер от тяжелых запросов на чтение.

5. Надежность и ACID
   Когда речь идет о призах и деньгах, нельзя терять данные. Postgres
   гарантирует, что транзакция либо записана полностью, либо нет. В связке с
   Transactional Outbox это делает систему «пуленепробиваемой».

Как ответить на интервью:

          «Для проекта с чеками мы выбрали PostgreSQL из-за его мощных возможностей оптимизации: частичных и составных индексов, а также поддержки JSONB для гибких данных от ФНС. Его механизм MVCC позволяет нам поддерживать 1000 RPS без взаимных блокировок при чтении и записи. Кроме того, Postgres отлично масштабируется через Read Replicas и интегрируется в Kubernetes с использованием PgBouncer для управления пулом соединений».

# === Проектирование БД ===

Для проекта с загрузкой чеков и нагрузкой 1000 RPS проектирование БД — это не
просто создание таблиц, а стратегия выживания данных. На интервью по этому
пункту стоит рассказать про 5 ключевых архитектурных решений:

1. Гибридное хранение (Database + S3)
   «Главный принцип — не хранить бинарные данные в реляционной базе.

    * Реализация: Сами сканы чеков (картинки) мы сохраняем в объектное хранилище
      (S3/MinIO), а в PostgreSQL пишем только метаданные и ссылку на файл
      (file_url).
    * Зачем: Это сохраняет размер БД компактным, ускоряет бэкапы и позволяет
      базе фокусироваться на быстрой фильтрации статусов».

2. Схема под высокую нагрузку (Data Types & Scaling)
   «При 1000 RPS таблица чеков растет на миллионы записей в месяц.

    * Типы данных: Для первичных ключей (ID) я выбрал BigInt, чтобы избежать
      переполнения (обычный Integer закончится слишком быстро).
    * JSONB для гибкости: Ответы от ФНС (состав товаров) мы храним в поле типа
      JSONB. Это позволяет не переделывать схему при изменении формата чека, но
      при этом индексировать вложенные поля через GIN-индексы».

3. Индексация «от запроса» (Query-Driven Indexing)
   «Я проектировал индексы, исходя из самых частых бизнес-сценариев:

    * Составной индекс (user_id, status): Чтобы пользователь мгновенно видел
      список своих 'новых' или 'обработанных' чеков.
    * Частичный индекс (Partial Index): Создал индекс только для чеков в статусе
      ERROR или PENDING.
    * Зачем: Это экономит место на диске и ускоряет вставку (INSERT), так как
      индекс не нужно обновлять для 90% успешно обработанных чеков».

4. Паттерн Transactional Outbox
   «Чтобы гарантировать доставку события в Kafka, я спроектировал таблицу
   outbox.

    * Механика: Запись о чеке и событие для Кафки сохраняются в одной транзакции
      через Spring JDBC.
    * Зачем: Это исключает ситуацию, когда чек в базе есть, а процесс
      распознавания не запустился из-за моргнувшей сети».

5. Оптимизация соединений (Connection Management)
   «Для 6 микросервисов в Kubernetes я настроил HikariCP.

    * Решение: Я рассчитал размер пула так, чтобы суммарное количество
      соединений от всех подов не превышало лимит PostgreSQL, и использовал
      PgBouncer для эффективного переиспользования коннектов на стороне
      сервера».

------------------------------
Твой итоговый ответ (Senior-style):

          «Проектирование БД для меня — это поиск баланса между нормализацией и производительностью. Я спроектировал схему, где тяжелый контент вынесен в S3, а в PostgreSQL используются частичные и составные индексы для мгновенной выборки при 1000 RPS. Для обеспечения надежности всей цепочки сервисов я заложил таблицу Outbox, что в связке с асинхронной обработкой в Kafka делает систему устойчивой к любым пикам нагрузки».

# [1] Client Credentials Flow (технический токен сервиса)

Это отличная тема для интервью по безопасности микросервисов. Client Credentials
Flow — это один из сценариев (грантов) стандарта OAuth 2.0, предназначенный для
взаимодействия «машина-машина» (M2M).
В твоем проекте с 6 сервисами это именно то, как, например, сервис «Призов»
подтверждает сервису «Уведомлений», что он — это он, и имеет право отправить пуш
пользователю.

1. В чем суть (Главное отличие)
   В обычном сценарии (Authorization Code) нужен пользователь, который вводит
   логин/пароль. В Client Credentials пользователя нет. Сервис сам является
   «владельцем» своих прав.

    * Идентификатор: client_id (аналог логина сервиса).
    * Секрет: client_secret (аналог пароля сервиса).

2. Как это работает технически (Flow)

    1. Запрос токена: Сервис А стучится в Authorization Server (например,
       Keycloak) и передает свои client_id и client_secret.
    2. Выдача: Сервер проверяет секрет и выдает Machine-to-Machine JWT. В этом
       токене в поле sub (subject) указан ID самого сервиса, а в authorities —
       его технические роли (например, ROLE_INTERNAL_SERVICE).
    3. Использование: Сервис А прикрепляет этот JWT к заголовку Authorization:
       Bearer <token> при вызове Сервиса Б.
    4. Валидация: Сервис Б проверяет подпись токена и видит, что это доверенный
       «коллега» по системе.

3. Почему это важно для твоего проекта (Highload & Security)

    * Безопасность в K8s: Если злоумышленник взломает один сервис, он не сможет
      просто так вызвать остальные без валидного токена.
    * Отсутствие сессий: Токены короткоживущие (например, 5 минут). Если сервис
      скомпрометирован, секрет можно отозвать в Keycloak.
    * Кэширование: При 1000 RPS сервис не запрашивает токен на каждый чих. Он
      берет один токен, кэширует его в памяти (в Spring Boot это делает Spring
      Security OAuth2 Client) и использует, пока тот не протухнет.

4. Что ответить на интервью:

          «Для обеспечения безопасности взаимодействия между нашими 6 микросервисами мы использовали Client Credentials Flow. Каждый сервис имеет свои учетные данные в Keycloak. Мы настроили Spring Security, чтобы сервисы автоматически получали и обновляли технические JWT-токены. Это позволило нам реализовать принцип Zero Trust: даже внутренний трафик в Kubernetes полностью авторизован, а права сервисов ограничены их функционалом (Scopes)».

5. Коварный вопрос: «Где вы хранили client_secret сервиса?»
   Твой ответ:
   «Мы никогда не храним секреты в коде или application.properties. Они хранятся
   в Kubernetes Secrets и пробрасываются в приложение как переменные окружения
   через пайплайн GitLab CI».

## client_id и client_secret

Не совсем. Если ты «зашьешь» логин и пароль прямо в код каждого сервиса, это
будет дырой в безопасности (hardcoded credentials).
В профессиональной разработке на Spring Boot и Kubernetes процесс выглядит как
«матрешка»: данные рождаются в одном месте и безопасно передаются в другое.

1. Где они рождаются? (Keycloak)
   Сначала ты (или DevOps-инженер) заходишь в админку Keycloak и регистрируешь
   там каждый свой сервис как «Client».

    * Выбираешь тип: Confidential.
    * Включаешь галочку: Service Accounts Enable, это и есть Client Credentials.
    * Keycloak сам генерирует уникальный client_id (например, order-service) и
      длинный случайный client_secret.

2. Как они попадают в проект? (GitLab + K8s)
   Чтобы не хранить эти секреты в Git, используется такая цепочка:

    1. GitLab CI: Ты прописываешь эти значения в настройках репозитория
       (Settings -> CI/CD -> Variables) как «Masked» (чтобы их не было видно в
       логах).
    2. Helm/Kubernetes: При деплое GitLab берет эти переменные и создает в твоем
       кластере объект Kubernetes Secret.
    3. Pod: В манифесте твоего приложения (Deployment) указано: «Возьми значение
       из K8s Secret и положи его в переменную окружения
       SPRING_SECURITY_CLIENT_SECRET».

3. Как их видит Spring Security?
   В самом приложении, в файле application.yml, ты не пишешь пароль. Ты пишешь
   ссылку на переменную:

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          internal-client:
            client-id: ${INTERNAL_CLIENT_ID}
            client-secret: ${INTERNAL_CLIENT_SECRET}
            authorization-grant-type: client_credentials
            scope: internal_api
        provider:
          keycloak:
            issuer-uri: https://yourdomain.com
```

Как ответить на интервью:

          «client_id и client_secret создаются в Keycloak при регистрации сервиса. В приложении мы их не храним — они доставляются в контейнер через Kubernetes Secrets. При запуске Spring Security OAuth2 Client подхватывает эти переменные окружения и использует их для автоматического получения технического JWT-токена. Таким образом, разработчик даже не знает реального пароля, что соответствует принципам безопасности Production-ready систем».

Секреты в K8s обычно не общие. У каждого микросервиса (из твоих 6+) свой
собственный «шкафчик» с секретами.

Как это выглядит на практике (Step-by-Step):

1. В Keycloak: Ты создаешь 6 разных клиентов.

* order-service -> свой секрет.
    * payment-service -> свой секрет.
    * ...и так далее.

2. В GitLab: В настройках CI/CD ты создаешь переменные, например,
   ORDER_SERVICE_SECRET, PAYMENT_SERVICE_SECRET.
3. В Kubernetes (Важный момент!): При деплое через Helm для каждого сервиса
   создается свой персональный объект Secret (например, order-service-secret).
    * Зачем? Чтобы сервис «Призов» даже теоретически не мог подсмотреть пароль
      сервиса «Оплаты». Это принцип минимальных привилегий.
4. В Pod (Spring Boot): В манифесте деплоя ты прописываешь маппинг: «Возьми
   значение из ключа secret в секрете order-service-secret и запиши в переменную
   окружения SPRING_SECURITY_CLIENT_SECRET».
5. В Spring Boot: Приложение стартует, видит переменную окружения, идет в
   Keycloak, предъявляет свой ID и секрет, получает JWT и прикрепляет его к
   запросам к другим сервисам.

Почему это круто для интервью?

Если ты скажешь: «Мы использовали раздельные Kubernetes Secrets для каждого
микросервиса», архитектор поймет, что ты заботишься о безопасности и изоляции
компонентов.

Что отвечать, если спросят: «А если секретов станет 100?»

Твой ответ:

          «Для управления большим количеством секретов мы использовали HashiCorp Vault (или интеграцию GitLab + External Secrets Operator), чтобы не копировать их вручную в GitLab, а автоматически доставлять из защищенного хранилища прямо в поды Kubernetes».

В Keycloak секрет приложения не «сравнивается с уже выданным», а используется
для создания (генерации) нового токена.
Вот как это происходит по шагам:

1. Запрос (Request): Твой сервис (например, сервис «Призов») приходит в Keycloak
   и говорит: «Я — promo-service, вот мой секрет super-secret-123. Дай мне
   токен, чтобы я мог сходить в сервис "Уведомлений"».
2. Валидация (Validation): Keycloak смотрит в свою базу данных. Он находит
   клиента promo-service и сверяет присланный секрет с тем, что хранится у него.
    * Важно: Секрет — это как «пароль» сервиса. Он не меняется при каждом
      запросе, он статичен (пока ты не сделаешь ротацию).
3. Выпуск (Issuance): Если секрет совпал, Keycloak генерирует новый JWT-токен
   (Access Token).
    * В этот токен он «зашивает» права (scopes) этого сервиса.
    * Токен подписывается приватным ключом Keycloak.
4. Ответ: Keycloak отдает этот токен твоему сервису.

Что происходит дальше (самое интересное):
Твой сервис «Призов» берет этот токен и идет с ним в сервис «Уведомлений».

* Сервис «Уведомлений» не идет в Keycloak и не знает секрета сервиса «Призов».
* Он просто проверяет подпись JWT-токена (публичным ключом Keycloak). Если
  подпись верна — он верит, что запрос пришел от доверенного «коллеги».

Как это «продать» на интервью:

          «В Client Credentials Flow секрет приложения используется только на этапе авторизации в Keycloak для получения Access-токена. Мы настроили короткое время жизни токена (TTL), чтобы повысить безопасность. Приложение кэширует полученный JWT и использует его для внутренних вызовов, пока он валиден, что снижает нагрузку на Keycloak при наших 1000 RPS».

# Spring JDBC против Hibernate

В высоконагруженных системах (1000 RPS) и проектах с быстрыми спринтами (2–3
недели) Spring JDBC (JdbcTemplate) выигрывает у Hibernate (JPA) по пяти
критическим причинам:

1. Предсказуемость и контроль (No Magic)
   Hibernate генерирует SQL автоматически. Иногда он делает это неэффективно:
   выбирает лишние колонки (SELECT *) или делает скрытые JOIN, которые вы не
   заказывали.

    * В JDBC: Вы пишете SQL руками. Вы точно знаете, какой запрос уйдет в базу,
      и можете мгновенно проверить его через EXPLAIN ANALYZE. Это исключает
      «сюрпризы» с производительностью на проде.

2. Решение проблемы N+1 «из коробки»
   В Hibernate легко допустить ошибку, когда при загрузке списка чеков
   приложение делает отдельный запрос в базу для каждого товара в чеке (1 запрос
   для списка + 100 запросов для деталей).

    * В JDBC: Вы сами проектируете JOIN. Используя ResultSetExtractor, вы
      вытягиваете чек и все его товары за один поход в базу, экономя сетевые
      ресурсы и время ответа.

3. Экономия памяти (Low Overhead)
   Hibernate — тяжелый фреймворк. Он создает прокси-объекты, держит кэш первого
   уровня и постоянно проверяет объекты на изменения (Dirty Checking).

    * В JDBC: Это тонкая обертка над драйвером. Он потребляет минимум RAM
      (Heap). В Kubernetes, где ресурсы подов ограничены, это позволяет
      запустить больше копий приложения на том же железе.

4. Эффективная массовая вставка (Batch Updates)
   Для системы, принимающей тысячи чеков, критично писать данные пачками.

    * В JDBC: Метод jdbcTemplate.batchUpdate () — это прямой и самый быстрый
      способ отправить массив данных в БД одним сетевым пакетом. В Hibernate
      настройка батчинга капризна и часто работает медленнее из-за логики
      жизненного цикла сущностей.

5. Скорость разработки и отладки (Agile)
   В коротких спринтах (2 недели) время на отладку «почему Hibernate ведет себя
   не так» — это непозволительная роскошь.

    * В JDBC: Маппинг через RowMapper прозрачен. Ошибка в SQL видна сразу в
      логах. Любой разработчик в команде мгновенно поймет логику запроса, не
      гадая, как настроены каскады и ленивая загрузка в аннотациях.

Твой ответ на интервью:

          «Для высоконагруженного узла (1000 RPS) мы выбрали Spring JDBC, так как он дает нам полный контроль над SQL и планом выполнения запросов. Мы избежали накладных расходов Hibernate на кэширование и проксирование, что критично для лимитов памяти в Kubernetes. Благодаря Batch Updates и прямому управлению JOIN-ами, мы добились минимального Latency, который был бы труднодостижим на тяжелом ORM в такие сжатые сроки».
