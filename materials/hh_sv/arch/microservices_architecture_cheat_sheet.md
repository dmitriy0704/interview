# Архитектурная шпаргалка для собеседования (Spring Cloud, K8s, Kafka, Redis)

## 1. Входной контур (BFF & Безопасность)
* **Архитектурный паттерн:** BFF (Backend for Frontend) на базе **Spring Cloud Gateway**.
* **Аутентификация:** OAuth2 Authorization Code Flow через **Keycloak**.
* **Связка «Замок и Ключ»:**
  * **В браузере (Ключ):** Строка-идентификатор сессии в формате `HttpOnly, Secure, SameSite=Strict Cookie`. JavaScript не имеет к ней доступа (защита от XSS). Браузер прикрепляет её автоматически.
  * **В сервере (Сейф в Redis):** Объект сессии, привязанный к ID из куки. Хранит тяжелые `access_token` и `refresh_token`.
* **Движение к User Service:** Gateway принимает куку, достает из **Redis** актуальный JWT (Access Token), стирает куку из заголовков и прокидывает токен дальше как `Authorization: Bearer <JWT>`.

## 2. Обработка внутри микросервиса (Stateless Контур)
* **Валидация:** `user-service` принимает JWT и валидирует его подпись **локально** в памяти, используя закэшированные публичные ключи Keycloak (эндпоинт JWKS). Запрос к Keycloak на каждый чих не идет.
* **Парсинг Claims:** Из claim `sub` достается UUID пользователя для запросов к БД, из claim `roles` — права доступа для аннотаций `@PreAuthorize`. Данные хранятся в `SecurityContextHolder` (`ThreadLocal`).

## 3. Асинхронный обмен через Apache Kafka
* **Передача контекста:** В сценариях с долгой или отложенной обработкой в Кафку передается только **`userId`** внутри тела сообщения (JSON). Оригинальный JWT не передается, так как он быстро протухнет (короткий `exp`).
* **Развертывание Кафки:** Для продакшена Кафку выносят **за контур Kubernetes** (в Managed-облако), чтобы изолировать тяжелый дисковый ввод-вывод (I/O Bottleneck) от кластера приложений. Для локального тестирования используют **Docker Compose** (Кафка в режиме KRaft, Redis, Postgres).

## 4. Идемпотентность и Хранение данных (Redis vs PostgreSQL)
* **Роль Redis:** Работает как быстрый инвертированный фильтр *до* обращения к БД. Принимает `event_id` из Кафки (метод `SETNX` с TTL на 24-48 часов). Если пришел дубликат — метод делает `return;`, предотвращая повторные списания.
* **Роль PostgreSQL:** Служит надежным персистентным хранилищем бизнес-сущностей платежей на долгий срок (месяцы/годы).
* **Синхронизация:** Автоматической связи между Redis и БД нет, их последовательным вызовом управляет сам код микросервиса.
* **Уведомления:** Применяется паттерн **Transactional Outbox**. Запись о платеже и задача на пуш-уведомление сохраняются в PostgreSQL в одной транзакции, после чего асинхронный воркер пересылает задачу в топик уведомлений Кафки.

## 5. Управление конфигурациями в Kubernetes
* **Хранение данных:** Адреса и пароли выносятся из кода в нативные ресурсы Kubernetes — **ConfigMaps** и **Secrets**.
* **Обновление на лету:** Библиотека `Spring Cloud Kubernetes Config` отслеживает изменения в ConfigMap и через Spring Actuator обновляет бины с аннотацией `@RefreshScope` без перезапуска подов (подходит для безопасных настроек, например, уровней логирования).
