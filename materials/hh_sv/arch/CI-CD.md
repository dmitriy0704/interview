Чтобы правильно задеплоить Java Spring Boot приложение в Kubernetes через GitLab, нужно пройти три ключевых этапа: подготовить само приложение, настроить CI/CD пайплайн в GitLab и корректно описать манифесты для Kubernetes.

# 🚀 Шаг 1: Подготовка Spring Boot приложения

Основа успешного деплоя — это правильная "упаковка" приложения в Docker-образ с учетом лучших практик для Java в Kubernetes.

  * **Оптимизация Docker-образа**: Используйте многоэтапную сборку. Это позволяет разделить этап компиляции (где нужен тяжелый JDK) и этап запуска (где достаточно легковесной JRE). Также можно "расслоить" JAR-файл (layered JAR), что ускорит загрузку образа, так как при изменении кода будут пересобираться только последние слои.
  * **Внешняя конфигурация**: В кластере Kubernetes для управления настройками приложения используйте **ConfigMap** (для обычных параметров) и **Secrets** (для паролей, ключей API). Это позволит менять конфигурацию без пересборки образа.
  * **Health-чеки Actuator**: Подключите зависимость Spring Boot Actuator. Он предоставляет стандартные эндпоинты для проверки здоровья приложения, которые необходимы Kubernetes:
    * `livenessProbe`: проверяет, "жив" ли контейнер (эндпоинт `/actuator/health/liveness`). Если проверка не проходит, K8s перезапустит контейнер.
    * `readinessProbe`: проверяет, готов ли контейнер принимать трафик (эндпоинт `/actuator/health/readiness`). Пока проверка не пройдена, K8s не будет направлять на под запросы.
* **Graceful Shutdown**: Настройте корректное завершение работы приложения, чтобы при остановке пода оно успевало завершить текущие запросы без потерь. Это настраивается в `application.yml` через параметр `server.shutdown=graceful`.

# ⚙️ Шаг 2: Настройка GitLab CI/CD пайплайна

Файл `.gitlab-ci.yml` в корне вашего репозитория — это "инструкция" для GitLab по сборке, тестированию и деплою.

## 📦 Сборка и публикация Docker-образа

1.  **Соберите код и запустите тесты**: Используйте образ с Maven/Gradle, чтобы выполнить команды сборки и прогона тестов.
2.  **Соберите Docker-образ**: Используйте команду `docker build` для создания образа из вашего Dockerfile.
3.  **Опубликуйте образ в регистри**: Отправьте собранный образ в GitLab Container Registry или другой внешний регистр (Docker Hub, Harbor).

Пример этапа сборки в `.gitlab-ci.yml`:

```yaml
# .gitlab-ci.yml
stages:
  - build
  - test
  - deploy

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"
  IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

cache:
  paths:
    - .m2/repository/

build:
  stage: build
  image: maven:3.8.4-openjdk-17 # Образ с Maven и JDK
  script:
    - mvn clean package -DskipTests # Собираем приложение без тестов
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
  artifacts:
    paths:
      - target/*.jar # Сохраняем собранный JAR для следующих этапов

unit-tests:
  stage: test
  image: maven:3.8.4-openjdk-17
  script: mvn test # Прогоняем unit-тесты
```

## 🚢 Развертывание в Kubernetes

На этом этапе происходит обновление приложения в кластере Kubernetes. Для этого GitLab нужно "подружить" с вашим кластером.

1.  **Подключите кластер**: В настройках вашего проекта GitLab (Settings -> CI/CD -> Variables) создайте переменные для доступа к кластеру, например, `KUBE_CONFIG` с содержимым вашего `kubeconfig`-файла (в формате base64). Или используйте GitLab Kubernetes Agent для более безопасной связи.
2.  **Примените манифесты**: На этапе `deploy` используйте образ с `kubectl` (например, `bitnami/kubectl:latest`) и примените ваши Kubernetes-манифесты командой `kubectl apply -f k8s/`.

Пример этапа деплоя в `.gitlab-ci.yml`:

```yaml
deploy:
  stage: deploy
  image: bitnami/kubectl:latest # Образ с kubectl
  script:
    - echo "$KUBE_CONFIG" | base64 -d > kubeconfig # Декодируем kubeconfig
    - kubectl --kubeconfig=kubeconfig set image deployment/your-app your-app=$IMAGE_TAG # Обновляем образ в деплойменте
    - kubectl --kubeconfig=kubeconfig rollout status deployment/your-app # Ждем успешного обновления
  only:
    - main # Деплоим только из ветки main
```

# 📝 Шаг 3: Подготовка Kubernetes манифестов

Эти YAML-файлы описывают желаемое состояние вашего приложения в кластере. Храните их в репозитории, например, в папке `k8s/`.

* **Deployment**: Управляет под-ами, обеспечивая их нужное количество, стратегию обновления и возможность отката.
* **Service**: Обеспечивает стабильный сетевой доступ к вашим подам (внутренний балансировщик нагрузки).
* **ConfigMap / Secret**: Хранят конфигурацию отдельно от образа.

Пример минимального манифеста `deployment.yaml`:

```yaml
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: your-app
spec:
  replicas: 2 # Две реплики для отказоустойчивости
  selector:
    matchLabels:
      app: your-app
  template:
    metadata:
      labels:
        app: your-app
    spec:
      containers:
      - name: your-app
        image: registry.gitlab.com/your-namespace/your-app:latest # Образ из registry
        ports:
        - containerPort: 8080 # Порт, который слушает приложение
        envFrom: # Подтягиваем переменные из ConfigMap и Secret
        - configMapRef:
            name: your-app-config
        - secretRef:
            name: your-app-secret
        resources: # Обязательно указываем лимиты и запросы ресурсов
          requests:
            memory: "512Mi"
            cpu: "500m"
          limits:
            memory: "1Gi"
            cpu: "1000m"
        livenessProbe: # Проверка на "живость"
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 60 # Ждем 60с перед первой проверкой
          periodSeconds: 10
        readinessProbe: # Проверка на "готовность"
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 5
```

## 💎 Главные советы для production-окружения

*   **Лимиты и запросы ресурсов**: Всегда указывайте `resources.requests` и `resources.limits` для CPU и памяти. Это основа для стабильной работы и масштабирования.
*   **Разделяй и используй**: Активно используйте **ConfigMap** для конфигурации приложения и **Secrets** для чувствительных данных.
*   **Следи за стартом**: Для медленно стартующих Java-приложений настройте `initialDelaySeconds` в пробах, чтобы избежать преждевременных рестартов.
*   **Думай о памяти**: Учитывайте, что JVM потребляет больше памяти, чем просто размер кучи (`-Xmx`). Настройте JVM так, чтобы она не выходила за лимиты памяти контейнера. В новых версиях Java можно использовать `-XX:MaxRAMPercentage`.

Если какой-то из этапов вызовет затруднения, например, написание Dockerfile или настройка переменных в GitLab, дайте знать! Я помогу разобраться детальнее.


## я не совсем понял этап, в котором образ из Gitlab попадает в Kubernetes

Понял, давайте разложу по шагам, как именно собранный Docker-образ из GitLab попадает в работающие поды Kubernetes — здесь часто возникает путаница.

Вся цепочка выглядит так:

1. **GitLab CI собирает образ и пушит его в контейнерный регистри** (в вашем случае — GitLab Container Registry).
2. **В том же пайплайне GitLab выполняет `kubectl`-команду, которая говорит кластеру: «Обнови деплоймент, используя новый образ»**.
3. **Kubernetes сам идёт в регистри, скачивает образ и запускает новые контейнеры** — это и есть «попадание образа в кластер».

Разберу каждый пункт подробно, особенно то, что часто упускают.

---

### 🔄 Шаг 1. Сборка и пуш образа в GitLab Container Registry

У каждого GitLab-проекта есть свой бесплатный контейнерный регистри с адресом вида:
```
registry.gitlab.com/ваш-неймспейс/имя-проекта
```
В CI-переменных уже определены:
- `$CI_REGISTRY` – адрес регистри (`registry.gitlab.com`)
- `$CI_REGISTRY_IMAGE` – полное имя образа для этого проекта (`registry.gitlab.com/your-namespace/your-project`)
- `$CI_REGISTRY_USER` и `$CI_REGISTRY_PASSWORD` – временные учётные данные для пуша (или можно использовать `$CI_JOB_TOKEN`)

В `.gitlab-ci.yml` на этапе сборки мы:
- логинимся в регистри (`docker login ...`)
- собираем образ с тегом, обычно короткий SHA коммита: `$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA`
- пушим его в регистри:
```yaml
build-image:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```
После этого образ физически лежит в GitLab Container Registry и доступен по тегу. Например:
`registry.gitlab.com/mycompany/backend:v1a2b3c4`

---

### 🎮 Шаг 2. GitLab отдаёт команду Kubernetes обновить образ

На этапе деплоя в том же `.gitlab-ci.yml` мы используем образ с `kubectl` и применяем конфигурацию к нашему кластеру Kubernetes. При этом мы **не** копируем образ напрямую в кластер — мы лишь передаём команду: «В деплойменте `my-app` использовать новый образ `registry.gitlab.com/...:v1a2b3c4`».

Один из самых простых способов — команда `kubectl set image`:
```yaml
deploy:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    # Декодируем kubeconfig из CI-переменной, чтобы kubectl мог подключиться к кластеру
    - echo "$KUBE_CONFIG" | base64 -d > kubeconfig
    # Указываем деплойменту использовать новый образ
    - kubectl --kubeconfig=kubeconfig set image deployment/my-app my-app=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    # Ждём завершения обновления
    - kubectl --kubeconfig=kubeconfig rollout status deployment/my-app
  only:
    - main
```
Что здесь происходит:
- `kubectl set image deployment/my-app` обновляет поле `spec.template.spec.containers[].image` в указанном деплойменте.
- Kubernetes сравнивает текущий образ с новым и запускает rolling update: постепенно создаёт поды с новым образом, пока старые ещё работают.

Тот же результат можно получить, если хранить манифест деплоймента в репозитории и вместо `set image` делать `kubectl apply -f deployment.yaml`,  обновив в YAML файле тег образа. Но `set image` удобнее для динамической подстановки.

---

### 🔐 Шаг 3. Как Kubernetes получает доступ к приватному образу

Образ лежит в **приватном** GitLab Container Registry. Kubernetes не сможет его скачать, пока мы не дадим ему учётные данные. Для этого существует объект типа `docker-registry Secret`.

Создаём секрет в том же неймспейсе, где развёрнуто приложение:
```bash
kubectl create secret docker-registry gitlab-regcred \
  --docker-server=registry.gitlab.com \
  --docker-username=<ваш_пользователь_или_токен> \
  --docker-password=<ваш_пароль_или_токен> \
  --namespace=your-namespace
```
(В production вместо личного пароля используют GitLab Deploy Token или Project Access Token.)

Затем в Deployment манифесте ссылаемся на этот секрет через `imagePullSecrets`:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      imagePullSecrets:
      - name: gitlab-regcred   # <-- секрет, который даёт доступ к образу
      containers:
      - name: my-app
        image: registry.gitlab.com/mycompany/backend:v1a2b3c4  # <-- образ из регистри
        ports:
        - containerPort: 8080
        ...
```

Теперь, когда Kubernetes по команде `kubectl set image` видит, что нужно запустить контейнер с образом из `registry.gitlab.com`, он использует этот секрет для авторизации и скачивает образ на ноду.

---

### 🌊 Итоговая картина

Всё вместе выглядит так:

1. **Разработчик пушит код** в ветку `main`.
2. **GitLab CI**:
   - Собирает Spring Boot JAR.
   - Собирает Docker-образ и пушит его в GitLab Container Registry с тегом `$CI_COMMIT_SHORT_SHA`.
   - С помощью `kubectl` даёт команду кластеру обновить деплоймент.
3. **Kubernetes master** принимает команду, создаёт новый ReplicaSet с новыми подами.
4. **Kubelet на ноде**, увидев что под должен использовать образ из приватного регистри, берёт данные из `imagePullSecrets`, логинится в `registry.gitlab.com` и **скачивает образ**.
5. Запускается новый контейнер с вашим приложением. Старые поды постепенно удаляются.

Таким образом, GitLab не «заливает» образ в Kubernetes, а только даёт указание, какой образ из какого регистри взять. Сам же процесс загрузки образа выполняет Kubernetes внутри кластера.

### 📁 Файл `.gitlab-ci.yml` — инструкция только для GitLab
Этот файл действительно лежит в корне вашего репозитория на GitLab, и его понимает **только GitLab CI/CD**. Это «сценарий» для раннеров GitLab: какие этапы запускать, в каких Docker-образах, какие команды выполнять.

### 🔗 Как команды доходят до Kubernetes
Внутри этого сценария вы на этапе деплоя запускаете инструмент `kubectl` (в образе `bitnami/kubectl`, например). `kubectl` — это клиент, который обращается к API вашего кластера Kubernetes и говорит: «обнови деплоймент таким образом, чтобы там использовался новый образ».  
Для этого в GitLab CI нужны учётные данные от кластера (обычно их кладут в переменную `KUBE_CONFIG` — закодированный файл `kubeconfig`). Благодаря им `kubectl` может авторизоваться в Kubernetes.

### ⬇️ Кто скачивает образ
Когда Kubernetes получает от `kubectl` команду «используй образ `registry.gitlab.com/...`», он **сам** идёт в GitLab Container Registry и скачивает этот образ на свои ноды. Никакие инструкции для этого он из `.gitlab-ci.yml` не извлекает — он руководствуется своей внутренней логикой и манифестами (Deployment, StatefulSet и т.п.), которые были применены ранее.

### 🔐 Доступ к приватному регистри
Чтобы Kubernetes мог скачать образ из приватного GitLab Registry, вы должны заранее создать в кластере специальный секрет типа `docker-registry` (например, через `kubectl create secret docker-registry ...`) и указать его в манифесте Deployment в поле `imagePullSecrets`. Именно этот секрет даёт кластеру право доступа к вашему регистри.

### 💡 Итог: кто чем управляет
- **GitLab** (через `.gitlab-ci.yml` и раннеры) выполняет сборку, тесты и **отдаёт команды в Kubernetes** через `kubectl`.
- **Kubernetes** получает команду, сверяет её со своим текущим состоянием, скачивает нужный образ, запускает поды и следит за их статусом.

То есть цепочка: `.gitlab-ci.yml` → `kubectl` (из CI) → Kubernetes API → кластер скачивает образ из регистри. Сам YAML-файл CI/CD не покидает GitLab и невидим для Kubernetes.

Да, вы всё верно понимаете. Давайте разложим процесс с самого начала, чтобы он стал кристально ясным.

### 1. 🚀 Пуш в ветку `main`
Вы делаете `git push` в репозиторий на GitLab. В корне вашего проекта, помимо `Dockerfile` и кода, обязательно лежит файл `.gitlab-ci.yml`. Именно он описывает, что делать GitLab-раннеру.

### 2. ⚙️ Запуск пайплайна
GitLab видит пуш в `main` и, следуя инструкциям из `.gitlab-ci.yml`, запускает цепочку шагов (stages). Обычно это:
- **build** – сборка и юнит-тесты
- **package** – создание JAR-файла (если не сделано в build)
- **docker-build** – сборка Docker-образа
- **deploy** – обновление в Kubernetes

В реальном файле все эти шаги можно объединить для скорости, но логически они разделены.

### 3. 🧪 Тесты проходят ДО сборки образа
В классическом подходе **тесты не запускаются внутри Docker-образа**, а выполняются отдельно, на этапе `build` или `test`.  
Примерная последовательность:
1. Раннер GitLab берёт образ с Maven/Gradle (например, `maven:3.8.4-openjdk-17`).
2. Выполняется `mvn test` – прогоняются все модульные тесты. Если тесты падают, пайплайн останавливается, и дальше ничего не собирается.
3. Если тесты прошли, выполняется `mvn package -DskipTests` (тесты уже не нужны, они проверены), чтобы получить итоговый JAR-файл.
4. После этого запускается сборка Docker-образа, где в Dockerfile мы просто копируем готовый JAR в контейнер (как в примере с многоэтапной сборкой из первого ответа).

Таким образом, **в продакшн-образ попадает только протестированный код, без тестовых зависимостей и без необходимости гонять тесты при каждом запуске контейнера**.

### 4. 🐳 Сборка и публикация Docker-образа
После успешного прохождения тестов GitLab-раннер:
- Логинится в GitLab Container Registry (учётные данные уже есть в переменных CI).
- Выполняет `docker build -t registry.gitlab.com/...:v1a2b3c4 .`
- Выполняет `docker push ...` – теперь образ лежит в регистри и доступен по этому тегу.

Это и есть «образ, готовый для скачивания Kubernetes». Он остаётся в регистри и ждёт.

### 5. ☸️ Kubernetes скачивает образ сам
На следующем этапе (`deploy`) GitLab с помощью `kubectl` говорит кластеру: «в деплойменте `my-app` используй образ `registry.gitlab.com/...:v1a2b3c4`».  
Kubernetes, получив эту команду, проверяет свой `imagePullSecrets` и идёт в GitLab Registry, скачивает образ на нужные ноды и запускает новые поды.

### 🔁 Резюме всей цепочки
```
Пуш кода → GitLab CI:
  1. Сборка + тесты (mvn test) → получен JAR
  2. Сборка Docker-образа (docker build из JAR) → образ в локальном кэше раннера
  3. Пуш образа в GitLab Registry → образ доступен удалённо
  4. Команда kubectl → «обнови деплоймент таким-то образом»

```

  # Конфигурация

  Вы затронули одну из самых дискуссионных тем на собеседованиях. Действительно, подход к управлению конфигурациями сильно изменился с приходом Kubernetes.
Существует два основных способа выноса конфигураций, и на собеседовании очень важно показать, что вы знаете оба, но понимаете, какой из них современнее.
------------------------------
## Подход 1. Классический (Spring-way) — Spring Cloud Config Server
Это тот самый подход, о котором вы читали (с отдельным Git-репозиторием).

* Как это работает: Создается отдельный микросервис — Spring Cloud Config Server. Он подключается к приватному Git-репозиторию, где лежат .properties или .yaml файлы для всех ваших сервисов. Когда payment-service стартует, он первым делом идет в Config Server и скачивает свои настройки.
* Как менять без перезагрузки: Если вы изменили конфигурацию в Git, вы можете отправить специальный HTTP-запрос (POST на эндпоинт /actuator/refresh) в ваш микросервис. Spring Boot перечитает бины, помеченные аннотацией @RefreshScope, и применит новые настройки (например, изменит уровень логирования с INFO на DEBUG или поменяет таймаут) без перезапуска самого приложения.
* Для кого подходит: Для систем, которые разворачиваются на обычных виртуальных машинах (без Kubernetes).

------------------------------
## Подход 2. Современный (Cloud-Native) — Kubernetes ConfigMaps & Secrets
Если ваши микросервисы уже живут в Kubernetes, разворачивать отдельный Spring Cloud Config Server — это избыточность (антипаттерн). Kubernetes сам умеет отлично управлять конфигурациями.

* Как это работает: Настройки хранятся в манифестах Kubernetes в виде двух сущностей:
* ConfigMap — для обычных настроек (адреса Кафки, порты).
   * Secret — для зашифрованных данных (пароли к БД, токены Keycloak).
   * Kubernetes «прокидывает» эти настройки внутрь пода вашего микросервиса либо как переменные окружения (Environment Variables), либо монтирует их как текстовые файлы в виртуальную папку.
* Как менять без перезагрузки: Если вы обновите ConfigMap в Kubernetes, файлы внутри пода обновятся автоматически в течение минуты. Чтобы Spring Boot заметил эти изменения без перезапуска, в экосистеме Spring есть библиотека Spring Cloud Kubernetes Config. Она следит за файлами конфигурации и сама инициирует контекстный рефреш приложения при их изменении.

------------------------------
## Подвох на собеседовании: Стоит ли менять конфигурацию на лету?
Интервьюер может спросить: "А хорошо ли менять настройки без перезагрузки в продакшене?".
Правильный ответ Senior-разработчика: "Нет, для большинства критических настроек это опасно".

* Почему это опасно: Если вы измените адрес базы данных на лету без перезапуска, и половина подов вашего сервиса переключится на новую базу, а вторая половина (из-за сбоя сети) останется на старой — вы получите рассинхронизацию системы (Split-Brain).
* Как делают в проде: На лету меняют только безопасные вещи (например, включают DEBUG-логи, чтобы отловить баг, или меняют текст баннера). Для изменения серьезных настроек (пароли, адреса) используют GitOps и стандартный Rolling Update в Kubernetes: K8s плавно, по одному, перезапускает поды с новыми конфигурациями, гарантируя zero-downtime (без остановки системы).

«Для выноса конфигураций в нашей архитектуре мы используем нативные инструменты Kubernetes — ConfigMaps для обычных настроек и Secrets для конфиденциальных данных. Это избавляет нас от необходимости поддерживать отдельный Spring Cloud Config Server.
Для изменения конфигураций без перезапуска микросервисов мы используем библиотеку Spring Cloud Kubernetes Config в связке со Spring Actuator. Однако для критических инфраструктурных настроек (адреса БД, брокеров) мы предпочитаем безопасный перезапуск подов через стандартный Rolling Update в Kubernetes, чтобы избежать рассинхронизации состояния кластера».
