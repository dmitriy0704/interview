## 📌 Краткое описание приложения (для презентации)

**Название (условно):** Retail Promotion Engine

**Бизнес-задача:**  
Покупатели в крупных розничных сетях участвуют в акциях: после покупки они регистрируют чек в мобильном приложении. Система распознаёт QR-код чека, проверяет его в налоговой службе, выявляет акционные товары и автоматически начисляет призы. Пользователь видит результаты в личном кабинете.

**Архитектура:**  
Микросервисная, развёрнута в Kubernetes. Каждый сервис имеет собственную базу данных. Асинхронное взаимодействие через Kafka. Аутентификация через Keycloak, встроенный service discovery (Kubernetes DNS). Мониторинг: Prometheus, Grafana, Loki.

### 6 микросервисов (основные)

1. **Сервис загрузки чеков** – принимает чек (изображение или PDF), сохраняет в локальное объектное хранилище (MinIO / S3) и публикует событие в Kafka.
2. **Сервис распознавания** – слушает события, загружает файл, извлекает QR-код, отправляет данные в **внешнюю налоговую систему**. Получает от неё список товаров.
3. **Сервис валидации чека** – проверяет, есть ли среди товаров акционные позиции. Если да – формирует событие для выдачи приза.
4. **Сервис выдачи призов** – начисляет призы (баллы, купоны и т.п.), сохраняет информацию в своей БД.
5. **Сервис накопителя данных** – слушает события обо всех чеках и призах, агрегирует их в удобном для отображения виде.
6. **API / Личный кабинет** – предоставляет REST API для клиентского приложения (веб или мобильного), показывает историю чеков и начисленных призов.

**Дополнительные компоненты в кластере:**
- **Keycloak** – выдача JWT-токенов, аутентификация пользователей.
- **Kafka** (например, Strimzi или Confluent) – брокер сообщений.
- **Ingress + OAuth2-Proxy** – защита периметра (внешний трафик).
- **Prometheus, Grafana, Loki** – сбор метрик, логов, дашборды.

### 🖌 Как читать схему

- **Сплошные стрелки** – основной поток данных (синхронный или через Kafka).
- **Пунктирные стрелки** – служебные вызовы (мониторинг, внешние API, аутентификация).
- **MessageBus** – шина Kafka. Все микросервисы общаются асинхронно через топики.
- **OAuth2-Proxy + Keycloak** защищают только **два сервиса**, которые доступны извне: загрузку чеков и личный кабинет. Внутренние вызовы между сервисами идут без дополнительной аутентификации (или с техническими токенами).
- **Object Storage** – локальное файловое хранилище (например, MinIO). Туда складываются оригиналы чеков.
- **Налоговая система** – внешний REST API, который вызывается синхронно из сервиса распознавания (ради простоты; в реальности может быть асинхронная очередь).

## 📝 Что подчеркнуть в рассказе (устно или на слайде)

1. **Пользовательский сценарий:**  
   «Купил товар → сфотографировал чек → загрузил в приложение → система проверила чек через налоговую → нашла акционный товар → начислила приз → пользователь увидел приз в личном кабинете.»

2. **Технологические решения:**  
   - Асинхронное взаимодействие через Kafka – выдерживает пиковые нагрузки (распродажи, чёрная пятница).  
   - Каждый сервис масштабируется независимо (Horizontal Pod Autoscaler).  
   - Авторизация через Keycloak + OAuth2-Proxy на периметре – безопасно и просто.  
   - Мониторинг "золотых метрик" (RPS, latency, errors) через Prometheus + Grafana, логи через Loki.

3. **Kubernetes как платформа:**  
   - Service Discovery – встроенный DNS.  
   - Хранилища – StatefulSet с PersistentVolume для БД и объектное хранилище (MinIO).  
   - Развёртывание через Helm-чарты, GitOps (ArgoCD).
