# Партиционирование

**Партицирование** (правильнее — *партиционирование* или *секционирование*) — это метод организации данных в базе данных, при котором одна большая таблица логически остаётся единой, но физически разбивается на несколько более мелких частей — **партиций** (или секций). Каждая партиция хранится отдельно, но при этом все они остаются частью одной таблицы.

## Основные цели партиционирования

1. **Улучшение производительности** — запросы, которые фильтруют данные по ключу партиционирования, могут обращаться только к нужным партициям, а не ко всей таблице (это называется *pruning* — отсечение партиций). Это особенно заметно на гигантских таблицах (миллиарды строк).

2. **Упрощение обслуживания** — можно удалять, архивировать или реорганизовывать целые партиции мгновенно (например, `DROP PARTITION` работает намного быстрее, чем `DELETE FROM ... WHERE`). Это удобно для хранения данных по времени (например, помесячная ротация логов).

3. **Повышение доступности** — при сбое в одной партиции остальные могут оставаться доступными.

4. **Параллельная обработка** — некоторые СУБД могут параллельно читать/обрабатывать разные партиции.

## Типы партиционирования

- **По диапазону (RANGE)** — разбиение по интервалам значений (например, по датам: данные за январь, февраль, ...).
- **По списку (LIST)** — явный список значений (например, партиции для стран: 'RU', 'US', 'DE', ...).
- **По хэшу (HASH)** — равномерное распределение по хэш-функции от ключа; полезно для балансировки нагрузки.
- **Составное (композитное)** — сочетание нескольких методов (например, сначала RANGE по году, а внутри — HASH по ID клиента).

## Пример (PostgreSQL)

```sql
CREATE TABLE sales (
    id serial,
    sale_date date,
    amount numeric
) PARTITION BY RANGE (sale_date);

-- Создаём партиции на каждый месяц
CREATE TABLE sales_2025_01 PARTITION OF sales
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
```

Запрос `SELECT * FROM sales WHERE sale_date BETWEEN '2025-01-10' AND '2025-01-20'` обратится только к партиции `sales_2025_01`.

## Важные замечания

- Партиционирование **не улучшает все запросы** — оно эффективно, когда условие `WHERE` включает ключ разбиения. В противном случае СУБД может сканировать все партиции, что иногда даже медленнее обычной таблицы.
- Нужно продумывать стратегию: слишком мелкие партиции (например, дневные) создают оверхед, слишком крупные — не дают выигрыша.
- Не все СУБД поддерживают партиционирование одинаково. В MySQL (InnoDB), PostgreSQL, Oracle, SQL Server эта возможность есть, но могут быть ограничения (например, по внешним ключам, уникальным индексам).

## Отличие от шардирования

- **Партиционирование** — физическое разделение внутри одной базы данных (на одном сервере/инстансе).
- **Шардирование** — горизонтальное разделение между разными серверами (распределённые системы). Шардирование часто реализуется на уровне приложения или промежуточного слоя.

## Итог

Партиционирование — это мощный инструмент для работы с очень большими таблицами, где критична скорость удаления старых данных, а запросы почти всегда содержат фильтр по времени или другому «естественному» ключу разбиения. Но, как и любой метод оптимизации, требует грамотного проектирования под конкретные паттерны доступа.

# Шардирование

**Шардирование** (sharding) — это метод горизонтального масштабирования базы данных, при котором большая таблица (или коллекция) разбивается на несколько частей — **шардов** (shards), и каждый шард размещается на отдельном сервере (узле). В отличие от партиционирования (которое остаётся в пределах одного сервера), шардирование распределяет данные по нескольким физическим или виртуальным машинам.

## Основные цели шардирования

1. **Преодоление ограничений одного сервера** — когда объём данных или нагрузка (количество запросов в секунду) превышают возможности одной машины (CPU, RAM, диск, сеть).
2. **Горизонтальное масштабирование** — добавление новых серверов увеличивает ёмкость системы почти линейно.
3. **Повышение отказоустойчивости** — если один шард выходит из строя, другие продолжают работать (но данные на упавшем шарде временно недоступны, если нет реплик).
4. **Снижение задержек** — можно размещать шарды ближе к пользователям (геораспределение).

## Как работает шардирование

Данные распределяются по шардам на основе **ключа шардирования** (shard key). Например, если таблица `users`, ключом может быть `user_id`. Функция распределения (хэш или диапазон) определяет, в какой шард попадёт запись.

При получении запроса:
- Если запрос содержит условие по ключу шардирования (например, `WHERE user_id = 123`), система знает, на какой шард отправить запрос (маршрутизация).
- Если запрос не содержит ключ шардирования (например, `SELECT * FROM users WHERE name = 'Alex'`), его, вероятно, придётся отправить на **все шарды**, а затем агрегировать результаты («scatter-gather»). Это дорого.

## Методы шардирования

### 1. **Диапазонное (Range sharding)**
Каждый шард отвечает за определённый диапазон значений ключа.
- Пример: шард 1: `user_id` 1-1000, шард 2: 1001-2000.
- **Плюсы**: простота, удобно для запросов типа `BETWEEN`.
- **Минусы**: возможен «горячий» шард, если данные распределены неравномерно (например, частые запросы к новым пользователям с большими ID).

### 2. **Хэш-шардирование (Hash sharding)**
Ключ прогоняется через хэш-функцию, и результат определяет шард (обычно `hash(key) % number_of_shards`).
- **Плюсы**: равномерное распределение данных при хорошей хэш-функции.
- **Минусы**: сложность с диапазонными запросами; изменение количества шардов требует перераспределения всех данных (рехэширование).

### 3. **Динамическое (или консистентное хэширование)**
Используется в распределённых системах (Cassandra, DynamoDB). Минимизирует перемещение данных при добавлении или удалении шардов. Каждый шард отвечает за область хэш-кольца, а ключи мапятся по хэшу. При добавлении узла затрагивается только часть данных.

## Где лежит логика шардирования?

- **На уровне приложения** — код сам вычисляет, в какую БД идти. Самый гибкий, но сложный в поддержке.
- **На уровне промежуточного слоя (прокси)** — например, Vitess (для MySQL), Citus (для PostgreSQL), Mongos (для MongoDB).
- **В самой СУБД** — некоторые базы данных поддерживают «родное» шардирование (например, MongoDB, ClickHouse, YugabyteDB, CockroachDB, ScyllaDB).

## Отличия от партиционирования

| Характеристика | Партиционирование | Шардирование |
|----------------|-------------------|---------------|
| Распределение | Внутри одного сервера | Между разными серверами |
| Масштабирование | Ограничено мощностью сервера | Горизонтальное, практически без ограничений |
| Прозрачность | Полностью прозрачно для приложения | Частично прозрачно (нужно знать ключ шарда или использовать прокси) |
| Транзакции и JOIN | Работают естественным образом | Сложны: транзакции через несколько шардов требуют 2PC или других протоколов, JOIN приходится делать на уровне приложения |
| Сложность | Низкая | Высокая |

## Отличие от репликации

- **Репликация** — копирование одних и тех же данных на несколько серверов для отказоустойчивости и масштабирования чтения.
- **Шардирование** — разделение *разных* данных по серверам.

Часто шардирование комбинируют с репликацией: каждый шард может иметь несколько реплик (master-slave или multi-master).

## Основные проблемы шардирования

1. **Операции, не покрытые ключом шарда** — требуют full shard scan → медленно.
2. **Перебалансировка** — при добавлении нового шарда данные нужно перераспределить, что занимает время и нагружает систему.
3. **Глобальные уникальные ID** — стандартный автоинкремент не работает. Используют снежинки (Twitter Snowflake), UUID, или централизованные сервисы (например, Redis incr).
4. **Распределённые транзакции и согласованность** — приходится либо жертвовать ACID (идти к BASE и eventual consistency), либо использовать тяжёлые протоколы.
5. **Сложность администрирования** — нужно следить за состоянием каждого шарда, делать бэкапы, мониторить задержки.

## Примеры систем, использующих шардирование «из коробки»

- **MongoDB** — автоматическое шардирование на основе диапазонов или хэша.
- **Apache Cassandra** — консистентное хэширование, шардирование + репликация.
- **ClickHouse** — для аналитики, шардирование через DISTRIBUTED таблицы.
- **Vitess** — шардирование для MySQL, используется в YouTube.
- **Citus** — расширение PostgreSQL для шардирования.

## Итог

Шардирование — это основной способ масштабирования БД «вширь» для интернет-сервисов с миллиардами записей и высокой нагрузкой. Оно требует тщательного проектирования ключа шардирования, часто подразумевает переход от строгой ACID к более гибким моделям согласованности и не является «серебряной пулей»: многие приложения прекрасно живут с вертикальным масштабированием или репликацией. Но когда одна машина перестаёт справляться — шардирование становится неизбежным.

# Репликация

**Репликация** — это процесс копирования данных с одного сервера базы данных (обычно *мастер* или *источник*) на один или несколько других серверов (*реплики*, или *слейвы*). Цель — обеспечить:

- **Отказоустойчивость** — если мастер выйдет из строя, одну из реплик можно сделать новым мастером.
- **Масштабирование чтения** — все SELECT запросы можно распределять между репликами, снижая нагрузку на мастер.
- **Геораспределение** — разместить реплики ближе к пользователям в разных регионах, уменьшив задержку.
- **Резервное копирование без остановки работы** — бэкап можно делать с реплики, не трогая мастер.

## Как это работает

Обычно **один мастер** принимает все операции записи (INSERT, UPDATE, DELETE), а также чтения. **Одна или несколько реплик** подключаются к мастеру и получают от него поток изменений (благодаря *журналу упреждающей записи* — WAL, или бинарному логу). Реплики повторяют эти изменения на своих копиях данных.

Поток изменений может передаваться:
- **Асинхронно** — мастер не ждёт подтверждения от реплик. Это быстрее, но при падении мастера последние изменения могут быть потеряны.
- **Синхронно** — мастер ждёт, пока хотя бы одна реплика подтвердит запись. Медленнее, но нулевая потеря данных.
- **Полусинхронно** — баланс: мастер ждёт подтверждения от одной реплики, остальные получают асинхронно.

## Типовые топологии репликации

### 1. **Master-Slave (ведущий-ведомый)**
- Один мастер для записи, один или несколько слейвов для чтения.
- Пример: классическая репликация MySQL, PostgreSQL streaming replication.
- **Плюсы**: простота, хорошее масштабирование чтения.
- **Минусы**: если мастер падает, нужно вручную или автоматически повышать один из слейвов. Слейвы могут быть неактуальны из-за асинхронности.

### 2. **Multi-Master (многомастерная)**
- Несколько мастеров, каждый принимает запись. Изменения распространяются между ними. Сложно обеспечить согласованность (конфликты при одновременной записи одной строки).
- Пример: MySQL Group Replication, Galera Cluster, PostgreSQL BDR.
- **Плюсы**: высокая доступность записи, распределённая запись.
- **Минусы**: сложность настройки, возможные конфликты, задержки при синхронизации.

### 3. **С цепочкой реплик**
- Мастер → слейв1 → слейв2. Слейв1 выступает репликой для слейва2. Это полезно при большом количестве реплик, чтобы не нагружать мастер сетью.
- Минус: задержки возрастают с каждым звеном.

### 4. **Вложенная репликация с демультиплексором** — редко, но бывает.

## Отличия от шардирования и партиционирования

| Метод | Что делает | Для чего |
|-------|------------|----------|
| **Репликация** | Копирует *те же самые* данные на другие серверы | Отказоустойчивость, масштабирование чтения |
| **Шардирование** | Разбивает *разные* данные по серверам | Масштабирование записи, обход ограничений одного сервера |
| **Партиционирование** | Разбивает таблицу на части внутри одного сервера | Обслуживание (DROP PARTITION), иногда ускорение запросов |

Репликацию и шардирование часто комбинируют: каждый шард может быть мастером с несколькими репликами. Тогда система одновременно получает и масштабирование записи (за счёт шардов), и отказоустойчивость (за счёт реплик внутри шарда).

## Основные проблемы репликации

1. **Задержка репликации (replication lag)** — реплика может отставать от мастера, и при чтении из неё пользователь увидит устаревшие данные. Решается синхронной репликацией (ценой производительности) или чтением из мастера для критических операций («read-after-write consistency»).
2. **Конфликты в multi-master** — если один мастер изменил строку, а другой в то же время её удалил или тоже изменил. Нужны детекторы и разрешители конфликтов.
3. **Автоматический failover** — при падении мастера система должна быстро поднять нового. Это требует дополнительного софта (Patroni, Orchestrator, MHA или встроенных решений).
4. **Сетевая нагрузка** — при частых изменениях реплики потребляют трафик; особенно тяжело при цепочках.

## Примеры реализации

- **PostgreSQL** — потоковая репликация (физическая) и логическая репликация (на уровне таблиц, может выборочно).
- **MySQL** — асинхронная и полусинхронная репликация, Group Replication (multi-master).
- **MongoDB** — replica sets (от 1 мастера, до 50 реплик, автоматический failover).
- **Redis** — master-replica репликация (в том числе с sentinel для failover).
- **Cassandra** — репликация встроена в шардированную архитектуру (каждая запись отправляется на несколько узлов по топологии).

## Итог

Репликация — базовый и очень эффективный инструмент для повышения отказоустойчивости и разгрузки мастера за счёт чтения с реплик. Она не решает проблему масштабирования записи (здесь нужен шардинг), но в паре с ним создаёт промышленные кластеры БД. Главная сложность — это обеспечение свежести данных на репликах и автоматический выбор нового мастера при сбое. Для большинства проектов с хорошим разделением на чтение/запись и не сверхвысокой требовательностью к актуальности (возможен небольшой lag) репликация — идеальное решение.

# Надежность

Надежность баз данных в микросервисной архитектуре — это нетривиальная задача, потому что вместо одной «толстой» БД вы получаете множество мелких, распределенных по разным сервисам. Общая надежность системы **не равна сумме надежностей отдельных БД** — появляются новые виды отказов и сложности.

## Ключевые отличия от монолитной надежности

В монолите обычно одна БД с ACID-транзакциями, бэкапами и репликацией. При сбое БД падает весь монолит. В микросервисах:

- **Один сервис может упасть, остальные продолжают работать** — это плюс для надежности (изоляция отказов).
- **Но распределенные транзакции и консистентность данных между сервисами — главная головная боль**.
- Сетевые задержки, разделение (network partition), частичные отказы становятся нормой.

## Основные угрозы надежности БД в микросервисах

1. **Потеря данных при сбое одного сервиса** — если у сервиса своя БД, она тоже может упасть. Нужна репликация и резервное копирование **для каждой БД**.
2. **Несогласованность данных между сервисами** — из-за отсутствия распределенных транзакций (2PC редко используют из-за проблем с масштабируемостью и блокировками).
3. **Каскадные отказы** — один медленный БД-запрос может исчерпать пул соединений сервиса, затем зависнуть весь сервис, а вызовы из других сервисов начнут накапливаться.
4. **Сложность восстановления после сбоя** — нужно восстанавливать не одну БД, а десятки, и в правильном порядке (если есть зависимости по данным).
5. **Проблемы с миграциями схем** — разные сервисы могут эволюционировать независимо, но обратная совместимость критична.

## Паттерны и практики повышения надежности

### 1. **Database per Service (и изоляция)**
Каждый микросервис владеет **своей БД** (логически или физически). Никто не обращается к чужой БД напрямую — только через API.
- **Надежность**: отказ одной БД не валит другие. Но данные того сервиса становятся временно недоступны для всех, кто от него зависит.

### 2. **Асинхронное общение и саги (Sagas)**
Вместо распределенных транзакций — последовательность локальных транзакций с компенсирующими действиями.
- Если шаг не удался, запускаются откаты (компенсации). Система остается в консистентном состоянии (часто в *eventual consistency*).
- **Надежность**: нет длительных блокировок, но требуется идемпотентность и обработка частичных отказов.

### 3. **CQRS + Event Sourcing**
Хранение событий (event store) как источника истины. Базы данных (чтения) могут перестраиваться из событий.
- При сбое можно «переиграть» события — точное восстановление состояния.
- Но сам event store должен быть сверхнадежным (обычно используют репликацию и распределенные логи).

### 4. **Репликация, резервное копирование, failover**
- Каждая БД должна быть отказоустойчивой внутренне: репликация (желательно синхронная в критичных случаях), автоматический failover (например, Patroni для PostgreSQL).
- Регулярные бэкапы + возможность point-in-time recovery.
- **Важно**: восстановление одной БД не должно сломать зависимости (версии API, неактуальные события).

### 5. **Шаблоны устойчивости на уровне приложения**
- **Retry with backoff** — временные сетевые сбои или старт реплики.
- **Circuit Breaker** — если БД сервиса A не отвечает, вызовы из сервиса B быстро отсекаются, чтобы не держать потоки.
- **Bulkhead** — изолированные пулы соединений для разных вызовов, чтобы один «плохой» запрос не забил все.
- **Timeouts** — обязательно на все БД-операции.

### 6. **Избегание распределенных транзакций (2PC)**
Они редко используются в микросервисах, потому что:
- Низкая производительность.
- Блокировки ресурсов на неопределенное время.
- При сбое координатора — ручное вмешательство.
Вместо них — саги, idempotent APIs, eventual consistency.

### 7. **Мониторинг и observability**
- Метрики для каждой БД: latency, ошибки, свободное место, репликационный лаг.
- Distributed tracing — чтобы увидеть цепочку вызовов через несколько сервисов и их БД.
- Логирование всех «почти сбоев» (retries, circuit breaker trip).

### 8. **Версионирование и обратная совместимость**
Миграция схемы одной БД не должна ломать другие сервисы. Практики:
- Добавлять новые поля, не удалять старые (пока все не перестанут их использовать).
- Использовать расширения (например, `ALTER TABLE.. ADD COLUMN` без NOT NULL).
- Применять стратегии «expand & contract» (сначала добавить, потом удалить).

## CAP-теорема и выбор

В микросервисной архитектуре вы неизбежно сталкиваетесь с CAP: при сетевом разделении выбирайте между согласованностью (C) и доступностью (A).  
- Для платежных систем — согласованность важнее (даже если недоступна, лучше отказать).  
- Для корзины покупок — доступность (пусть данные устареют, но пользователь должен добавлять товары).  

Понимание этого помогает проектировать БД каждого сервиса с правильной моделью.

## Отказы на практике

Что происходит, когда БД сервиса «Заказы» падает целиком?
- Сервис «Платежи» не может подтвердить оплату → клиент видит ошибку.
- Но сервис «Каталог товаров» продолжает работать.
- Если используется **eventual consistency**, накопленные события (например, из очереди) будут обработаны после восстановления БД.
- Если же был синхронный вызов, то надо крутить ретраи или отдавать 5xx.

## Итог

Надежность БД в микросервисной архитектуре — это **компромисс между локальной надежностью каждой БД и глобальной консистентностью**.  
Общая надежность может быть **выше**, чем у монолита, из-за изоляции отказов и возможности деградации отдельных функций (partial failure handling). Но достигается это ценой огромной операционной сложности: каждая БД требует своих бэкапов, реплик, миграций, плюс нужны саги, circuit breakers, идемпотентность.  

**Ключевые принципы**:
- Каждый сервис отвечает за свою БД.
- Используйте eventual consistency везде, где можно.
- Проектируйте для отказов (failures are expected).
- Инвестируйте в observability.
