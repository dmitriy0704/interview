### Повторная отправка запросов в Spring JDBC и HicariCP

Нет, это миф. Ни Spring JDBC, ни пул соединений HikariCP не умеют и не должны
автоматически повторять SQL-запросы в случае ошибок выполнения бизнес-логики.
Здесь часто происходит путаница между двумя совершенно разными понятиями:
повтором сетевых соединений (то, что делает HikariCP) и повтором
бизнес-запросов/транзакций (то, что пулы делать не имеют права).

Что на самом деле делает HikariCP?

HikariCP — это исключительно пул соединений (Connection Pool). Его зона
ответственности — выдать вашему приложению готовую «трубу» (Connection) до базы
данных, а после использования забрать её обратно. [1]
(https://redstack.dev/2026/06/11/oracle-connection-pooling-in-spring-boot-when-to-use-hikaricp-and-when-to-use-ucp/), [2]
(https://habr.com/ru/articles/1030880/)
• Он умеет: Переподключаться к базе данных. Если база данных моргнула, упала или
сетевой кабель между серверами задели шваброй, HikariCP в фоновом режиме будет
циклично пытаться восстановить само соединение с СУБД. Когда ваше приложение
попросит у него соединение (dataSource.getConnection ()), HikariCP перед выдачей
проверит его на «живучесть». Если оно мертвое — он попробует создать новое. [1]
(https://stackoverflow.com/questions/71046984/why-doesnt-hikaricp-reconnect-to-the-database), [2]
(https://github.com/brettwooldridge/HikariCP/issues/907)
• Он НЕ умеет: Повторять ваши SQL-запросы. Если соединение было живым, но в
процессе выполнения вашего SELECT или UPDATE база данных вернула ошибку
(например, таймаут блокировки строки Deadlock, сетевой сбой посреди транзакции
или ошибка синтаксиса), HikariCP просто пробросит это исключение (SQLException)
наверх в ваше приложение. Он не будет заново отправлять этот SQL-запрос. [1]
(https://github.com/brettwooldridge/HikariCP/issues/907), [2]
(https://stackoverflow.com/questions/71046984/why-doesnt-hikaricp-reconnect-to-the-database)

Почему HikariCP или Spring JDBC не имеют права делать ретраи?

Если бы они делали это автоматически, это привело бы к катастрофическим
последствиям для данных (нарушению принципа идемпотентности):
Представьте запрос UPDATE accounts SET balance = balance - 100 WHERE id = 1.
Запрос долетел до базы данных, списал деньги, но в этот момент моргнула сеть, и
ответ от базы до приложения не дошел. Если бы HikariCP или Spring JDBC молча
повторили этот запрос еще раз в новом соединении, у пользователя списались бы
деньги дважды.
Определять, безопасно ли повторять упавший запрос, может только само приложение,
которое знает бизнес-контекст.

Как правильно настроить повторные запросы в Spring Boot?

Если вам нужно, чтобы при определенных ошибках (например, при сетевых микросбоях
или блокировках Deadlock) запросы повторялись автоматически, это настраивается
на уровне бизнес-логики приложения.

Способ 1. Использование Spring Retry (Стандартный путь)

Для этого в проект подключается библиотека spring-retry. Она позволяет повесить
простую аннотацию на метод сервиса или репозитория.

1. Добавляем аннотацию @EnableRetry над главным классом конфигурации.
2. Помечаем метод аннотацией @Retryable:

```java

@Service
public class OrderService {

    @Autowired
    private JdbcTemplate jdbcTemplate;

    // Метод повторится максимум 3 раза, если вылетит TransientDataAccessException
    // (класс исключений Spring JDBC для временных ошибок БД, например, таймаутов)
    @Retryable(
            retryFor = {TransientDataAccessException.class},
            maxAttempts = 3,
            backoff = @Backoff(delay = 1000, multiplier = 2) // Сначала подождать 1с, потом 2с
    )
    @Transactional
    public void createOrder(Order order) {
        jdbcTemplate.update("INSERT INTO orders ...", ...);
    }

    // Если все 3 попытки провалились, сработает этот метод (опционально)
    @Recover
    public void recoverOrderFailure(TransientDataAccessException e, Order order) {
        // Логируем ошибку, отправляем уведомление или пишем в очередь ошибок (DLQ)
        logger.error("Не удалось создать заказ после 3 попыток", e);
    }
}

```

Способ 2. Функциональный подход (через RetryTemplate)

Если аннотации вам не подходят, можно использовать RetryTemplate в коде явно,
оборачивая в него вызовы jdbcTemplate:

```java
public void demo() {
    retryTemplate.execute(context -> {
        return jdbcTemplate.queryForObject("SELECT ...", String.class);
    });
}

```

Исключение из правил: Некоторые продвинутые драйверы баз данных коммерческого
уровня (например, Oracle JDBC с технологией Transparent Application Continuity
(TAC)) умеют на уровне самого драйвера СУБД безопасно повторять строго
неизменяющие данные запросы (SELECT) при падении узла кластера. Но это фича
дорогой СУБД и её специфичного драйвера, а не Spring или HikariCP. [1]
(https://blogs.oracle.com/developers/hikaricp-best-practices-for-oracle-database-and-spring-boot), [2]
(https://redstack.dev/2026/06/11/oracle-connection-pooling-in-spring-boot-when-to-use-hikaricp-and-when-to-use-ucp/)
Хотите узнать, какие именно типы исключений (кроме TransientDataAccessException)
стоит указывать в параметрах ретрая, чтобы случайно не начать бесконечно
повторять запросы с заведомо неверным синтаксисом (BadSqlGrammarException)?

Как это красиво сказать на интервью:

      «Для меня отказоустойчивость — это когда система деградирует грациозно 
      `(Graceful Degradation)`. Например, если у нас упал сервис рекомендаций, 
      пользователь всё равно может оформить заказ, просто не увидит блок "С 
      этим также покупают". Мы достигали этого за счет Circuit Breakers, 
      асинхронности через очереди и грамотной настройки Liveness/Readiness проб
      в Kubernetes».


# Пул соединений (HikariCP)? как он работает с БД и со Spring JDBC?

Работа HikariCP — это критический узел в высоконагруженных системах (1000 RPS).
Без него ваше приложение на Spring Boot просто «задохнулось» бы, пытаясь
открывать новое соединение для каждого чека.
Вот как это работает и что рассказать на интервью:

1. Зачем нужен пул (Проблема)
   Установление физического соединения с БД (TCP-хендшейк, авторизация) — это
   очень дорогая и медленная операция (может занимать 10–50 мс). Если у вас 1000
   запросов в секунду, база данных сойдет с ума только от процесса подключения.
2. Принцип работы HikariCP («Библиотека готовых связей»)
   HikariCP заранее открывает определенное количество соединений и держит их
   «горячими» в памяти.

    * Borrow (Аренда): Когда ваш JdbcTemplate хочет выполнить SQL, он просит
      соединение у Hikari. Тот выдает уже готовое за микросекунды.
    * Return (Возврат): Как только метод репозитория отработал, соединение не
      закрывается физически, а просто помечается как «свободное» и возвращается
      в пул для следующего запроса.

3. Ключевые параметры (Что вы «настраивали»)
   Интервьюер-архитектор обязательно спросит про эти настройки:

    * maximum-pool-size: Сколько максимум соединений может открыть один под. Для
      1000 RPS и 6 сервисов важно не превысить max_connections самой базы
      данных.
    * connection-timeout: Сколько времени поток из Java готов ждать свободное
      соединение из пула, прежде чем выкинуть ошибку.
    * idle-timeout: Через какое время «простаивающее» соединение будет закрыто
      для экономии ресурсов.

4. Связка с Spring JDBC и Транзакциями

    * @Transactional: Когда вы ставите эту аннотацию, Spring берет одно
      соединение из HikariCP в начале метода и удерживает его до самого конца.
    * Риск: Если внутри транзакции вы делаете долгий вызов внешнего API
      (например, ФНС), соединение будет «занято» всё это время.
    * Решение: Сначала скачайте данные от ФНС, а потом открывайте транзакцию для
      записи в БД через JDBC. Это экономит место в пуле.

5. Почему именно HikariCP?
   Это самый быстрый пул в мире Java (название переводится с японского как
   «свет»). Он использует микро-оптимизации в байт-коде и кастомные коллекции,
   чтобы минимизировать задержки.

Как это «продать» на интервью:

      «Для работы с БД на 1000 RPS мы использовали HikariCP как самый 
      производительный пул соединений. Я настраивал размеры пула так, чтобы 
      сбалансировать нагрузку между 6 микросервисами и не перегрузить 
      PostgreSQL. Также мы мониторили метрики пула через Micrometer: если 
      количество ожидающих потоков (Pending Threads) росло, это был сигнал для 
      масштабирования базы или оптимизации медленных SQL-запросов».

Коварный вопрос: «Что будет, если в пуле 10 соединений, а пришло 100
одновременных запросов?»
Ваш ответ: «10 запросов начнут работу мгновенно, а остальные 90 встанут в
очередь. Если они не дождутся свободного соединения за время connection-timeout,
они упадут с ошибкой. Чтобы этого избежать, мы используем горизонтальное
масштабирование подов и мониторинг утилизации пула».
