Виртуальные потоки (Virtual Threads) — это киллер-фича Java 21, которая
позволяет твоему приложению масштабироваться почти «бесплатно». На интервью это
лучший способ показать, что ты не просто обновил версию в Maven, а понимаешь
современную архитектуру JVM.

1. В чем проблема «старых» потоков (Platform Threads)?
   Раньше один поток Java соответствовал одному потоку операционной системы (1:
   1).

    * Они тяжелые: Один поток потребляет около 1 МБ памяти (Stack).
    * Их мало: Ты не можешь поднять 100 000 потоков — сервер упадет по памяти
      или захлебнется в Context Switching (когда процессор тратит больше времени
      на переключение между задачами, чем на саму работу).
    * Проблема ожидания: Когда твой сервис ждет ответа от Postgres или Kafka,
      поток просто «висит» и ничего не делает, но ресурсы ОС потребляет.

2. Как работают Virtual Threads (Многие к Одному)?
   Виртуальные потоки живут внутри JVM. Они очень легкие (несколько КБ вместо 1
   МБ).

    * Суть: Когда виртуальный поток доходит до блокирующей операции (запрос к БД
      или чтение из сокета), JVM просто «снимает» его с реального потока ОС и
      откладывает в сторону.
    * Результат: Реальный поток ОС в это время берет другую задачу. Как только
      данные из БД пришли, JVM возвращает виртуальный поток обратно и продолжает
      работу.

3. Что это дало твоему проекту?
   В приложении с чеками у тебя было много I/O-интенсивных задач (запросы к ФНС,
   в Кафку, в БД).

    * Пропускная способность: Вместо того чтобы ограничивать сервер пулом в 200
      потоков (и заставлять 201-го пользователя ждать), ты смог обрабатывать
      тысячи запросов одновременно на том же самом железе.
    * Упрощение кода: Тебе не нужно писать сложный реактивный код (WebFlux),
      который трудно отлаживать. Ты пишешь обычный синхронный код, а Java 21
      делает его эффективным «под капотом».

Как ответить на интервью (Твой сценарий):

      «В проекте мы перешли на Java 21, чтобы использовать Virtual Threads. 
      Это позволило нам отказаться от ограничений стандартных пулов потоков при
      работе с блокирующим I/O.
      Поскольку наш сервис постоянно взаимодействует с PostgreSQL и Kafka, 
      раньше потоки часто простаивали в ожидании ответа. Виртуальные потоки 
      позволили нам держать тысячи открытых соединений одновременно, при этом 
      потребление памяти (RAM) снизилось на 15-20%, так как мы перестали плодить
      тяжелые нативные потоки ОС. Это значительно подняло пропускную способность
      системы без закупки дополнительных серверов».

Каверзный вопрос: «А когда их НЕЛЬЗЯ использовать?»
Твой ответ:

1. CPU-интенсивные задачи: Если поток считает сложные математические алгоритмы
   или жмет видео — виртуальные потоки не помогут, тут нужны ядра процессора.
2. ThreadLocal: Если в коде активно используется огромный объем данных в
   ThreadLocal, это может «раздуть» память, так как виртуальных потоков теперь
   миллионы.
3. Synchronized блоки: В некоторых случаях (хотя в Java 21 это почти пофиксили)
   поток может «приклеиться» (pinning) к реальному потоку и не отпускать его.
   Лучше использовать ReentrantLock.
4. Закрепление потока-носителя (Pinning): Если виртуальный поток выполняет
   блокирующую операцию внутри synchronized-блока (до JDK 24), нативного метода
   (JNI / FFM), загрузки класса или файлового ввода-вывода в Linux, он временно
   «привязывается» к физическому потоку ОС, блокируя его и снижая эффективность
   (хотя в JDK 24+ по JEP 491 проблема synchronized решена).
5. Узкие места в зависимых системах: Виртуальные потоки позволяют запустить
   тысячи одновременных задач, но если ваше приложение упирается в базу данных
   (например, пул соединений HikariCP ограничен 10–20 коннектами) или внешний
   API, то само приложение просто перегрузит эти внешние системы очередями
   запросов.
6. Проблемы с пулами на базе ThreadLocal: Массовое создание виртуальных потоков
   приводит к взрывному росту инициализаций объектов внутри ThreadLocal
   (например, не потокобезопасных SimpleDateFormat), так как разработчики
   привыкли считать, что «потоков мало», а с виртуальными их могут быть
   миллионы. Вместо ThreadLocal теперь рекомендуется использовать Scoped Values.
7. Не подходят для тяжелых CPU-bound задач: Виртуальные потоки не дают
   прироста скорости для чистых вычислительных задач (математика, обработка
   видео, шифрование). Они эффективны только для I/O-bound (ожидание ответа
   сети, базы данных, файлов).
8. Монополизация без вытеснения: Виртуальные потоки не являются вытесняющими в
   плане ЦП; если поток крутится в бесконечном цикле без блокировок
   ввода-вывода, он может монополизировать поток-носитель.

### Java Virtual Threads и Spring Boot

Это отличный вопрос, который показывает, что ты лезешь «под капот» фреймворка.
Короткий ответ: в Spring Boot по умолчанию всё еще используются «старые» потоки,
но одной строчкой в конфиге их можно заменить на виртуальные.
Давай разберемся, как это устроено:

1. Как это работает «по старинке» (Java 8/11/17)
   В Spring Boot встроен сервер (обычно Tomcat). У него есть Thread Pool (пул
   потоков), обычно это 200 штук.

    * Пришел запрос → Tomcat берет один «живой» поток из пула → поток идет в
      БД → поток ждет ответа → поток отдает ответ пользователю → поток
      возвращается в пул.
    * Проблема: Если 201-й пользователь пришел, а все 200 потоков ждут ответа от
      медленной базы данных, 201-й будет просто висеть и ждать, пока освободится
      поток ОС.

2. Как это работает в Java 21 + Spring Boot 3.2+
   Начиная со Spring Boot 3.2, появилась магическая настройка в
   application.properties: spring.threads.virtual.enabled=true
   Что происходит, когда ты это включаешь:
   Spring перенастраивает Tomcat и все внутренние исполнители (TaskExecutors).
   Теперь на каждый входящий HTTP-запрос Spring Boot не берет тяжелый поток из
   пула, а создает новый виртуальный поток.

* Результат: Ты больше не ограничен числом 200. Ты можешь обрабатывать 10 000
  запросов одновременно. Как только запрос уходит в «ожидание» (БД или Kafka),
  виртуальный поток освобождает реальный поток процессора для других задач.

3. Это разные вещи или одно и то же?
   Это совместная работа:

    * Spring Boot — это диспетчер (кто принимает запрос и вызывает нужный метод
      контроллера).
    * Java 21 (Virtual Threads) — это ресурс (на чем именно выполняется этот
      метод).

Как ответить на интервью (Твой сценарий):

      «В своих проектах на Spring Boot 3 я активировал поддержку виртуальных 
      потоков через свойство spring.threads.virtual.enabled.
      Это позволило отойти от классической модели Thread-per-request, где 
      количество одновременных соединений ограничено размером пула потоков 
      Tomcat (обычно 200). Теперь на каждый входящий запрос Spring создает 
      легковесный виртуальный поток Java 21.
      Это особенно эффективно в нашем микросервисе чеков, так как там много 
      блокирующих операций (запросы к ФНС и PostgreSQL). В итоге мы получили 
      высокую пропускную способность (Throughput) на том же железе, не 
      переписывая код на сложный реактивный WebFlux».

Важный нюанс: Если ты не включил эту настройку в конфиге, то даже на Java 21
твой Spring Boot будет работать на старых тяжелых потоках.

### Использование виртуальных потоков и HikariCP

Да, вы абсолютно правы. В приложении на Spring Boot можно одной строчкой
включить виртуальные потоки, а пул подключений к БД настраивается отдельно,
чтобы приложение не перегрузило базу данных.

Что такое HikariCP?

HikariCP — это не отдельный модуль, а стандартный пул подключений (Connection
Pool) для работы с реляционными базами данных, который встроен в Spring Boot по
умолчанию (начиная с версии 2.x).
Когда вашему приложению нужно выполнить SQL-запрос, оно не создает каждый раз
новое тяжелое физическое сетевое соединение с БД (это очень медленно). Вместо
этого оно берет уже открытое соединение из пула HikariCP, использует его и сразу
возвращает обратно.

Как это настроить вместе?

Вам достаточно настроить всего несколько параметров в файле
application.properties (или application.yml):
properties

# 1. Включаем виртуальные потоки (требуется Spring Boot 3.2+ и Java 21+)

spring.threads.virtual.enabled=true

# 2. Ограничиваем максимальное количество одновременных подключений к БД в HikariCP

spring.datasource.hikari.maximum-pool-size=30

# 3. Время ожидания свободного подключения из пула (в миллисекундах)

spring.datasource.hikari.connection-timeout=2000
Используйте код с осторожностью.

Как это работает под капотом и в чем подвох?

1. Новое «узкое горлышко»: Раньше (на классических потоках платформы) количество
   запросов ограничивалось потоками самого веб-сервера (например, по умолчанию в
   Tomcat их 200). База данных была защищена этим лимитом. С виртуальными
   потоками веб-сервер может одновременно принять десятки тысяч запросов.
2. Борьба за подключения: Если к вам придет 10 000 одновременных запросов,
   виртуальные потоки обработают их мгновенно, но когда они все одновременно
   пойдут в БД, они упрутся в лимит HikariCP (в нашем примере — 30).
3. Очередь и таймаут: Первые 30 виртуальных потоков получат соединения и начнут
   делать запросы. Остальные 9970 потоков «уснут» и будут ждать своей очереди в
   течение connection-timeout (2 секунды). Если за 2 секунды соединение не
   освободится, пользователь получит ошибку (SQLException / Connection is not
   available).

Рекомендации по настройке пула для виртуальных потоков

• Не раздувайте пул слишком сильно: Не нужно ставить maximum-pool-size=5000
только потому, что у вас много виртуальных потоков. Сама база данных
(PostgreSQL, MySQL) имеет свой жесткий лимит на физические подключения и просто
упадет от нехватки памяти или CPU. Официальные рекомендации для HikariCP на
Medium советуют держать размер пула в районе 20–50 соединений для большинства
стандартных приложений.
• Защита на входе (Rate Limiting): Чтобы при резком наплыве трафика пользователи
не получали ошибки от HikariCP, запросы лучше ограничивать еще на входе в
приложение — с помощью Bucket4j, Spring Cloud Gateway или на уровне
Nginx/Kubernetes.

• Какую базу данных вы используете?
• Какой объем параллельных запросов (RPS) вы ожидаете?

### Расчет нагрузки для 1000 RPS в Kubernetes, Postgres

Нагрузка в 1000 RPS в связке с Kubernetes, PostgreSQL и виртуальными потоками —
это классический сценарий, где стандартные настройки «из коробки» гарантированно
приведут к сбою. Виртуальные потоки снимут лимит на конкурентность внутри Java,
и вся нагрузка моментально ударит по базе данных.
Ниже представлена архитектура и расчет параметров для стабильной работы такой
системы.

1. Архитектурный расчет для 1000 RPS

Главное правило: Размер пула HikariCP зависит не от количества виртуальных
потоков и не от RPS, а от времени выполнения одного SQL-запроса и возможностей
самого сервера PostgreSQL.
Допустим, ваш средний запрос в БД (с учетом индексов) выполняется за 10
миллисекунд (0.01 сек).
• Одно соединение в пуле за 1 секунду может обслужить: 1 / 0.01 = 100 запросов.
• Чтобы суммарно обработать 1000 RPS, всей системе математически необходимо:
\(1000 / 100 = \mathbf{10}\) активных соединений. [1]
(https://habr.com/ru/articles/1031770/), [2]
(https://medium.com/codex/jdbc-connection-pool-exhaustion-in-spring-boot-how-hikaricp-actually-works-under-load-9a142a570934)

Фактор Kubernetes (Репликация)

В K8s вы вряд ли держите один большой под (Pod). Допустим, ваше приложение
развернуто в 4 подах (репликах) для отказоустойчивости и балансировки.
Если общая потребность — 10 соединений, мы закладываем запас на неравномерность
трафика (умножаем на 2-3). Итого нужно около 30 соединений на всю систему.
Делим на 4 пода:
spring.datasource.hikari.maximum-pool-size = 8 (или 10) на каждый под. [1]
(https://blog.devgenius.io/maximise-your-postgresql-database-performance-with-connection-pooling-e746cb35802c), [2]
(https://www.linkedin.com/pulse/optimizing-hikaricp-connection-pooling-spring-boot-3x-manoj-mishra-3ehff)
Важно: Суммарное количество соединений со всех подов не должно превышать лимит
самой Postgres (max_connections в postgresql.conf). Если у вас 4 пода по 10
соединений = 40. Плюс запас на администраторов и другие сервисы. Для Postgres
держать max_connections в районе 100–200 — абсолютно нормально.

2. Конфигурация для каждого Пода (Spring Boot)

В application.properties для каждого пода устанавливаем жесткие, но справедливые
лимиты:

```properties
# Включаем виртуальные потоки
spring.threads.virtual.enabled=true
# Маленький, но эффективный пул (для 4 подов)
spring.datasource.hikari.maximum-pool-size=10
# Удерживаем соединения открытыми, чтобы не тратить время на handshake
spring.datasource.hikari.minimum-idle=10
# Время ожидания соединения в пиках. В K8s лучше поставить жесткие 2-3 секунды.
# Если виртуальный поток не получил коннект за 2 сек, лучше быстро ответить пользователю 503,
# чем копить очередь из тысяч «зависших» виртуальных потоков.
spring.datasource.hikari.connection-timeout=2000
# Время жизни соединения в пуле (30 минут — стандарт)
spring.datasource.hikari.max-lifetime=1800000
```

3. Где и как настраивать Rate Limiting при 1000 RPS?

Так как виртуальные потоки легко переварят 1000 RPS на уровне CPU и памяти
приложения, защищать нужно именно базу данных от «захлебывания», если время
ответов БД вдруг вырастет (например, с 10 мс до 100 мс из-за тяжелого запроса).
В инфраструктуре Kubernetes ограничивать входящий поток правильнее всего
послойно:

Уровень 1: Лимиты на уровне Ingress / API Gateway (Рекомендуется)

Если вы используете популярный NGINX Ingress Controller, не нужно писать код для
контроля RPS внутри Java. Настройте аннотации прямо в манифесте Ingress. Это
отсечет острую DDOS-нагрузку или ошибки циклов со стороны фронтенда еще до того,
как они дойдут до Spring Boot:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    # Ограничение: не более 300 запросов в секунду с одного IP (подгоняется под нужды)
    nginx.ingress.kubernetes.io/limit-rps: "300"
    # Буфер для кратковременных всплесков
    nginx.ingress.kubernetes.io/limit-burst-connections: "50"
```

Уровень 2: Защита внутри Spring Boot (Внутренний Rate Limiter)

Если трафик легитимный, но локально один из эндпоинтов начинает перегружать пул,
можно использовать Semaphore или библиотеку Resilience4j Resilience4j
RateLimiter поверх методов, работающих с БД.
Поскольку виртуальные потоки блокируются очень "дешево", обычный Java Semaphore
на 40-50 разрешений перед вызовом тяжелых сервисов с БД сработает идеально. Он
просто временно приостановит виртуальный поток, не расходуя системные ресурсы
ОС, и не даст пулу HikariCP уйти в глухой таймаут.

Итог для вашей архитектуры:

1. Виртуальные потоки: Включены, легко держат 1000+ параллельных
   HTTP-соединений.
2. HikariCP: Настроен на 10 соединений на под (при условии наличия нескольких
   подов).
3. PostgreSQL: Защищен малым размером пула HikariCP и не падает от нехватки
   памяти.
4. Ingress: Срезает аномальные всплески трафика на входе в кластер. [1]
   (https://habr.com/ru/articles/1031770/)
   Чтобы окончательно зафиксировать конфигурацию, подскажите:
   • Какое примерно время выполнения (latency) у ваших основных SQL-запросов?
   • Используете ли вы PgBouncer перед PostgreSQL, или приложения подключаются к
   базе напрямую?

> погоди, объясни еще раз, параметры приложения в цифрах, все равно какие, для
> нескольких подов одного сервиса всегда считаются для каждого пода как для
> отдельного приложения? параметр * количество подов? или это один параметр на
> весь сервис? параметр / количество подоа?

Да, вы абсолютно правы в своей догадке: все параметры в конфигурационном файле
приложения (application.properties) всегда указываются для каждого пода в
отдельности, как для независимой копии приложения.
Каждый под — это изолированный контейнер со своим экземпляром Spring Boot и
своим собственным пулом HikariCP, который ничего не знает о существовании
соседних подов.
Поэтому работает математика деления (Параметр базы данных / Количество подов):

Формула расчета пула соединений

Если вы определили, что для вашей базы данных PostgreSQL оптимально и безопасно
держать, например, всего 40 одновременных подключений со стороны этого
микросервиса, то настройка для application.properties считается так:
\(\text{Maximum\ Pool\ Size для одного пода}=\frac{\text{Общий лимит соединений
для всего сервиса}}{\text{Количество подов}}\)
• Если у вас 1 под \(\rightarrow \) прописываете
spring.datasource.hikari.maximum-pool-size = 40
• Если у вас 2 пода \(\rightarrow \) прописываете
spring.datasource.hikari.maximum-pool-size = 20 (в сумме \(20 \times 2 = 40\))
• Если у вас 4 пода \(\rightarrow \) прописываете
spring.datasource.hikari.maximum-pool-size = 10 (в сумме \(10 \times 4 = 40\))

Почему это критически важно в Kubernetes?

Если вы совершите частую ошибку и укажете в конфиге «общую» цифру (например,
40), рассчитывая, что это лимит на весь сервис, то произойдет следующее:

1. Вы раскатываете приложение в Kubernetes, указав maximum-pool-size=40.
2. Kubernetes запускает 4 пода.
3. Каждый под инициализирует свой HikariCP и пытается забрать себе до 40
   соединений.
4. В пике нагрузки 4 пода попытаются открыть \(40 \times 4 = \mathbf{160}\)
   подключений к PostgreSQL.
5. Если в настройках самой Postgres (max_connections) стоял лимит, например,
   100, то база данных начнет выдавать ошибку too many connections, и часть
   ваших подов просто «отвалится» и не сможет обрабатывать запросы.

Главный вывод

Конфигурируя Spring Boot, вы всегда настраиваете один конкретный экземпляр, а

Если у вас в Kubernetes настроено автомасштабирование (HPA), из-за которого
количество подов постоянно меняется (например, от 2 до 10 в зависимости от
нагрузки), это может усложнить расчет пула. Скажите:
• У вас фиксированное количество подов (например, всегда ровно 4)?
• Или настроено динамическое масштабирование в зависимости от CPU/памяти?
Я подскажу, как правильно рассчитать лимиты пула, чтобы база не легла при резком
масштабировании подов.

толку: виртуальные потоки снимают ограничение с Java-приложения, но они никак не
масштабируют саму базу данных.
Если у вас 5000 запросов, а пул к БД равен 50, то 4950 виртуальных потоков
действительно будут просто стоять «в очереди» и ждать свободного коннекта. Из-за
того, что виртуальные потоки очень «легкие», они не съедят всю оперативную
память сервера (как это сделали бы классические потоки ОС), но пользователи всё
равно начнут получать ошибки по таймауту (connection-timeout), так как база
физически не успевает переварить такой поток.
И чтобы 10 000 человек не «долбили» ваше приложение, в игру вступает Rate
Limiting.

Как ограничить количество запросов?

Ограничивать количество именно виртуальных потоков напрямую в Spring Boot обычно
не имеет смысла (ведь сервер создает их автоматически на каждый чих/запрос).
Вместо этого ограничивают количество одновременно обрабатываемых HTTP-запросов
(concurrency) или количество запросов в секунду (RPS).
Делать это можно на двух уровнях, в зависимости от вашей архитектуры:

Способ 1: На входе в кластер (Инфраструктурный Rate Limit)

Это самый правильный подход в Kubernetes. Вы не пускаете лишних пользователей
внутрь приложения. Запросы режутся на уровне Ingress-контроллера (например,
Nginx) или API Gateway.
• Плюс: Приложение вообще не тратит ресурсы на лишний трафик.
• Минус: Если у вас 4 пода, и лимит общий, нужно настраивать распределенный rate
limiter.

Способ 2: Внутри самого Java-приложения (Прикладной Rate Limit)

Если вам нужно защитить конкретный эндпоинт (например, /api/v1/buy), который
делает тяжелые запросы в БД, вы можете ограничить конкурентность прямо в коде.
Поскольку виртуальные потоки блокируются невероятно дешево, для этого идеально
подходит обычный java.util.concurrent.Semaphore [3] или библиотека Resilience4j.
Пример, как это выглядит концептуально:

```java

@RestController
public class OrderController {

    // Разрешаем одновременно выполнять запросы к БД только 60 потокам на этот под
    // (чуть больше, чем размер пула HikariCP, чтобы была небольшая очередь)
    private final Semaphore databaseSemaphore = new Semaphore(60);

    @GetMapping("/heavy-query")
    public ResponseEntity<String> getDatabaseData() throws InterruptedException {
        // Если уже зашло 60 потоков, 61-й виртуальный поток мягко "уснет" прямо здесь, 
        // НЕ занимая пул HikariCP и НЕ расходуя память ОС
        if (!databaseSemaphore.tryAcquire(1, TimeUnit.SECONDS)) {
            // Если за 1 секунду очередь не дошла, сразу возвращаем клиенту ошибку 429
            return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS).body("Сервер перегружен");
        }

        try {
            // Здесь идет ваш обычный вызов репозитория/БД
            return ResponseEntity.ok(orderService.findAll());
        } {
            databaseSemaphore.release(); // Обязательно освобождаем место для следующего потока
        }
    }

}
```

Используйте код с осторожностью.

Идеальный баланс в цифрах

Если вам нужно обрабатывать 1000 RPS, а база (через пул HikariCP) может
комфортно переваривать только 40 одновременных запросов, ваша защитная цепочка
должна выглядеть так:

1. База данных (PostgreSQL): Готова принять максимум 40 соединений со Spring
   Boot.
2. Пул HikariCP: Выделяет ровно maximum-pool-size = 40.
3. Внутренний Rate Limiter (Semaphore): Настроен, например, на 50-60 разрешений.
   Зачем чуть больше, чем пул? Чтобы 40 потоков работали в БД, а еще 10–20
   стояли на «низком старте» в Java-памяти и мгновенно хватали освободившееся
   соединение, исключая простои.
4. Внешний Rate Limiter (Ingress/Gateway): Обрубает всё, что летит свыше
   условных 1200 RPS (на весь кластер).
   При такой схеме:
   • При обычном трафике всё летает за счет виртуальных потоков.
   • При всплеске до 5000 RPS лишние запросы либо отсекаются на Ingress (ошибка
   429), либо упираются в Семафор внутри Java и цивилизованно ждут, не создавая
   хаос в пуле подключений HikariCP и не перегружая PostgreSQL.
   Теперь, когда общая картина ясна, скажите:
   • Хотите посмотреть, как настроить Resilience4j RateLimiter через аннотации,
   чтобы не писать Semaphore вручную?
   • Или вам интереснее, как настроить аналогичную защиту на уровне Nginx
   Ingress в Kubernetes?

> как настроить Resilience4j RateLimiter через аннотации, чтобы не писать
> Semaphore вручную? и второй вопрос, получается если я ограничу количество
> запросов на кластер или приложение то и количество виртуальных потоков будет
> примерно такого же количества? они не будут создаваться сами собой в гигантских

Отличные вопросы, которые выводят на правильное понимание архитектуры
высоконагруженных систем.
Сначала небольшое терминологическое уточнение для Resilience4j: в этой
библиотеке есть два похожих, но разных инструмента:
• RateLimiter — ограничивает RPS (количество запросов за единицу времени,
например, не более 1000 запросов в 1 секунду).
• Bulkhead (Перегородка) — ограничивает concurrency (количество одновременно
выполняющихся запросов прямо сейчас). [1]
(https://www.baeldung.com/spring-boot-resilience4j), [2]
(https://medium.com/@noushka99anu/understanding-rate-limits-in-java-springboot-using-resilience4j-b7f3d9ee0715)
Так как ваша цель — заменить Semaphore (контролировать именно количество
одновременно выполняющихся в БД потоков, а не секундный лимит), вам нужен именно
@Bulkhead. Ниже показано, как его настроить. [1]
(https://www.baeldung.com/spring-boot-resilience4j)

Часть 1: Настройка Resilience4j Bulkhead через аннотации

Чтобы заменить ручной Semaphore, выполните три простых шага.

Шаг 1: Добавьте зависимости

В pom.xml вашего Spring Boot 3 приложения должны быть добавлены стартер
Resilience4j и AOP (необходим для работы аннотаций): [1]
(https://www.baeldung.com/spring-boot-resilience4j)
```xml
<dependency>
<groupId>io.github.resilience4j</groupId>
<artifactId>resilience4j-spring-boot3</artifactId>
<version>2.2.0</version> <!-- Используйте актуальную версию -->
</dependency>
<dependency>
<groupId>org.springframework.boot</groupId>
<artifactId>spring-boot-starter-aop</artifactId>
</dependency>
```


Шаг 2: Конфигурация в application.yml

Прописываем настройки для нашей "перегородки" (аналог параметров Семафора): [1]
(https://resilience4j.readme.io/docs/getting-started-3)
```yaml
resilience4j:
bulkhead:
instances:
dbLimit:

  # Максимальное количество ОДНОВРЕМЕННО выполняющихся потоков внутри метода
  maxConcurrentCalls: 60
  # Сколько времени входящий виртуальный поток готов ждать в очереди,
  # если все 60 мест заняты. 1 секунда (1000мс) — разумный предел.
  maxWaitDuration: 1000ms
```

Используйте код с осторожностью.

Шаг 3: Применение аннотации в коде

Теперь достаточно просто повесить аннотацию @Bulkhead на метод контроллера или
сервиса, который обращается к базе данных: [1]
(https://www.baeldung.com/spring-boot-resilience4j)
```java
import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @GetMapping("/orders")
    // Указываем имя инстанса из конфига и метод-запасной вариант (fallback), если места кончились
    @Bulkhead(name = "dbLimit", fallbackMethod = "dbLimitFallback")
    public ResponseEntity<Object> getOrders() {
        return ResponseEntity.ok(orderService.findAll());
    }

    // Этот метод сработает автоматически, если 60 мест заняты и поток прождал 1 секунду
    public ResponseEntity<Object> dbLimitFallback(Throwable exception) {
        // Возвращаем клиенту цивилизованный HTTP 429 Too Many Requests
        return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS)
                .body("Сервер перегружен. Пожалуйста, повторите попытку позже.");
    }

}
```
Вся логика с tryAcquire, очередями и release () теперь под капотом библиотеки.

Часть 2: Что происходит с количеством виртуальных потоков при лимитах?

Ответ: Да, вы абсолютно правы. Если вы ограничиваете трафик на входе в кластер
или приложение, количество виртуальных потоков НЕ будет расти бесконечно. Оно
будет строго пропорционально количеству допущенных в систему запросов.
Давайте пошагово проследим физику процесса для двух сценариев:

Сценарий А: Лимит на уровне Ingress (внешний)

К вам летит 10 000 RPS. На Ingress-контроллере стоит жесткий лимит — 1 200 RPS
на кластер.

1. Ingress пропускает только 1 200 запросов. Остальные 8 800 он сбрасывает на
   подлете и мгновенно возвращает им ошибку 429.
2. Внутрь вашего Spring Boot приложения за эту секунду доходит только 1 200
   сетевых запросов.
3. Встроенный сервер (Tomcat) создаст ровно 1 200 виртуальных потоков (по одному
   на запрос).
4. Результат: Никакого гигантского количества потоков. Приложение работает в
   абсолютно штатном и комфортном режиме.

Сценарий Б: Лимит внутри приложения (@Bulkhead или Semaphore)

К вам пришел резкий всплеск, и Ingress пропустил 5 000 запросов прямо в Spring
Boot. На методе БД стоит @Bulkhead (maxConcurrentCalls = 60). [1]
(https://www.baeldung.com/spring-boot-resilience4j)

1. Tomcat мгновенно создаст 5 000 виртуальных потоков, так как они создаются на
   каждый входящий HTTP-запрос автоматически.
2. Пугаться ли этого? Нет. 5 000 виртуальных потоков для Java — это сущие
   копейки (они займут всего несколько мегабайт в куче, в отличие от тяжелых
   потоков ОС, которые бы намертво забили память сервера).
3. Первые 60 потоков заходят в метод и занимают пул HikariCP.
4. Остальные 4 940 потоков упираются в @Bulkhead и мягко «засыпают». Они не
   тратят ресурсы CPU, а просто лежат в памяти в виде легковесных
   Java-объектов. [1] (https://www.baeldung.com/spring-boot-resilience4j)
5. По истечении maxWaitDuration: 1000ms, те потоки, что не дождались очереди,
   получают ошибку, выполняют метод dbLimitFallback и тут же уничтожаются
   сборщиком мусора (GC).

Вывод

Виртуальные потоки создаются сами собой на каждый чих приложения, но они
микроскопические. Защита (Rate Limit) на уровне Ingress гарантирует, что их
количество никогда не превысит разумный барьер. А защита на уровне приложения
(Bulkhead) гарантирует, что даже если потоков создалось много, они цивилизованно
постоят в памяти Java, но ни за что не пойдут ломать вашу базу данных. [1]
(https://medium.com/@noushka99anu/understanding-rate-limits-in-java-springboot-using-resilience4j-b7f3d9ee0715), [2]
(https://www.baeldung.com/spring-boot-resilience4j)
