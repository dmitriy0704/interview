# CI/CD

Чтобы правильно задеплоить Java Spring Boot приложение в Kubernetes через
GitLab, нужно пройти три ключевых этапа: подготовить само приложение, настроить
CI/CD пайплайн в GitLab и корректно описать манифесты для Kubernetes.

# 🚀 Шаг 1: Подготовка Spring Boot приложения

Основа успешного деплоя — это правильная "упаковка" приложения в Docker-образ с
учетом лучших практик для Java в Kubernetes.

* **Оптимизация Docker-образа**: Используйте многоэтапную сборку. Это позволяет
  разделить этап компиляции (где нужен тяжелый JDK) и этап запуска (где
  достаточно легковесной JRE). Также можно "расслоить" JAR-файл (layered JAR),
  что ускорит загрузку образа, так как при изменении кода будут пересобираться
  только последние слои.
* **Внешняя конфигурация**: В кластере Kubernetes для управления настройками
  приложения используйте **ConfigMap** (для обычных параметров) и **Secrets**
  (для паролей, ключей API). Это позволит менять конфигурацию без пересборки
  образа.
* **Health-чеки Actuator**: Подключите зависимость Spring Boot Actuator. Он
  предоставляет стандартные эндпоинты для проверки здоровья приложения, которые
  необходимы Kubernetes:
    * `livenessProbe`: проверяет, "жив" ли контейнер (эндпоинт
      `/actuator/health/liveness`). Если проверка не проходит, K8s перезапустит
      контейнер.
    * `readinessProbe`: проверяет, готов ли контейнер принимать трафик (эндпоинт
      `/actuator/health/readiness`). Пока проверка не пройдена, K8s не будет
      направлять на под запросы.
* **Graceful Shutdown**: Настройте корректное завершение работы приложения,
  чтобы при остановке пода оно успевало завершить текущие запросы без потерь.
  Это настраивается в `application.yml` через параметр
  `server.shutdown=graceful`.

# ⚙️ Шаг 2: Настройка GitLab CI/CD пайплайна

Файл `.gitlab-ci.yml` в корне вашего репозитория — это "инструкция" для GitLab
по сборке, тестированию и деплою.

## 📦 Сборка и публикация Docker-образа

1. **Соберите код и запустите тесты**: Используйте образ с Maven/Gradle, чтобы
   выполнить команды сборки и прогона тестов.
2. **Соберите Docker-образ**: Используйте команду `docker build` для создания
   образа из вашего Dockerfile.
3. **Опубликуйте образ в регистри**: Отправьте собранный образ в GitLab
   Container Registry или другой внешний регистр (Docker Hub, Harbor).

Пример этапа сборки в `.gitlab-ci.yml`:

```yaml
# .gitlab-ci.yml
stages:
  - build
  - test
  - deploy

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"
  IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

cache:
  paths:
    - .m2/repository/

build:
  stage: build
  image: maven:3.8.4-openjdk-17 # Образ с Maven и JDK
  script:
    - mvn clean package -DskipTests # Собираем приложение без тестов
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
  artifacts:
    paths:
      - target/*.jar # Сохраняем собранный JAR для следующих этапов

unit-tests:
  stage: test
  image: maven:3.8.4-openjdk-17
  script: mvn test # Прогоняем unit-тесты
```

## 🚢 Развертывание в Kubernetes

На этом этапе происходит обновление приложения в кластере Kubernetes. Для этого
GitLab нужно "подружить" с вашим кластером.

1. **Подключите кластер**: В настройках вашего проекта GitLab (Settings ->
   CI/CD -> Variables) создайте переменные для доступа к кластеру, например,
   `KUBE_CONFIG` с содержимым вашего `kubeconfig`-файла (в формате base64). Или
   используйте GitLab Kubernetes Agent для более безопасной связи.
2. **Примените манифесты**: На этапе `deploy` используйте образ с `kubectl`
   (например, `bitnami/kubectl:latest`) и примените ваши Kubernetes-манифесты
   командой `kubectl apply -f k8s/`.

Пример этапа деплоя в `.gitlab-ci.yml`:

```yaml
deploy:
  stage: deploy
  image: bitnami/kubectl:latest # Образ с kubectl
  script:
    - echo "$KUBE_CONFIG" | base64 -d > kubeconfig # Декодируем kubeconfig
    - kubectl --kubeconfig=kubeconfig set image deployment/your-app your-app=$IMAGE_TAG # Обновляем образ в деплойменте
    - kubectl --kubeconfig=kubeconfig rollout status deployment/your-app # Ждем успешного обновления
  only:
    - main # Деплоим только из ветки main
```

# 📝 Шаг 3: Подготовка Kubernetes манифестов

Эти YAML-файлы описывают желаемое состояние вашего приложения в кластере.
Храните их в репозитории, например, в папке `k8s/`.

* **Deployment**: Управляет под-ами, обеспечивая их нужное количество, стратегию
  обновления и возможность отката.
* **Service**: Обеспечивает стабильный сетевой доступ к вашим подам (внутренний
  балансировщик нагрузки).
* **ConfigMap / Secret**: Хранят конфигурацию отдельно от образа.

Пример минимального манифеста `deployment.yaml`:

```yaml
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: your-app
spec:
  replicas: 2 # Две реплики для отказоустойчивости
  selector:
    matchLabels:
      app: your-app
  template:
    metadata:
      labels:
        app: your-app
    spec:
      containers:
        - name: your-app
          image: registry.gitlab.com/your-namespace/your-app:latest # Образ из registry
          ports:
            - containerPort: 8080 # Порт, который слушает приложение
          envFrom: # Подтягиваем переменные из ConfigMap и Secret
            - configMapRef:
                name: your-app-config
            - secretRef:
                name: your-app-secret
          resources: # Обязательно указываем лимиты и запросы ресурсов
            requests:
              memory: "512Mi"
              cpu: "500m"
            limits:
              memory: "1Gi"
              cpu: "1000m"
          livenessProbe: # Проверка на "живость"
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 60 # Ждем 60с перед первой проверкой
            periodSeconds: 10
          readinessProbe: # Проверка на "готовность"
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 5
```

## 💎 Главные советы для production-окружения

* **Лимиты и запросы ресурсов**: Всегда указывайте `resources.requests` и
  `resources.limits` для CPU и памяти. Это основа для стабильной работы и
  масштабирования.
* **Разделяй и используй**: Активно используйте **ConfigMap** для конфигурации
  приложения и **Secrets** для чувствительных данных.
* **Следи за стартом**: Для медленно стартующих Java-приложений настройте
  `initialDelaySeconds` в пробах, чтобы избежать преждевременных рестартов.
* **Думай о памяти**: Учитывайте, что JVM потребляет больше памяти, чем просто
  размер кучи (`-Xmx`). Настройте JVM так, чтобы она не выходила за лимиты
  памяти контейнера. В новых версиях Java можно использовать
  `-XX:MaxRAMPercentage`.

Если какой-то из этапов вызовет затруднения, например, написание Dockerfile или
настройка переменных в GitLab, дайте знать! Я помогу разобраться детальнее.

## я не совсем понял этап, в котором образ из Gitlab попадает в Kubernetes

Понял, давайте разложу по шагам, как именно собранный Docker-образ из GitLab
попадает в работающие поды Kubernetes — здесь часто возникает путаница.

Вся цепочка выглядит так:

1. **GitLab CI собирает образ и пушит его в контейнерный регистри** (в вашем
   случае — GitLab Container Registry).
2. **В том же пайплайне GitLab выполняет `kubectl`-команду, которая говорит
   кластеру: «Обнови деплоймент, используя новый образ»**.
3. **Kubernetes сам идёт в регистри, скачивает образ и запускает новые
   контейнеры** — это и есть «попадание образа в кластер».

Разберу каждый пункт подробно, особенно то, что часто упускают.

---

### 🔄 Шаг 1. Сборка и пуш образа в GitLab Container Registry

У каждого GitLab-проекта есть свой бесплатный контейнерный регистри с адресом
вида:

```
registry.gitlab.com/ваш-неймспейс/имя-проекта
```

В CI-переменных уже определены:

- `$CI_REGISTRY` – адрес регистри (`registry.gitlab.com`)
- `$CI_REGISTRY_IMAGE` – полное имя образа для этого проекта
  (`registry.gitlab.com/your-namespace/your-project`)
- `$CI_REGISTRY_USER` и `$CI_REGISTRY_PASSWORD` – временные учётные данные для
  пуша (или можно использовать `$CI_JOB_TOKEN`)

В `.gitlab-ci.yml` на этапе сборки мы:

- логинимся в регистри (`docker login ...`)
- собираем образ с тегом, обычно короткий SHA коммита:
  `$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA`
- пушим его в регистри:

```yaml
build-image:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

После этого образ физически лежит в GitLab Container Registry и доступен по
тегу. Например:
`registry.gitlab.com/mycompany/backend:v1a2b3c4`

---

### 🎮 Шаг 2. GitLab отдаёт команду Kubernetes обновить образ

На этапе деплоя в том же `.gitlab-ci.yml` мы используем образ с `kubectl` и
применяем конфигурацию к нашему кластеру Kubernetes. При этом мы **не** копируем
образ напрямую в кластер — мы лишь передаём команду: «В деплойменте `my-app`
использовать новый образ `registry.gitlab.com/...:v1a2b3c4`».

Один из самых простых способов — команда `kubectl set image`:

```yaml
deploy:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    # Декодируем kubeconfig из CI-переменной, чтобы kubectl мог подключиться к кластеру
    - echo "$KUBE_CONFIG" | base64 -d > kubeconfig
    # Указываем деплойменту использовать новый образ
    - kubectl --kubeconfig=kubeconfig set image deployment/my-app my-app=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    # Ждём завершения обновления
    - kubectl --kubeconfig=kubeconfig rollout status deployment/my-app
  only:
    - main
```

Что здесь происходит:

- `kubectl set image deployment/my-app` обновляет поле
  `spec.template.spec.containers[].image` в указанном деплойменте.
- Kubernetes сравнивает текущий образ с новым и запускает rolling update:
  постепенно создаёт поды с новым образом, пока старые ещё работают.

Тот же результат можно получить, если хранить манифест деплоймента в репозитории
и вместо `set image` делать `kubectl apply -f deployment.yaml`, обновив в YAML
файле тег образа. Но `set image` удобнее для динамической подстановки.

---

### 🔐 Шаг 3. Как Kubernetes получает доступ к приватному образу

Образ лежит в **приватном** GitLab Container Registry. Kubernetes не сможет его
скачать, пока мы не дадим ему учётные данные. Для этого существует объект типа
`docker-registry Secret`.

Создаём секрет в том же неймспейсе, где развёрнуто приложение:

```bash
kubectl create secret docker-registry gitlab-regcred \
  --docker-server=registry.gitlab.com \
  --docker-username=<ваш_пользователь_или_токен> \
  --docker-password=<ваш_пароль_или_токен> \
  --namespace=your-namespace
```

(В production вместо личного пароля используют GitLab Deploy Token или Project
Access Token.)

Затем в Deployment манифесте ссылаемся на этот секрет через `imagePullSecrets`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      imagePullSecrets:
        - name: gitlab-regcred   # <-- секрет, который даёт доступ к образу
      containers:
        - name: my-app
          image: registry.gitlab.com/mycompany/backend:v1a2b3c4  # <-- образ из регистри
          ports:
            - containerPort: 8080
          ...
```

Теперь, когда Kubernetes по команде `kubectl set image` видит, что нужно
запустить контейнер с образом из `registry.gitlab.com`, он использует этот
секрет для авторизации и скачивает образ на ноду.

---

### 🌊 Итоговая картина

Всё вместе выглядит так:

1. **Разработчик пушит код** в ветку `main`.
2. **GitLab CI**:
    - Собирает Spring Boot JAR.
    - Собирает Docker-образ и пушит его в GitLab Container Registry с тегом
      `$CI_COMMIT_SHORT_SHA`.
    - С помощью `kubectl` даёт команду кластеру обновить деплоймент.
3. **Kubernetes master** принимает команду, создаёт новый ReplicaSet с новыми
   подами.
4. **Kubelet на ноде**, увидев что под должен использовать образ из приватного
   регистри, берёт данные из `imagePullSecrets`, логинится в
   `registry.gitlab.com` и **скачивает образ**.
5. Запускается новый контейнер с вашим приложением. Старые поды постепенно
   удаляются.

Таким образом, GitLab не «заливает» образ в Kubernetes, а только даёт указание,
какой образ из какого регистри взять. Сам же процесс загрузки образа выполняет
Kubernetes внутри кластера.

### 📁 Файл `.gitlab-ci.yml` — инструкция только для GitLab

Этот файл действительно лежит в корне вашего репозитория на GitLab, и его
понимает **только GitLab CI/CD**. Это «сценарий» для раннеров GitLab: какие
этапы запускать, в каких Docker-образах, какие команды выполнять.

### 🔗 Как команды доходят до Kubernetes

Внутри этого сценария вы на этапе деплоя запускаете инструмент `kubectl` (в
образе `bitnami/kubectl`, например). `kubectl` — это клиент, который обращается
к API вашего кластера Kubernetes и говорит: «обнови деплоймент таким образом,
чтобы там использовался новый образ».  
Для этого в GitLab CI нужны учётные данные от кластера (обычно их кладут в
переменную `KUBE_CONFIG` — закодированный файл `kubeconfig`). Благодаря им
`kubectl` может авторизоваться в Kubernetes.

### ⬇️ Кто скачивает образ

Когда Kubernetes получает от `kubectl` команду «используй образ
`registry.gitlab.com/...`», он **сам** идёт в GitLab Container Registry и
скачивает этот образ на свои ноды. Никакие инструкции для этого он из
`.gitlab-ci.yml` не извлекает — он руководствуется своей внутренней логикой и
манифестами (Deployment, StatefulSet и т.п.), которые были применены ранее.

### 🔐 Доступ к приватному регистри

Чтобы Kubernetes мог скачать образ из приватного GitLab Registry, вы должны
заранее создать в кластере специальный секрет типа `docker-registry` (например,
через `kubectl create secret docker-registry ...`) и указать его в манифесте
Deployment в поле `imagePullSecrets`. Именно этот секрет даёт кластеру право
доступа к вашему регистри.

### 💡 Итог: кто чем управляет

- **GitLab** (через `.gitlab-ci.yml` и раннеры) выполняет сборку, тесты и
  **отдаёт команды в Kubernetes** через `kubectl`.
- **Kubernetes** получает команду, сверяет её со своим текущим состоянием,
  скачивает нужный образ, запускает поды и следит за их статусом.

То есть цепочка: `.gitlab-ci.yml` → `kubectl` (из CI) → Kubernetes API → кластер
скачивает образ из регистри. Сам YAML-файл CI/CD не покидает GitLab и невидим
для Kubernetes.

Да, вы всё верно понимаете. Давайте разложим процесс с самого начала, чтобы он

### 1. 🚀 Пуш в ветку `main`

Вы делаете `git push` в репозиторий на GitLab. В корне вашего проекта, помимо
`Dockerfile` и кода, обязательно лежит файл `.gitlab-ci.yml`. Именно он
описывает, что делать GitLab-раннеру.

### 2. ⚙️ Запуск пайплайна

GitLab видит пуш в `main` и, следуя инструкциям из `.gitlab-ci.yml`, запускает
цепочку шагов (stages). Обычно это:

- **build** – сборка и юнит-тесты
- **package** – создание JAR-файла (если не сделано в build)
- **docker-build** – сборка Docker-образа
- **deploy** – обновление в Kubernetes

В реальном файле все эти шаги можно объединить для скорости, но логически они
разделены.

### 3. 🧪 Тесты проходят ДО сборки образа

В классическом подходе **тесты не запускаются внутри Docker-образа**, а
выполняются отдельно, на этапе `build` или `test`.  
Примерная последовательность:

1. Раннер GitLab берёт образ с Maven/Gradle (например,
   `maven:3.8.4-openjdk-17`).
2. Выполняется `mvn test` – прогоняются все модульные тесты. Если тесты падают,
   пайплайн останавливается, и дальше ничего не собирается.
3. Если тесты прошли, выполняется `mvn package -DskipTests` (тесты уже не нужны,
   они проверены), чтобы получить итоговый JAR-файл.
4. После этого запускается сборка Docker-образа, где в Dockerfile мы просто
   копируем готовый JAR в контейнер (как в примере с многоэтапной сборкой из
   первого ответа).

Таким образом, **в продакшн-образ попадает только протестированный код, без
тестовых зависимостей и без необходимости гонять тесты при каждом запуске
контейнера**.

### 4. 🐳 Сборка и публикация Docker-образа

После успешного прохождения тестов GitLab-раннер:

- Логинится в GitLab Container Registry (учётные данные уже есть в переменных
  CI).
- Выполняет `docker build -t registry.gitlab.com/...:v1a2b3c4 .`
- Выполняет `docker push ...` – теперь образ лежит в регистри и доступен по
  этому тегу.

Это и есть «образ, готовый для скачивания Kubernetes». Он остаётся в регистри и
ждёт.

### 5. ☸️ Kubernetes скачивает образ сам

На следующем этапе (`deploy`) GitLab с помощью `kubectl` говорит кластеру: «в
деплойменте `my-app` используй образ `registry.gitlab.com/...:v1a2b3c4`».  
Kubernetes, получив эту команду, проверяет свой `imagePullSecrets` и идёт в
GitLab Registry, скачивает образ на нужные ноды и запускает новые поды.

### 🔁 Резюме всей цепочки

Пуш кода → GitLab CI:

1. Сборка + тесты (mvn test) → получен JAR
2. Сборка Docker-образа (docker build из JAR) → образ в локальном кэше раннера
3. Пуш образа в GitLab Registry → образ доступен удалённо
4. Команда kubectl → «обнови деплоймент таким-то образом»
   → Kubernetes скачивает образ из Registry и запускает новые контейнеры

Тесты идут **до** создания Docker-образа, а сам образ после пуша становится
готовым для Kubernetes. Именно такой подход считается правильным и надёжным.

# Конфигурация

Вы затронули одну из самых дискуссионных тем на собеседованиях. Действительно,
подход к управлению конфигурациями сильно изменился с приходом Kubernetes.
Существует два основных способа выноса конфигураций, и на собеседовании очень
важно показать, что вы знаете оба, но понимаете, какой из них современнее.

## Подход 1. Классический (Spring-way) — Spring Cloud Config Server

Это тот самый подход, о котором вы читали (с отдельным Git-репозиторием).

* Как это работает: Создается отдельный микросервис — Spring Cloud Config
  Server. Он подключается к приватному Git-репозиторию, где лежат .properties
  или .yaml файлы для всех ваших сервисов. Когда payment-service стартует, он
  первым делом идет в Config Server и скачивает свои настройки.
* Как менять без перезагрузки: Если вы изменили конфигурацию в Git, вы можете
  отправить специальный HTTP-запрос (POST на эндпоинт /actuator/refresh) в ваш
  микросервис. Spring Boot перечитает бины, помеченные аннотацией @RefreshScope,
  и применит новые настройки (например, изменит уровень логирования с INFO на
  DEBUG или поменяет таймаут) без перезапуска самого приложения.
* Для кого подходит: Для систем, которые разворачиваются на обычных виртуальных
  машинах (без Kubernetes).

## Подход 2. Современный (Cloud-Native) — Kubernetes ConfigMaps & Secrets

Если ваши микросервисы уже живут в Kubernetes, разворачивать отдельный Spring
Cloud Config Server — это избыточность (антипаттерн). Kubernetes сам умеет
отлично управлять конфигурациями.

* Как это работает: Настройки хранятся в манифестах Kubernetes в виде двух
  сущностей:
* ConfigMap — для обычных настроек (адреса Кафки, порты).
    * Secret — для зашифрованных данных (пароли к БД, токены Keycloak).
    * Kubernetes «прокидывает» эти настройки внутрь пода вашего микросервиса
      либо как переменные окружения (Environment Variables), либо монтирует их
      как текстовые файлы в виртуальную папку.
* Как менять без перезагрузки: Если вы обновите ConfigMap в Kubernetes, файлы
  внутри пода обновятся автоматически в течение минуты. Чтобы Spring Boot
  заметил эти изменения без перезапуска, в экосистеме Spring есть библиотека
  Spring Cloud Kubernetes Config. Она следит за файлами конфигурации и сама
  инициирует контекстный рефреш приложения при их изменении.

## Подвох на собеседовании: Стоит ли менять конфигурацию на лету?

Интервьюер может спросить: "А хорошо ли менять настройки без перезагрузки в
продакшене?".
Правильный ответ Senior-разработчика: "Нет, для большинства критических настроек
это опасно".

* Почему это опасно: Если вы измените адрес базы данных на лету без перезапуска,
  и половина подов вашего сервиса переключится на новую базу, а вторая половина
  (из-за сбоя сети) останется на старой — вы получите рассинхронизацию системы
  (Split-Brain).
* Как делают в проде: На лету меняют только безопасные вещи (например, включают
  DEBUG-логи, чтобы отловить баг, или меняют текст баннера). Для изменения
  серьезных настроек (пароли, адреса) используют GitOps и стандартный Rolling
  Update в Kubernetes: K8s плавно, по одному, перезапускает поды с новыми
  конфигурациями, гарантируя zero-downtime (без остановки системы).

## Ответ на собеседовании (Итоговое резюме):

«Для выноса конфигураций в нашей архитектуре мы используем нативные инструменты
Kubernetes — ConfigMaps для обычных настроек и Secrets для конфиденциальных
данных. Это избавляет нас от необходимости поддерживать отдельный Spring Cloud
Config Server.
Для изменения конфигураций без перезапуска микросервисов мы используем
библиотеку Spring Cloud Kubernetes Config в связке со Spring Actuator. Бины,
настройки которых должны меняться на лету (например, уровни логирования), мы
помечаем аннотацией @RefreshScope. При обновлении ConfigMap в Kubernetes
библиотека фиксирует изменения файлов и обновляет контекст Spring Boot без
перезапуска пода. Однако для критических инфраструктурных настроек (адреса БД,
брокеров) мы предпочитаем безопасный перезапуск подов через стандартный Rolling
Update в Kubernetes, чтобы избежать рассинхронизации состояния кластера».

Рекомендуемая архитектура локальной "песочницы" строится по следующей схеме:

1. Как поднять Kubernetes локально

Устанавливать тяжелый "взрослый" Kubernetes на домашний ПК не нужно. Используйте
легковесные дистрибутивы, которые запускаются одной командой:
• Minikube или Kind — разворачивают полноценный кластер внутри Docker.

2. Где взять GitLab

Сам GitLab — очень тяжелая система (ему одному нужно от 4 до 8 ГБ RAM). Чтобы
пощадить ваш компьютер, не поднимайте сервер GitLab локально. [1]
(https://habr.com/ru/companies/slurm/articles/538370/)
• Хитрый ход: Зарегистрируйтесь на бесплатном облачном GitLab.com. Создайте там
приватный репозиторий для своего кода. Весь интерфейс и логика CI/CD будут
крутиться в облаке GitLab, не нагружая ваш компьютер. [1]
(https://reg.cloud/blog/rukovodstvo-po-ci-cd-v-gitlab-dlya-novichka/), [2]
(https://purpleschool.ru/knowledge-base/kubernetes/integration/gitlab-kubernetes)

3. Как связать облачный GitLab и ваш локальный Kubernetes

Вот здесь начинается магия CI/CD. Чтобы облачный GitLab мог давать команды
вашему домашнему Kubernetes, вам понадобятся два компонента:

1. GitLab Runner (Раннер): Это агент, который выполняет команды сборки (джобы).
   Вы устанавливаете GitLab Runner прямо внутрь вашего локального Kubernetes
   (через Helm-чарт). Он сам будет стучаться в облачный GitLab.com, забирать
   оттуда задачи на сборку/тесты и выполнять их прямо внутри вашего локального
   кластера. [1] (https://habr.com/ru/articles/1031452/), [2]
   (https://purpleschool.ru/knowledge-base/kubernetes/integration/gitlab-kubernetes), [3]
   (https://cloud.vk.ru/blog/ci-cd-v-kubernetes-paiplain-s-gitlab-ci-i-github-actions/)
2. GitLab Agent for Kubernetes: Современный инструмент от GitLab. Вы
   устанавливаете его в свой Minikube, и он безопасно связывает ваш локальный
   кластер с облачным репозиторием. После этого ваш CI/CD пайплайн получает
   прямой контекст kubectl для деплоя приложений. [1]
   (https://cloud.vk.ru/blog/ci-cd-v-kubernetes-paiplain-s-gitlab-ci-i-github-actions/), [2]
   (https://purpleschool.ru/knowledge-base/kubernetes/integration/gitlab-kubernetes)

Как будет выглядеть ваш первый учебный пайплайн (.gitlab-ci.yml):

Когда вы всё настроите, процесс будет выглядеть так: [1]
(https://purpleschool.ru/knowledge-base/kubernetes/integration/gitlab-kubernetes)

1. Вы пишете код простого микросервиса (например, на Node.js или Go) у себя в

   (https://purpleschool.ru/knowledge-base/kubernetes/integration/gitlab-kubernetes)
2. В файле .gitlab-ci.yml вы описываете три шага (Stages):
   • Build: Облачный GitLab дает команду вашему домашнему Раннеру собрать

   (https://purpleschool.ru/knowledge-base/kubernetes/integration/gitlab-kubernetes)

   (https://purpleschool.ru/knowledge-base/kubernetes/integration/gitlab-kubernetes)
   Подсказать, с какого компонента лучше начать установку — Docker Desktop,

   (https://purpleschool.ru/knowledge-base/kubernetes/integration/gitlab-kubernetes)

> контейнер в docker hub и контейнер локально?

Да, это отличный вопрос, который часто путает на старте. Здесь важно разделить
два понятия: образ (Image) и контейнер (Container).
• Образ — это «чертеж» или установочный файл (как .exe или .iso), в котором
зашит ваш микросервис и все его зависимости.
• Контейнер — это запущенный и работающий экземпляр этого образа в памяти
компьютера.
В вашей учебной схеме CI/CD они распределяются следующим образом:

1. В Docker Hub отправляется ОБРАЗ (Image)

Docker Hub — это облачное хранилище (Registry) для ваших «чертежей». Локальный
Kubernetes не может запустить ваш микросервис, если он лежит просто в виде
исходного кода у вас в папке. Коду нужно скомпилироваться в Docker-образ.
Когда ваш GitLab Runner выполняет шаг Build:

1. Он собирает Docker-образ вашего микросервиса.
2. Он отправляет (делает docker push) этот образ в Docker Hub.
   В Docker Hub этот образ просто лежит на полке в виде заархивированных слоев,
   он там не работает и не потребляет ресурсы процессора.

2. Локально запускается КОНТЕЙНЕР (Container)

Когда GitLab Runner переходит к шагу Deploy и говорит вашему локальному
Kubernetes (Minikube): «Разверни мне микросервис №1»:

1. Локальный Kubernetes смотрит в манифест deployment.yaml.
2. Видит там строчку image: your-docker-hub-username/my-microservice:latest.
3. Kubernetes идет в интернет, обращается к Docker Hub и скачивает (делает
   docker pull) этот образ к вам на компьютер.
4. Из скачанного образа Kubernetes локально разворачивает под (Pod), внутри
   которого запускается работающий контейнер.

Резюме: как это циркулирует по сети

• Ваш ПК (Код) ➡️ git push ➡️ GitLab (Облако)
• GitLab (Облако) ➡️ дает команду ➡️ Локальный Runner (Ваш ПК)
• Локальный Runner собирает образ ➡️ docker push ➡️ Docker Hub (Облако)
• Локальный Kubernetes (Ваш ПК) ➡️ docker pull из Docker Hub ➡️ запускает
контейнер локально в вашей оперативной памяти.
Таким образом, Docker Hub служит безопасным "мостом" или передаточным пунктом,
откуда ваш локальный Kubernetes всегда может забрать самую свежую версию вашего
приложения.
Хотите посмотреть пример простого deployment.yaml манифеста, чтобы увидеть, как
именно в Kubernetes указывается ссылка на образ из Docker Hub?

> а тестирование на каком этапе происходит?

Тестирование в правильном CI/CD пайплайне происходит на нескольких этапах, и под
разные виды тестов выделяются свои шаги (Stages) в файле .gitlab-ci.yml.
В вашей архитектуре из 6 микросервисов, Kafka и Kubernetes, процесс тестирования
делится на две большие фазы: до сборки Docker-образа и после его деплоя.
Вот как выглядит классическая цепочка:

Этап 1. Unit-тесты (До сборки образа)

Это самые быстрые тесты, которые проверяют чистоту кода (отдельные функции,
классы). На этом этапе базы данных, Kafka и Kubernetes еще не нужны.
• Когда: Сразу после того, как вы сделали git push, на самом первом шаге
пайплайна (stage: test).
• Как: GitLab Runner запускает команду тестирования вашего языка (например, npm
test, go test или mvn test) прямо в изолированном контейнере с исходным кодом.
• Результат: Если unit-тест упал, пайплайн тут же останавливается. Бракованный
код не идет на сборку Docker-образа, экономя время и ресурсы.

Этап 2. Компонентные и Интеграционные тесты (Во время сборки)

Здесь проверяется, как ваш микросервис работает в связке с базами данных или
внешними API. Вот тут на сцену может выйти WireMock, о котором мы говорили в
самом начале.
• Когда: Параллельно с unit-тестами или сразу после них.
• Как: Если микросервису для теста нужна БД или внешняя система, GitLab умеет
поднимать их "рядом" на время теста с помощью механизма GitLab Services.
Например, можно временно поднять контейнер с Postgres и контейнер с WireMock.
Микросервис прогоняет тесты, общаясь с ними, а после завершения тестов GitLab
эти временные контейнеры уничтожает.

Этап 3. Сборка и Деплой (Промежуточный шаг)

Если первые два этапа прошли успешно, пайплайн собирает Docker-образ, пушит его
в Docker Hub и деплоит в ваш локальный Kubernetes (Minikube), как мы разбирали в
прошлый раз. Приложение запускается.

Этап 4. Сквозные (E2E) и Нагрузочные тесты (После деплоя)

Это финальный и самый интересный этап для вашей системы. Теперь ваши 6
микросервисов уже запущены внутри Kubernetes и связаны через Kafka. Нужно
проверить систему целиком в условиях, приближенных к реальности.
• Когда: На шаге stage: post-deploy или stage: performance.
• Как: GitLab Runner запускает инструмент нагрузки (например, k6 или JMeter).
Этот инструмент начинает засыпать запросами ваш свежеразвернутый в Kubernetes
микросервис (или слать сообщения напрямую в Kafka).
• Что происходит: Во время этого теста вы как раз открываете Kiali и Grafana,
чтобы смотреть, справляются ли сервисы с потоком, не растет ли лаг в Kafka и как
чувствует себя база данных.

Как это выглядит в коде пайплайна (в общих чертах):

```yaml
stages:

  - test # 1. Запускаем Unit-тесты
  - build # 2. Собираем образ и пушим в Docker Hub (если тесты прошли)
  - deploy # 3. Разворачиваем контейнер в Minikube
  - load-test # 4. Бьем по развернутому сервису нагрузкой с помощью k6
#  Хотите посмотреть пример, как в GitLab CI настроить шаг с нагрузочным
#  тестированием через k6, чтобы он автоматически проверял ваш сервис после
#  деплоя?
```

# Дополнительно

С точки зрения Middle+ разработчика, выкладывание кода — это не «закинуть
JAR-ник на сервер», а полностью автоматизированный процесс CI/CD (Continuous
Integration / Continuous Delivery). Твоя задача на интервью — показать, что ты
понимает каждый этап «конвейера».
Вот как выглядит идеальный процесс (пайплайн) в твоем проекте:

1. Этап CI (Continuous Integration) — Сборка и проверка
   Все начинается с твоего git push в ветку develop или main.

    * Сборка: GitLab CI или GitHub Actions запускает сборку проекта
      (Maven/Gradle).
    * Тесты: Обязательно прогоняются Unit-тесты и Integration-тесты (с
      использованием Testcontainers, чтобы поднять реальную базу Postgres в
      Docker на время теста).
    * Качество кода: Проверка через SonarQube (ищем костыли, уязвимости и
      покрытие тестами меньше 80%).
    * Docker: Если всё ок, собирается Docker-образ и пушится в Docker Registry
      (хранилище образов) с уникальным тегом (например, хэшем коммита).

2. Этап CD (Continuous Deployment) — Доставка в K8s
   Тут в дело вступает ArgoCD или аналогичный инструмент, который следит за
   состоянием твоего Kubernetes.

    * Helm-чарты: Ты не правишь конфиги руками. У тебя есть шаблоны (Helm), куда
      подставляются нужные переменные для конкретной акции (домен, БД, лимиты
      CPU).
    * Rolling Update: Kubernetes не выключает старый сервис сразу. Он поднимает
      новый под, ждет, пока пройдет Readiness Probe (сервис скажет «я готов»), и
      только потом переключает трафик и гасит старый под. Это обеспечивает Zero
      Downtime (пользователь ничего не заметит).

3. Стратегии выкладывания (Твой «козырь»)
   На интервью спросят: «А если в коде баг, вы положите весь прод?». Твой ответ:

    * Canary Deployment: Мы выкатываем новую версию только на 5-10%
      пользователей. Смотрим в Grafana на ошибки. Если ошибок нет — раскатываем
      на всех.
    * Blue-Green Deployment: Рядом со старой версией (Blue) поднимается полная
      копия новой (Green). Трафик переключается мгновенно на уровне
      Ingress/Gateway. Если что-то пошло не так — мгновенный откат (Rollback).

4. Сопровождение после выкладки

    * Мониторинг: Первые 15 минут после деплоя ты смотришь в дашборд. Если Error
      Rate вырос или Consumer Lag в Kafka пополз вверх — нажимаешь кнопку
      Rollback в ArgoCD.
    * Логи: Проверяешь в Loki по свежим логам, нет ли там новых
      NullPointerException.

Как ответить на интервью (кратко):

      «Процесс выкатки у нас полностью автоматизирован через CI/CD пайплайн. 
      После успешного прохождения тестов и проверок в SonarQube, образ 
      собирается в Docker и деплоится в Kubernetes с помощью Helm и ArgoCD. 
      Мы используем стратегию Rolling Update с обязательными Liveness/Readiness 
      пробами, что гарантирует отсутствие простоя. После деплоя я всегда 
      контролирую бизнес-метрики в Grafana, чтобы в случае аномалий мгновенно 
      провести откат к стабильной версии».

Важный нюанс: Упомяни, что миграции БД через Liquibase накатятся автоматически
при старте нового пода, так что база всегда соответствует коду.

> Хочешь разобрать, как именно Liquibase понимает, что нужно накатить миграцию
> именно в ПРОД-базу, а не сломать соседнюю акцию?

да

Чтобы Liquibase не превратил твою мультиарендную архитектуру (много акций —
много баз) в хаос, используется принцип «Один сервис — одна точка входа в БД».
Вот как это работает технически, чтобы на интервью ты ответил как профи:

1. Как Liquibase понимает, куда идти?
   Liquibase — это библиотека внутри твоего Spring Boot приложения. Она не живет
   сама по себе.

    * Когда Kubernetes запускает новый под user-service-promo-lays, он передает
      ему Environment Variables (переменные окружения): SPRING_DATASOURCE_URL,
      USER, PASSWORD.
    * При старте Spring поднимает контекст, инициализирует бин DataSource именно
      с этим URL (база для Lays).
    * Затем просыпается Liquibase, берет это же соединение и проверяет в этой
      конкретной базе таблицу databasechangelog.

2. Как не накатить «лишнего»? (Contexts и Labels)
   Иногда тебе нужно, чтобы одна миграция прошла в тестовой базе, а в проде —
   нет (например, тестовые данные).

    * Contexts: В файле миграции (changeset) ты пишешь context: prod или
      context: test.
    * При запуске сервиса в K8s в конфигах прописано
      spring.liquibase.contexts=prod. Liquibase выполнит только те скрипты, где
      помечено prod или где контекст не указан вовсе.

3. Как это работает в твоем CI/CD (Процесс):

    1. Разработчик: Добавил новую колонку в таблицу чеков, создал файл
       db.changelog-1.1.xml, закинул в Git.
    2. CI/CD (GitLab): Собрал Docker-образ.
    3. ArgoCD: Видит, что пора обновить user-service-promo-lays.
    4. Runtime: Под запускается, соединяется с базой Lays. Liquibase видит: «О,
       в таблице логов нет записи про версию 1.1!».
    5. Action: Выполняет SQL, записывает в лог базы Lays, что версия 1.1 успешно
       применена.
    6. Результат: Все остальные 5 акций (Pepsi, Mars и т.д.) об этом не знают,
       пока их поды тоже не перезапустятся с новым кодом.

Как ответить на интервью:

          «Для управления миграциями в условиях мультиарендности мы использовали Liquibase, встроенный в жизненный цикл Spring Boot.
          Поскольку каждый экземпляр сервиса получал настройки своей БД через Environment Variables в Kubernetes, Liquibase автоматически применял изменения именно к той базе, к которой подключен инстанс.
          Мы версионировали все изменения схемы в Git, а для разделения тестовых и продуктовых скриптов использовали Liquibase Contexts. Это позволило нам безопасно и атомарно обновлять схемы десятков изолированных баз данных одновременно с деплоем нового кода».

### ArgoCD

Если Helm — это способ «упаковать» приложение, то ArgoCD — это инструмент,
который автоматически доставляет его в Kubernetes и следит, чтобы оно там
работало именно так, как описано в Git.
Это ключевой инструмент концепции GitOps.
Как это работает (на примере вашего процесса)

1. Git как «Источник истины»: Все ваши Helm-чарты и values.yaml для 6+ сервисов
   лежат в Git-репозитории.
2. Синхронизация: ArgoCD постоянно сравнивает то, что написано в Git, с тем, что
   реально запущено в кластере K8s.
3. Авто-деплой: Как только вы пушите изменения в values.yaml (например, меняете
   версию образа после завершения спринта), ArgoCD видит расхождение (OutOfSync)
   и само применяет изменения в кластер.

Почему это круто для ваших 2-3 недельных спринтов:

    * Визуализация (UI): У ArgoCD есть шикарный веб-интерфейс. Вы видите дерево всех объектов вашего Spring Boot приложения (поды, сервисы, ингрессы) и их состояние (зеленые — работают, красные — ошибка). Это очень удобно показывать на демо заказчику.
    * Запрет «ручных» правок: Если кто-то из команды решит руками поменять что-то в K8s через консоль, ArgoCD увидит это и мгновенно вернет настройки из Git. Это гарантирует стабильность продакшена.
    * Легкий откат: Если новый релиз сломал систему, вы просто делаете git revert в своем репозитории, и ArgoCD тут же откатывает приложение на рабочую версию.
    * Управление 6+ сервисами: Вы создаете в ArgoCD одну «папку» (Application Set), и она сама следит за деплоем всех шести микросервисов одновременно.

Сравнение с обычным CI/CD (например, Jenkins/GitLab CI):

    * Обычный CI: «Пушит» изменения в кластер (Push-модель). Если кластер был недоступен в момент деплоя — деплой упал.
    * ArgoCD: Сам «тянет» изменения из Git (Pull-модель). Он будет пытаться применить конфиг до тех пор, пока кластер не примет его.

Итог: В связке Spring Boot + Helm + ArgoCD вы получаете полностью
автоматизированный конвейер. Разработчик просто пишет код и пушит в Git, а через
пару минут приложение уже обновлено в K8s.
Хотите узнать, как связать ArgoCD с вашим Gitlab/Github, чтобы автоматизировать
релизы?

да

Для связи ArgoCD с вашим Git-репозиторием (GitLab/GitHub) используется концепция
App-of-Apps или просто создание объекта Application.
Вот пошаговый план, как это настроить для ваших 6+ микросервисов:

1. Подготовка репозитория (Git)
   Обычно создают отдельный репозиторий (например, my-app-infrastructure), где
   лежат только настройки деплоя.

    * Структура: Папки с Helm-чартами для каждого сервиса
      (/charts/order-service, /charts/payment-service и т.д.) и файлы
      values-prod.yaml для них.

2. Регистрация репозитория в ArgoCD
   Чтобы ArgoCD мог «читать» ваш код, нужно добавить его в настройках:

    1. Заходите в интерфейс ArgoCD -> Settings -> Repositories.
    2. Нажимаете Connect Repo и вставляете URL (потребуется SSH-ключ или
       Personal Access Token от GitLab/GitHub).

3. Создание "Application" (Связующее звено)
   Вы создаете манифест (YAML), который говорит ArgoCD: «Смотри в эту папку в
   Git и деплой это в этот кластер».
   Пример манифеста для одного из ваших сервисов:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: order-service-prod
  namespace: argocd
  spec:
  project: default
  source:
    repoURL: 'https://github.com'
    targetRevision: HEAD          # Какую ветку мониторить (например, main)
    path: charts/order-service    # Путь к Helm-чарту в репозитории
    helm:
      valueFiles:
        - values-prod.yaml        # Файл с настройками для продакшена
  destination:
    server: 'https://kubernetes.default.svc' # Куда деплоить (локальный кластер)
    namespace: prod-apps          # В какой неймспейс положить Spring Boot приложение
  syncPolicy:
    automated: # Включаем магию авто-деплоя
      prune: true                 # Удалять лишнее, если оно пропало из Git
      selfHeal: true              # Исправлять ручные правки в K8s

```

4. Роль CI-пайплайна (GitLab CI / GitHub Actions)
   В этой схеме ваш обычный CI (который собирает Java-код) делает только одну
   вещь:

    1. Собирает .jar через Maven/Gradle.
    2. Делает Docker Image.
    3. Пушит новую версию тега в ваш репозиторий с конфигами (изменяет tag:
       v1.0.1 на tag: v1.0.2 в values.yaml).

Что происходит дальше:

1. ArgoCD видит коммит в Git (изменение тега).
2. Статус в UI меняется на OutOfSync (желтый).
3. Через пару секунд ArgoCD делает helm upgrade в K8s.
4. Вы видите в браузере, как старые поды со Spring Boot гаснут, а новые —
   загораются зеленым.



## Деплой приложения в продакшн

Обычно процесс (CI/CD пайплайн) выглядит так:

1. Подготовка артефакта (Docker)
   Spring Boot приложение упаковывается в Docker-образ. Внутри образа находится
   JRE и ваш .jar файл. Совет: Используйте многоэтапную сборку (Multi-stage
   build) в Dockerfile, чтобы образ весил меньше (только JRE, без Maven/Gradle).

2. Описание инфраструктуры (Manifests / Helm)
   Чтобы K8s понял, как запустить ваше приложение, создаются YAML-файлы:
    - Deployment: описывает количество копий приложения (Replicas), лимиты по
      памяти/CPU и путь к Docker-образу.
    - Service: дает приложению внутренний IP-адрес для связи с другими
      сервисами.
    - Ingress: открывает доступ к приложению из внешнего мира (интернет).
    - ConfigMap/Secrets: хранит настройки (БД, ключи), чтобы не «зашивать» их в
      код.

3. Сам процесс деплоя (CI/CD)
   В современных командах это делает робот (GitLab CI, GitHub Actions, Jenkins):
    - Build: компиляция кода и прогон тестов.
    - Push: отправка Docker-образа в хранилище (Docker Registry).
    - Apply: команда kubectl apply -f manifests/ или запуск Helm-чарта, который
      обновляет приложение в кластере K8s.

4. Особенности для Spring Boot в K8s
    - Liveness/Readiness Probes: K8s должен знать, живо ли приложение. Для этого
      в Spring Boot есть модуль Actuator (эндпоинты /actuator/health/liveness и
      /actuator/health/readiness).
    - Graceful Shutdown: Spring Boot нужно время (пару секунд), чтобы
      дообработать текущие запросы перед тем, как K8s его «прибьет». Это
      настраивается в application.properties.
    - External Database: База данных (PostgreSQL/MySQL) обычно живет либо вне
      K8s (Managed DB), либо в отдельном StatefulSet.

Как это помогает вашему Agile-процессу?
С таким подходом «предрелиз», который вы показываете заказчику каждые 2–3
недели, деплоится одной кнопкой (или автоматически при пуше в ветку main).
Заказчик получает ссылку и сразу видит результат.

## Gitlab

В вашей схеме GitLab — это «дирижер», который связывает написанный код на Java с
работающим приложением в Kubernetes. Он выполняет три ключевые роли:

1. CI (Continuous Integration) — Сборка и проверка
   Когда вы пушите код в GitLab, запускается конвейер (Pipeline), описанный в
   файле .gitlab-ci.yml:

    * Сборка: GitLab запускает Maven/Gradle внутри Docker-контейнера,
      компилирует ваш Spring Boot проект и прогоняет Unit-тесты.
    * Проверка качества: Можно подключить SonarQube, чтобы он проверил код на
      наличие багов или уязвимостей перед деплоем.
    * Создание образа: GitLab собирает Docker-образ вашего приложения и пушит
      его в свой встроенный Container Registry (хранилище образов).

2. CD (Continuous Delivery) — Доставка
   Здесь есть два пути, и выбор зависит от того, используете ли вы ArgoCD:

    * Вариант А (GitOps с ArgoCD): GitLab сам не лезет в Kubernetes. Он просто
      создает новый Docker-образ и отдельным шагом правит номер версии (tag) в
      вашем репозитории с Helm-чартами. Дальше ArgoCD видит это изменение в
      GitLab и обновляет поды в K8s.
    * Вариант Б (Push-модель): GitLab сам вызывает команду helm upgrade или
      kubectl apply, используя секретные ключи доступа к вашему кластеру, и
      «проталкивает» обновление.

3. Хранение конфигурации (Infrastructure as Code)
   В GitLab вы храните не только Java-код, но и:

    * Dockerfile: инструкция, как упаковать Spring Boot.
    * Helm-чарты: описание ресурсов K8s (память, CPU, количество реплик).
    * Переменные окружения: Пароли от БД или URL сервисов (через Settings ->
      CI/CD -> Variables), которые GitLab подставит при деплое.

4. Роль в Agile (Scrum)

    * Code Review: Перед тем как попасть в прод, код проходит через Merge
      Requests. Это точка контроля, где команда обсуждает решение.
    * Issue Tracking: Вы можете связывать задачи (запросы заказчика) с

## Запуск и корректировка пайплайна сборки и деплоя в Gitlab CI

На языке интервьюера это означает, что вы понимаете, как код превращается в
работающий продукт, и можете починить этот процесс, если он сломается.
Вот как это расшифровывается применительно к вашему опыту со Spring Boot и K8s:

1. Запускать (Run)
   Это базовая операционка. Вы понимаете, когда и как стартует сборка:

    * Автоматически: при каждом git push в ветку (например, develop или
      feature/*).
    * Вручную (Manual): умеете зайти в интерфейс GitLab, нажать кнопку «Run
      Pipeline» или подтвердить этап деплоя на продакшн (кнопка «Play» на стадии
      deploy).
    * Retry: умеете перезапустить упавшую стадию (например, если тест моргнул
      или сеть до K8s отвалилась).

2. Корректировать (Adjust/Fix)
   Это уже инженерный навык. Вы умеете лезть в файл .gitlab-ci.yml и менять
   логику:

    * Версии: обновить версию Docker-образа (например, с Java 11 на 17) или
      версию Helm-чарта.
    * Переменные (Environment Variables): добавить новый секрет (пароль к БД) в
      настройках GitLab и прокинуть его в пайплайн, чтобы Spring Boot его
      подхватил.
    * Скрипты: поправить bash-команды внутри пайплайна (например, изменить
      параметры сборки Maven: mvn clean package -DskipTests).
    * Условия (Only/Except/Rules): настроить, чтобы деплой в Kubernetes
      происходил только после того, как прошли все тесты.

Как это преподнести на интервью (пример):

      «В моих проектах я не просто писал код, но и отвечал за то, чтобы он 
      доехал до K8s. Я корректировал пайплайны: настраивал проброс переменных 
      окружения для разных сред (Dev/Prod), менял скрипты сборки в 
      .gitlab-ci.yml, если проект требовал новых зависимостей, и следил за тем,
      чтобы образы правильно тегировались и пушились в Registry».

Почему это важно для Agile (2-3 недели):
Если пайплайн «сломан», разработка встает. Умение быстро поправить конфиг и
запустить деплой заново — это критический навык, чтобы успеть показать предрелиз
заказчику в срок.

## Настройка пайплайна и .gitlab-ci.yml

Для интервью по GitLab CI вам нужно знать эти 4 секции. Они составляют костяк
любого .gitlab-ci.yml для Java-проекта. Если вы их назовете и объясните, как они
работают, этого будет достаточно, чтобы подтвердить ваш опыт.

1. stages (Этапы)
   Это «оглавление» вашего пайплайна. Здесь вы определяете последовательность
   шагов.

    * Что говорить: «Я настраивал этапы: сначала сборка (build), потом
      тестирование (test), затем упаковка в Docker и финальный деплой (deploy) в
      Kubernetes».

    ```yaml
    stages:
      - build
      - test
      - push
      - deploy
    ```

2. variables (Переменные)
   Это те самые настройки окружения, о которых вы говорили.

    * Что говорить: «В этой секции я определял общие параметры: путь к
      Docker-реестру, название образа и специфические настройки для Spring Boot
      (например, активный профиль spring.profiles.active). Секретные данные
      (пароли к БД) я настраивал в интерфейсе GitLab как Masked Variables, чтобы
      они не светились в логах».

3. script (Сердце каждой задачи)
   Это набор bash-команд, которые выполняются внутри контейнера (например, в
   образе с Maven).

    * Что говорить: «В блоке script я прописывал команды сборки. Для Java это
      обычно mvn clean package. Для деплоя в K8s я использовал команды helm
      upgrade или kubectl apply, подставляя нужные конфиги».

    ```yaml
    build_job:
      stage: build
      image: maven:3.8-openjdk-17
      script:
        - mvn clean package -DskipTests
      artifacts:
        paths:
          - target/*.jar  # Передаем собранный jar на следующий этап
    ```

4. rules или only/except (Условия запуска)
   Это логика того, когда запускать деплой.

    * Что говорить: «Я корректировал правила запуска. Например, автоматический
      деплой шел только при пуше в ветку develop (для стейджинга), а на прод —
      только вручную (when: manual) или по созданию тега версии (v1.0.0)».
    ```yaml
    deploy_prod:
      stage: deploy
      script:
        - echo "Deploying to K8s..."
      rules:
        - if: $CI_COMMIT_TAG  # Запуск только если создан тег
          when: manual        # И только после нажатия кнопки в UI
    ```

Как это «продать» на интервью:
Когда вас спросят: «Как вы корректировали пайплайн?», вы отвечаете:

      «Например, когда нам нужно было добавить новый микросервис, я копировал 
      существующий .gitlab-ci.yml, корректировал секцию variables под новые 
      эндпоинты, менял script сборки и настраивал rules, чтобы деплой в K8s 
      срабатывал только после успешного прохождения тестов в пайплайне».

Это звучит как ответ человека, который реально «трогал» процесс руками.

### Самый простой пример .gitlab-ci.yml для Spring Boot проекта, чтобы ты просто

пробежал по нему глазами?
-

Вот самый простой и понятный пример файла .gitlab-ci.yml. Представь, что это
«инструкция», по которой GitLab двигает твой код на Java до сервера в
Kubernetes.
Как это выглядит (разбор по шагам)

```yaml

# 1. Список этапов, которые пройдут один за другим
stages:
  - build   # Сборка .jar
  - test    # Запуск Unit-тестов
  - deploy  # Отправка в K8s
# 2. Этап сборки (используем образ с Maven и Java)
build_job:
  stage: build
  image: maven:3.8-openjdk-17
  script:
    - mvn clean package -DskipTests # Просто собираем файл
  artifacts:
    paths:
      - target/*.jar # Сохраняем результат, чтобы передать дальше
# 3. Этап тестирования
test_job:
  stage: test
  image: maven:3.8-openjdk-17
  script:
    - mvn test # Запускаем тесты, которые ты написал в проекте
# 4. Этап деплоя (упрощенный пример)
deploy_job:
  stage: deploy
  image: bitnami/kubectl:latest # Образ с утилитой для управления K8s
  script:
    # Здесь мы говорим Kubernetes: "Обнови приложение, используя переменные из GitLab"
    - kubectl set image deployment/my-app-deployment my-app-container=$CI_REGISTRY_IMAGE:$CI_COMMIT_REF_SLUG
  variables:
    # Пример переменной, которую ты можешь "корректировать" в интерфейсе GitLab
    DB_URL: $PROD_DATABASE_URL
  rules:
    - if: $CI_COMMIT_BRANCH == "main" # Деплоим только из главной ветки

```

Что тебе важно запомнить для интервью:

1. artifacts: Если в первой задаче (build) мы собрали .jar, то без этой секции
   он удалится сразу после завершения шага. artifacts — это «посылка», которая
   летит во второй шаг.
2. variables: Если завтра база данных переедет на другой адрес, тебе не нужно
   менять код Java. Ты просто заходишь в Settings -> CI/CD -> Variables в GitLab
   и меняешь значение там. Это и есть та самая «корректировка пайплайна», о
   которой тебя спрашивают.
3. image: Каждая задача запускается в своем «мини-компьютере» (контейнере). Для
   сборки нужен Maven, для деплоя — kubectl.

Как об этом сказать:

      «Я понимаю структуру .gitlab-ci.yml: как разделять сборку и деплой по 
      стадиям, как передавать артефакты (бинарные файлы) между шагами и как 
      использовать переменные окружения, чтобы приложение в K8s получало 
      правильные доступы к базе данных».

### Хочешь, подберем пару вопросов с подвохом, которые могут задать по этой

теме, чтобы ты не растерялся?
-

да

Лови 3 типичных вопроса «с подвохом», которые обожают задавать на интервью
Java-разработчикам, чтобы проверить, реально ли они касались CI/CD и K8s.

1. «Где в Spring Boot приложении хранятся пароли от БД при деплое в Kubernetes?»

    * Подвох: Если скажешь «в application.properties», это провал по
      безопасности.
    * Правильный ответ: «Пароли хранятся в Kubernetes Secrets. В GitLab CI мы
      настраиваем переменную (например, DB_PASSWORD), а при деплое она либо
      пробрасывается как переменная окружения (Environment Variable) в
      контейнер, либо монтируется как файл. Spring Boot подхватывает её
      автоматически через property expansion».

2. «Что произойдет, если Unit-тесты упадут на этапе test в пайплайне?»

    * Подвох: Проверка понимания цепочки (Flow).
    * Правильный ответ: «Пайплайн остановится. Этап deploy не запустится, и
      сломанный код не попадет в кластер. Это и есть главная задача CI — не дать
      багам доехать до продакшена. Я увижу красный значок в GitLab, изучу логи
      теста и исправлю код».

3. «Как Kubernetes узнает, что ваш Spring Boot сервис успешно запустился и готов
   принимать трафик?»

    * Подвох: Проверка знаний о связи Spring Boot Actuator и K8s.
    * Правильный ответ: «Для этого используются Readiness и Liveness probes. В
      Spring Boot мы включаем модуль Actuator, который дает эндпоинты
      /actuator/health/readiness. В манифесте деплоя (который мы корректируем в
      пайплайне) мы указываем K8s проверять этот адрес. Пока приложение не
      ответит 200 OK, трафик на него не пойдет».

4. (Бонус) «Зачем нам Docker, если мы можем просто запустить .jar на сервере?»

    * Подвох: Проверка понимания контейнеризации.
    * Правильный ответ: «Docker гарантирует, что приложение запустится в
      одинаковой среде и на моем компьютере, и в пайплайне GitLab, и в кластере
      Kubernetes. Нам не нужно ставить Java или нужные библиотеки на сам
      сервер — всё уже упаковано внутрь образа».

Совет для интервью: Если тебя спросят что-то совсем сложное (например, про
настройку сети в K8s), не бойся сказать: «Этим у нас занимались DevOps-инженеры,
я как разработчик фокусировался на конфигурации самого приложения и настройке
переменных в GitLab». Это звучит честно и профессионально.

### магия .gitlab.ci.yaml и Gitlab:

«Магия» прояснится, если познакомиться с главным героем — GitLab Runner.
Инструкции из .gitlab-ci.yml выполняет не сам сайт GitLab, а отдельная
программка-исполнитель (Runner), которая обычно установлена на каком-то сервере
(или прямо внутри вашего Kubernetes-кластера).
Как это происходит по шагам:

1. Триггер: Вы делаете git push. Сервер GitLab видит файл .gitlab-ci.yml и
   понимает: «Ага, нужно запустить работу».
2. Поиск исполнителя: GitLab ищет свободный Runner. Это как «прораб», который
   ждет заказов.
3. Создание окружения:
    * Runner видит в инструкции image: maven:3.8.
    * Он идет в интернет (Docker Hub), скачивает этот образ и запускает из него
      временный контейнер (чистую «виртуальную» среду с установленной Java и
      Maven).
4. Выполнение:
    * Runner скачивает ваш код внутрь этого контейнера.
    * По очереди запускает команды из секции script (например, mvn clean
      package).
5. Завершение:
    * Если команды выполнились успешно (вернули код 0), Runner сообщает GitLab:
      «Всё ок, стадия пройдена».
    * Если команда упала с ошибкой, Runner говорит: «Всё сломалось», и пайплайн
      останавливается.
    * Контейнер удаляется, чтобы не занимать место.

Где именно физически это работает?
В крупных компаниях это обычно:

* Спецсерверы: Отдельные мощные машины, где крутятся только раннеры.
* Сам Kubernetes: Раннер может сам создавать временные «поды» в K8s специально
  под вашу сборку, а после сборки их уничтожать.

Как это представить на интервью:

      «Инструкции из YAML-файла выполняются GitLab Раннерами. Это изолированные
      среды (Docker-контейнеры), которые динамически создаются под каждую 
      задачу. Это гарантирует, что сборка всегда идет в "чистых" условиях и не 
      зависит от того, что установлено на моем личном компьютере».

Простыми словами: Представьте, что GitLab — это официант (принимает заказ в виде
YAML), а Runner — это повар на кухне (выполняет инструкции и выдает результат).
Теперь стало понятнее, что Runner — это тот самый «чернорабочий», который на
самом деле запускает ваш Maven и Docker?

> Получается, скачивается контейнер, в котором проходят тесты приложения и его
> сборка? А потом это приложение отправляется в кубер?

Именно так! Ты только что описал классический CI/CD конвейер. Чтобы на интервью
это звучало максимально солидно, давай разделим этот процесс на две четкие фазы:
Фаза 1: Сборка и упаковка (CI — Continuous Integration)

1. Контейнер-сборщик: Раннер скачивает временный контейнер (например, с Maven).
2. Сборка: Внутри этого контейнера запускается mvn clean package. На выходе
   получается твой .jar файл.
3. Тесты: Прямо там же запускаются Unit-тесты. Если они падают — всё
   останавливается.
4. Создание образа (Docker): Этот .jar упаковывается в новый, «чистый»
   Docker-образ (где есть только JRE и твой код). Этот образ отправляется в
   хранилище (Registry).

* Зачем? Чтобы этот образ можно было запустить где угодно.

Фаза 2: Доставка в кластер (CD — Continuous Deployment)

1. Контейнер-деплоер: Раннер запускает другой временный контейнер (например, с
   утилитой kubectl или helm).
2. Команда на деплой: Этот контейнер «стучится» в твой Kubernetes и говорит:
   «Эй, обнови сервис my-app, возьми новый образ с тегом v1.2, который мы только
   что собрали».
3. Магия K8s: Kubernetes сам скачивает твой новый образ из хранилища, запускает
   новые поды (контейнеры с приложением) и, если они успешно стартовали, гасит
   старые.

Как это «продать» на интервью:
Когда тебя спросят про роль GitLab и K8s, отвечай так:

      «Процесс выглядит как эстафета: GitLab Runner в изолированном контейнере
      собирает артефакт и прогоняет тесты. Затем он упаковывает приложение в 
      Docker-образ и дает команду Kubernetes обновить текущую версию. Таким 
      образом, в K8s всегда крутится актуальный и протестированный код».

Главный нюанс (для продвинутых):
Важно понимать: приложение не живет в том контейнере, где оно собиралось.
Контейнер для сборки (с Maven) — это просто «верстак», который мы выбрасываем
после работы. А в Kubernetes уезжает уже готовый, легкий образ «только для
запуска».
