При каком условии в Java 8 связный список в бакете HashMap преобразуется в красно-черное дерево (Treeify)?
[] 
   
   1. Когда количество элементов в бакете превышает 8, а общая емкость таблицы (capacity) составляет не менее 64.
   Правильно! Одного лишь превышения порога в 8 элементов в бакете недостаточно; если общий размер массива мал (меньше 64), то вместо превращения в дерево HashMap выполнит увеличение размера (resize) всей таблицы.

   Неверно. Дерево создается локально в конкретном бакете, и для этого требуется как минимум 8 элементов в нем, плюс размер массива от 64.

[]

   Неверно. Интерфейс InitializingBean отрабатывает после инжектирования зависимостей, но @PostConstruct обрабатывается на более раннем этапе через BeanPostProcessor.

   Правильно! Сначала отрабатывает аннотация @PostConstruct (через CommonAnnotationBeanPostProcessor), затем программный метод интерфейса InitializingBean, и в конце — сконфигурированный пользовательский init-method.

   Неверно. Кастомный init-method вызывается последним из этих трех механизмов инициализации.
   4. @PostConstruct -> кастомный init-method -> InitializingBean.afterPropertiesSet()
   Неверно. InitializingBean вызывается раньше, чем XML- или конфиг-ориентированный init-method.

Что гарантирует ключевое слово volatile в Java Memory Model (JMM)?
[] 
   
   1. Полную потокобезопасность и атомарность любых операций с переменной, включая сложные (например, инкремент i++).
   Неверно. volatile не делает составные операции атомарными. Для инкремента требуются AtomicInteger или блокировки.
   2. Принудительное хранение переменной исключительно в кэше процессора первого уровня (L1) для минимизации задержек.
   Неверно. volatile заставляет читать и писать значение напрямую в основную память (Main Memory), минуя локальные кэши потоков, а не фиксирует её в L1.
   3. Видимость изменений переменной для всех потоков и запрет переупорядочивания инструкций (happens-before), но не атомарность.
   Правильно! volatile гарантирует отсутствие кеширования значения в локальной памяти потока (Visibility) и барьеры памяти, предотвращающие реордеринг, но не гарантирует атомарность операций чтения-модификации-записи.
   4. Автоматическую блокировку других потоков (mutex-like) на время выполнения чтения или записи переменной.
   Неверно. volatile является безнадежным (lock-free) механизмом и не использует мониторы или блокировки потоков.
   
Подсказка.
Разделите понятия «видимость данных в памяти» и «атомарность неделимых шагов». Подумайте, можно ли безопасно инкрементировать volatile int из нескольких потоков без гонки (race condition).
Какой низкоуровневый механизм используется в ConcurrentHashMap (начиная с Java 8) для вставки нового узла в пустой бакет без захвата тяжелого synchronized?
[] 
   
   1. Спин-лок (Spin-lock) на основе атомарного счетчика размера карты.
   Неверно. Для инициализации и вставки в пустой бакет не используются спин-локи счетчиков.
   2. Прямая запись без какой-либо синхронизации, поскольку сам массив бакетов объявлен как volatile.
   Неверно. Даже при наличии volatile-ссылок на массив, для предотвращения гонки при записи элементов в ячейку необходимы атомарные примитивы.
   3. Использование локального буфера ThreadLocal для каждого пишущего потока.
   Неверно. Архитектура ConcurrentHashMap не опирается на ThreadLocal для структуры хранения элементов.
   4. CAS (Compare-And-Swap) операция с использованием sun.misc.Unsafe / VarHandle.
   Правильно! Вставка в пустую ячейку (head бакета) в Java 8+ ConcurrentHashMap делается через атомарную CAS-операцию (casTabAt), а если бакет уже занят — происходит точечный захват synchronized на самом первом узле цепочки.

Что такое Escape Analysis (анализ бегства) в контексте оптимизации JVM с помощью JIT-компилятора?
[] 
   
   1. Механизм автоматического завершения зависших потоков, которые «убежали» из-под контроля пула.
   Неверно. Это оптимизация памяти и аллокации объектов, а не управление потоками.
   2. Анализ области жизни объекта: если объект не покидает пределы метода, JVM может выделить его на стеке (Stack Allocation) или заменить скалярами.
   Правильно! Если JIT-компилятор видит, что ссылка на объект не «убегает» (escapes) за рамки текущего метода (не возвращается и не записывается в глобальное поле), он может выделить память под объект прямо на стеке (Stack Allocation) или разложить его поля на локальные переменные (Scalar Replacement), избегая сборщика мусора.
   3. Системный перенос долгоживущих объектов из Eden-зоны сразу в Tenured поколение кучи.
   Неверно. Это относится к эвристике возрастных порогов (tenuring threshold) сборщика мусора, а не к Escape Analysis.
   4. Оптимизация синхронизованных блоков, позволяющая потоку «сбежать» из ожидания монитора (Lock Coarsening/Elision).
   Неверно. Хотя устранение блокировок (Lock Elision) тесно связано с результатами Escape Analysis (если объект локален, то синхронизация на нем не нужна), сам термин описывает анализ областей видимости объекта.
   
Подсказка.
Слово «escape» переводится как «побег». Куда может «убежать» созданный объект, чтобы его нельзя было выделить просто на стеке вызовов метода?
Почему аннотация @Transactional, размещенная на методе B(), вызванном внутри того же класса из метода A() (this.B()), не порождает новую транзакцию (проблема самовызова)?
[]

   Неверно. Spring успешно создает прокси и для классов (CGLIB), даже если нет явного интерфейса.
   3. Вызов идет напрямую на целевой объект (this), минуя динамический прокси-объект Spring, который перехватывает транзакции.

В каком случае ThreadPoolExecutor выбрасывает исключение RejectedExecutionException при стандартной стратегии отклонения AbortPolicy?
[] 
   
   1. Как только количество активных потоков превысит значение corePoolSize.
   Неверно. При превышении corePoolSize новые задачи отправляются в очередь (workQueue), а не отклоняются.
   2. Если выполнение задачи внутри пула привело к неперехваченному исключению (RuntimeException).
   Неверно. Исключения в задачах перехватываются потоком-исполнителем и могут быть получены через Future.get(), но пул при этом не отклоняет новые задачи.
   3. Когда количество потоков достигает maximumPoolSize, но очередь еще не пуста.
   Неверно. Пока очередь задач не заполнена полностью, задачи помещаются в очередь.
   4. Когда пул потоков задействован на максимум (maximumPoolSize), а очередь задач (workQueue) полностью переполнена.
   Правильно! Исключение RejectedExecutionException при AbortPolicy летит тогда, когда исчерпаны и свободные потоки вплоть до maximum лимита, и очередь не способна принять новую задачу.
   
Подсказка.
Вспомните последовательность обработки задач в ThreadPoolExecutor: сначала corePoolSize, потом очередь workQueue, затем расширение до maximumPoolSize, и только после этого — отказ.
Зачем нужен proxyMode = ScopedProxyMode.TARGET_CLASS при инъекции бина со скоупом request или session в синглтон-бин (singleton)?
[] 
   
   1. Чтобы в синглтон внедрился прокси-объект, который при каждом вызове метода динамически маршрутизирует вызов к актуальному инстансу для текущего запроса/сессии.
   Правильно! Синглтон создается один раз при старте приложения. Если в него внедрить request-бин напрямую, то ссылка навсегда зафиксирует инстанс первого запроса. Прокси решает эту проблему, выступая оберткой-делегатом, перенаправляющей вызовы на актуальный бин из текущего контекста запроса.
   2. Для ускорения сериализации полей синглтона при передаче состояния через распределенный кэш.
   Неверно. ProxyMode никак не связан с сериализацией или кэшированием состояния.
   3. Чтобы обойти архитектурное ограничение JVM на создание потоков для обработки входящих HTTP-соединений.
   Неверно. Потоки веб-сервера управляются контейнером сервлетов/Netty, проксирование скоупов к этому отношения не имеет.
   4. Для реализации ленивой инициализации (Lazy Initialization), чтобы синглтон не дожидался старта веб-окружения.
   Неверно. Цель прокси здесь — не ленивая загрузка, а решение проблемы несоответствия жизненных циклов (short-lived в долгоживущем).

Какое утверждение верно в отношении механизма стирания типов (Type Erasure) в дженериках Java?
[]

Какова ключевая особенность работы сборщика мусора G1 (Garbage-First) по сравнению со старыми поколениями сборщиков (например, Parallel GC)?
[] 
   
   1. G1 полностью исключает паузы Stop-The-World (STW) за счет параллельной фоновой компактификации кучи.
   Неверно. G1 существенно сокращает и делает предсказуемыми паузы, но не исключает STW полностью.
   2. Куча делится на множество одинаковых региональных блоков (regions), и G1 собирает мусор в первую очередь там, где его больше всего.
   Правильно! Название «Garbage-First» отражает его стратегию: куча делится на независимые логические регионы. Сборщик оценивает количество мусора в каждом регионе и очищает в первую очередь те, где сборка выгоднее всего, укладываясь в заданный пользователем лимит времени паузы (MaxGCPauseMillis).
   3. G1 работает исключительно в режиме непрерывной дефрагментации старого поколения без деления на возрастные зоны.
   Неверно. Концепция поколений (Eden, Survivor, Old) в G1 сохраняется, но они больше не привязаны к непрерывным физическим областям памяти.
   4. G1 не использует компактификацию памяти, ограничиваясь исключительно пометкой (marking) мертвых объектов.
   Неверно. G1 умеет перемещать объекты и выполнять компактификацию (evacuation) между регионами, уменьшая фрагментацию.
