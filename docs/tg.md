2. Что такое система контроля версий (git,svn) и зачем они нужны? (Назвать минимум 2 пункта)

Система контроля версий — это программное обеспечение, которое позволяет вести историю разработки. Изменения в коде фиксируются и привязаны к временным отметкам, благодаря чему можно вернуться назад к той или иной версии файлов разрабатываемого кода. Система контроля версий позволяет работать как индивидуально так и в кодманде, ведя сразу несколько историй разных версий кода у разных разработчиков.

Что такое Git и SVN:
- Git — это распределенная система. Копия всей истории проекта находится у каждого разработчика этого проекта.
- SVN (Subversion) — это централизованная система. Вся история хранится на одном сервере, а разработчики скачивают себе только рабочую копию последней версии файлов.

Нужны они для следующих целей:
- Совместная работа осуществляется с помощью концепции веток - историй разных версий кода у разных разработчиков в рамках одного проекта, которые можно объединить в одну ветку.
- История изменений и безопасный возврат по истории назад и обратно к текущей версии. Система сохраняет полную историю изменений: кто, когда и какую строчку кода изменил. Если в текщей версии приложения возникла критическая ошибка - можно быстро вернуться в работоспасобной версии.


3. REST: Разница между GET и POST методами. В чем главное отличие методов GET и POST согласно спецификации HTTP?

Согласно спецификации HTTP, главное отличие заключается в их назначении: метод GET читает данные с сервера и не должен менять состояние системы, к которой он запрашивается. Метод POST отправляет данные на сервер, создавая новую сущность, к которой клиент может обратиться по уникальному адресу URL.

Каждый из них обладает свойствами:

- Идемпотентность и безопасность: GET — безопасный и идемпотентный. При многократных обращениях по URL, состояние базы данных на сервере не изменится, ответ всегда будет одинаковым. POST — небезопасный и неидемпотентный. Каждое новое обращение к одному URL создаст новую сущность в системе(запись в БД или файл). Например, вызов POST /users будет приводить к созданию нового пользователя.
- Способ передачи данных: GET передает данные в строке URL, например, /search?query=java. POST передает данные в теле запроса.
- Кэширование: Ответы на GET-запросы кэшируются по умолчанию, например в браузере или прокси-сервере, так как данные не меняются. Ответы на POST-запросы не кэшируются, так как каждый новый запрос приводит к новому действию на сервере.


4. REST: Обработка ошибок с помощью HTTP-статусов. Какой HTTP-статус должен возвращать ваш REST API, если клиент передал невалидные/некорректные данные для создания пользователя (например, пустой email)? (ошибка на выбор: 400, 500, 404, но надо объяснить)

Если клиент передал невалидные данные в запросе, REST API должен возвращать статус 400 Bad Request, т.к. ошибка произошла на клиенте, например из-за невалидного поля email. 
Статусы 500 и 404 вовзращаются в других ситуациях:
- 500 Internal Server Error — означает ошибку внутри сервера, например, проблемы с обращением к БД или в коде возник неожиданный NullPointerException.
- 404 Not Found — означает, что ресурс не найден по URL запроса. Ресурс может существовать, но запрос к нему идет по некорректному URL


5. Hibernate/JPA: Что принципиально делает технология ORM (на примере Hibernate)?

Технология ORM (Object-Relational Mapping) разработана для связи между объектно-ориентированным кодом с реляционной базой данных.
Связи объектов отображаются на таблицы, связанные внешними ключами. Больше не нужно писать чистые SQL запросы - Hibernate делает это сам автоматически, предлагая свои методы, эквивалентные действиям SQL запросов:
- session.save(user) — для добавления объекта в БД, эквивалентно "INSERT INTO users...",
- session.get(User.class, id) — получение объекта, эквивалентно "SELECT * FROM users WHERE id = ...",
- session.delete(user) — удаление объекта, эквивалентно "DELETE FROM..."

Так же Hibernate способен управлять жизненным циклом объектов и кешированием их в рамках одной сессии. При повторном запросе одного и того же объекта Hibernate сделает в БД один запрос и повторно будет возвращать тот же объект из памяти. При изменении полей объекта Hibernate сам заметит изменения перед закрытием транзакции и обновит строку в базе данных.
Hibernate можно использовать с различными БД, имеющими свои особенности и синтаксис. Достаточно в конфигурации изменить диалект БД.
В Hibernate есть свой объектный язык, позволяющий делать запросы к классам и их свойствам, заменяя запросы на чистом SQL.


6. Hibernate/JPA: Разница между FetchType.LAZY и FetchType.EAGER. Есть 2 таблицы Orders – заказы и Users – пользователи. Как поведет себя Hibernate, если у сущности User есть связь со списком Order с типом загрузки FetchType.LAZY?

LAZY и EAGER отличаются моментом и способом загрузки связанных данных из базы.
Для связи сущностей User и списком Orders как FetchType.LAZY, Hibernate поведет себя следующим образом:

   1) При запросе сущности Users, Hibernate выполнит SQL-запрос только к таблице Users. Вместо реального списка заказов в поле orders он подставит Proxy-заглушку. На этом этапе User находится в состоянии Persistent внутри транзакции.
   2) При обращении к коллекции Orders (например, вызов user.getOrders().size()) произойдет следующее:
   		- Если сессия еще открыта (внутри метода под @Transactional), Proxy-заглушка автоматически отправит в БД дополнительный SQL-запрос к таблице Orders, чтобы наполнить коллекцию реальными данными.
   		- Если сессия уже закрыта (метод завершился, и объект перешел в состояние Detached), попытка обратиться к коллекции выбросит исключение LazyInitializationException, так как у Proxy больше нет связи с базой данных для отправки запроса.

9. Что произойдет, если внедрить (inject) бин с областью видимости prototype в бин с областью видимости singleton через стандартное поле (@Autowired)?

По умолчанию Singleton-бин создается один раз для всего приложения, живет в Heap и не имеет состояния. Prototype-бин создается на каждый вызов и хранит состояние. При внедрении Prototype в Singleton через @Autowired, из-за разных областей видимости Prototype зафиксируется внутри Singleton всего один раз при старте приложения. Ссылка на него запишется в поле Singleton-бина в Heap и больше обновляться не будет. Поэтому Prototype станет доступен всем потокам Java одновременно через общую память Heap. При одновременных запросах потоки будут конкурентно перезаписывать состояние этого бина, что приведет к состоянию гонки.
